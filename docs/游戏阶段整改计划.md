# M3E Canvas Pro 游戏阶段整改计划

> 本计划里的包编号（H1、J1、E1、P1、X1……）和决策编号（K1–K7）只在本计划的批次内有效，和第四、五批交接里同名的工作包无关。

Nov 9, 2026 · @AGI\_FireFly

## 概述

游戏阶段要把 M3E 从“导出应用”扩展到“导出引擎工程的界面层”：第五批之后再做五批（第六到第十批），交付 Cocos 小游戏和 Godot PC 两个导出目标，以及它们所需的设计模型扩展和外部接入。这份计划把 `docs/交接.md` 第六节“之后：游戏阶段”的四条方向拆成可执行的批次，格式沿用 `docs/整改计划.md`。

**完成的定义**（来自 `docs/交接.md` 第六节，逐条可验收）：

1. 除实时画面外全部做完：局外界面、HUD、弹窗、输入、流程都能设计、预览、导出。
2. 所有接口定义清楚：玩法契约（命令、事件、快照、时钟）、宿主契约、能力接口都是机器可读的文件。
3. 实时画面用文字提示加图像模拟场景变化；模拟库里的 3D 模型（glb、gltf、obj、stl）用于模拟 3D 接口。
4. 导出符合引擎规范的完整代码框架：核心游戏循环的算法留空，所有按键交互齐全。

**不做的事**（沿用《边界与契约》）：

- 不写玩法规则、数值、随机结果、权威时间：这些由 game-loop 提供，M3E 只读快照、只发意图。
- 不做世界画面：场景、物理、镜头、动画、特效由引擎工程负责，M3E 只生成宿主桥接和界面层。
- 不生产资产：美术、音频、材质由资产管线（含 Material Pro）提供，M3E 只按 ID 引用。
- 不嵌引擎 SDK、不放密钥：平台能力仍然只定义接口，适配写在只写一次的自定义文件里。

## 现状与依据

第五批完成后，M3E 能做 Web / H5 游戏（M3E 应用做宿主、世界作为视口），但还不能进入 Godot 或 Cocos 工程。完整产品的导出目标只有 9 个（`lib/export/targets/index.ts:18`），全部分支里没有引擎导出代码；《M3E审查及整改建议报告》也没有点名任何引擎。

| 方面 | 现在有的 | 第五批之后仍缺的 | 出处 |
| --- | --- | --- | --- |
| 导出目标 | Web、Expo / RN、Taro 小程序、契约、模拟库、运行时、能力、后端、契约测试 | Godot、Cocos 两个目标 | `lib/export/targets/` |
| 屏幕中间表示 | RN 和小程序打印器共用 | 引擎打印器 | `lib/export/ir/` |
| 组件套件 | `rn/`、`miniapp-kit/`，第三批做到原生 166 / 原子树 49 / 占位 1 | 引擎节点版套件 | `docs/手机端.md`、`docs/小程序.md` |
| 交互 | 点击是 Action 数据，一个解释器，五宿主一致性表 | 引擎宿主的解释器和一致性行 | `lib/actions/` |
| 数据 | 数据源、表单、会话，请求回答后 React 重新渲染 | 逐帧绑定、世界快照的表达式根 | `lib/app/`、`lib/bindings/expr.ts` |
| 界面结构 | 屏幕栈、浮层、流程 | 叠在世界上的层、锚定、按事件生成、焦点导航 | `lib/tokens.ts` |
| 游戏组件 | 抽奖类 `result`/`pending`/`settled`，摇杆 `vec2`，技能键 `cooldown` | 接玩法契约的绑定写法 | `parts/defs/game.ts` |
| 外部接入 | 可换传输层（`window.m3ePreviewTransport`、`setTransport`） | 玩法契约导入、链接数据、`asset:<id>`、材质包 | `components/Preview.tsx:182` |

两点容易混淆：小程序（Taro）不是小游戏，小游戏只有 Canvas，Taro 产物放不进去；Material Pro 导出到 Godot、Cocos 的是材质和贴图，属于资产管线，不是 M3E 的界面。

## 开工前要定的决策

七个决策要在第六批开工前定下，其中 K1、K2、K3 会影响第五批的契约设计，最好在第五批开工前就定。

| 编号 | 决策 | 建议 | 理由 |
| --- | --- | --- | --- |
| K1 | 两个目标用哪种宿主方式 | Godot PC 和 Cocos 小游戏都由引擎做宿主；Web / H5 继续用 M3E 应用做宿主 | 小游戏没有 DOM，Godot 是原生程序，都容不下 M3E 的 React 应用 |
| K2 | 玩法契约由谁写 | game-loop 写，M3E 导入、只读；OpenAPI 里 `game.*` 命名空间的操作由 game-loop 生成 | 《边界与契约》契约 9：每份契约只有一个作者 |
| K3 | HUD 的绑定模型 | 分两类：低频绑定继续走数据源；高频绑定读 `world` 快照，导出为逐帧代码，不经过 React | 血条、冷却、伤害数字每帧都变 |
| K4 | Godot 里的运行时语言 | 生成 GDScript 版的运行时和解释器；嵌入 JS 运行时作为备选 | GDScript 无第三方依赖、导出全平台；代价是要保持两份实现语义一致，靠一致性表守住 |
| K5 | game-loop 在 Godot 里怎么跑 | 由 game-loop 决定；在上线前先用本地端口接独立进程 | M3E 只依赖 World 接口，不依赖规则的语言 |
| K6 | 引擎版本 | Godot 4.x、Cocos Creator 3.8.x，按仓库惯例锁定精确版本，只在 `lib/exportPackages.ts` 写一处 | 版本单一来源是第四批定的规则 |
| K7 | 先做哪个引擎 | 先 Cocos，再 Godot | Cocos 是 TS，`lib/app` 和 `lib/actions` 基本可以复用；小游戏也是目标平台 |

待确认：Cocos Creator 编辑器只有 Windows 和 macOS 版本，CI 里的引擎构建检查需要 macOS 或 Windows 运行器；Godot 有 Linux 无头模式，可以放在现有 CI 里。

## 对第五批的要求

第五批的三项（实时通道、世界视口和输入动作、`now` 由传输层提供）定下的是游戏阶段要依赖的契约，所以要按“将来有引擎宿主”来设计，否则到第八批要返工。下面六条建议写进第五批的验收。

1. **World 接口和引擎无关**：接口只用可序列化的类型（数字、字符串、`Vec2`、ID），`mount(host)` 的 `host` 由宿主定义，不假设是 DOM 节点。
2. **输入动作有名字和类型**：摇杆、技能键发出的是声明过的动作（`move: vec2`、`skill1: bool`），将来可以再映射到键盘和手柄，不挂在触摸事件上。
3. **快照和事件各有 Schema**：`view()` 的快照和 `on(event)` 的载荷都用 JSON Schema 描述，导出时能生成 TS 和 GDScript 的类型。
4. **时钟域是契约的一部分**：`clock()` 给出世界时间、是否暂停、倍率，冷却和倒计时只按它推算，不读墙钟。
5. **宿主契约单独成文件**：输入优先级、HUD 遮挡区域（`occlude`）、浮层打开时释放输入、暂停策略、生命周期，写成一份不依赖 Web 的规范。
6. **验收里的“最小引擎示例”只走接口**：示例只通过 World 接口和 M3E 交互，第八批可以用同一个示例验证 Cocos 宿主。

## 批次总览

游戏阶段分五批：先扩展设计模型（第六批）和接入外部模块（第七批），再做 Cocos（第八批）和 Godot（第九批），最后用引擎框架和示例游戏收尾（第十批）。

依赖关系（原文是一张图）：

```
第五批（前提）
  └─ 第六批 设计模型扩展（H1–H7）
       ├─ H2 逐帧绑定 ── 第七批 接入玩法契约、数据和资产（J1–J7，可与第六批后半并行）
       └──────────────┬─ 第八批 Cocos 小游戏导出（E1–E10，依赖第六批与 J1）
                      └─ 第九批 Godot PC 导出（P1–P9，依赖第八批）
                           └─ 第十批 引擎框架、一致性与示例游戏（X1–X5，依赖第八、九批）
```

虚线框的第五批是前提，不属于本计划；第七批只依赖第六批的 H2，可以和第六批后半并行；第九批不再改设计模型和契约，只新增 Godot 适配层。

## 第六批：游戏界面的设计模型扩展

目标：让设计模型能表达局内界面，并在 Web 预览里跑通。这一批只改编辑器、预览和项目文件，不碰引擎；引擎导出是它的下游。依赖：第五批。

| 包 | 内容 | 落在哪里 |
| --- | --- | --- |
| H1 分层 | 屏幕可以标为世界层、HUD 层、弹窗层、提示层，叠在 `world-view` 上，不替换世界；层的顺序和输入优先级按宿主契约 | `lib/tokens.ts`、`lib/interact.ts`、预览 |
| H2 逐帧绑定 | 表达式新增 `world` 根（读快照），绑定可标为高频；高频表达式只允许廉价的读取和算术，预览里用 `requestAnimationFrame` 直接更新，不经过 React 状态 | `lib/bindings/expr.ts`、`lib/app/` |
| H3 锚定组件 | 组件可以锚到实体（实体 ID 来自快照），带偏移、贴边、超出屏幕时的箭头、被遮挡时隐藏；投影由宿主提供 | `parts/types.ts`、布局引擎 |
| H4 按事件生成 | “每收到一次 `Damaged` 事件就用这个模板生成一个实例”，带寿命、上限和对象池；写法对应现在的“按数据重复” | `lib/collections.ts`、解释器 |
| H5 焦点和输入映射 | 手柄和键盘的焦点顺序（上下左右、确认、取消）；输入动作到按键的映射表；界面按当前输入设备显示按键提示 | `lib/actions/`、新增 `Doc.inputs` |
| H6 世界模拟 | 没有引擎时 `world-view` 用文字提示加图像模拟场景变化；模拟库按脚本产出快照和事件；3D 模型（glb、gltf、obj、stl）用来模拟 3D 接口 | `lib/mocks/`、`world-view` |
| H7 格式版本、AI 和 MCP | 以上字段随一次格式迁移入库；应用内 AI 和 MCP 增加对应工具；边界规则增加“不在 HUD 里结算玩法”的负例评测 | `lib/migrations.ts`、`lib/tools/`、`evals/` |

验收：

- 战斗模板改成分层写法：20 个敌人的头顶血条、伤害数字、技能冷却在预览里由模拟世界驱动，编辑器性能基准里每帧不触发 React 提交。
- 浮层打开时输入按宿主契约释放，关闭后恢复；只用键盘能走完大厅、商城、背包、暂停菜单。
- 旧文件打开外观不变（历史文件回归）；评测不低于最新基线。

## 第八批：Cocos 小游戏导出

目标：完整产品增加 `games/cocos` 工作区，一个 Cocos Creator 3.8 工程，能构建微信和抖音小游戏。依赖：第六批、第七批的 J1。沿用第三批 D1–D5 的并行方式，套件按类别拆包。

| 包 | 内容 |
| --- | --- |
| E1 工程骨架 | `cocosTarget`（`lib/export/targets/`）：工程结构分 `assets/generated/` 和 `assets/custom/`，生成文件记入 `.m3e/manifest.json`；`custom/setup.ts`、`custom/capabilities.ts`、`custom/slots/`、`custom/world/` 只写一次 |
| E2 打印器 | 从 `lib/export/ir/` 生成预制体和场景（Cocos 的 JSON 格式，含 uuid 和 `.meta`）；自动布局对应 Layout + Widget；不用字符串拼接和正则，沿用报告 9.6 的规则 |

| E8 风格、字体和外观 | 主题角色映射到引擎的颜色和字体；引擎画不出的效果（毛玻璃、混合模式等）列表，写进导出报告，就像 `docs/小程序.md` 的“画不出来的效果”；材质层的 `surface` 用平铺 Sprite，`shading` 用叠加着色器 |

- 商店示例和战斗模板导出后，在 Cocos Creator 里打开无报错，构建出微信小游戏包。
- 局外界面在模拟库和真实后端上各跑一遍；局内 HUD 由第五批的最小引擎示例驱动。
- 一致性表在 Cocos 列无新增分歧；再导出一次时 `custom/` 完全不变。

## 第九批：Godot PC 导出

目标：完整产品增加 `games/godot` 工作区，一个 Godot 4 工程，能导出 Windows、macOS、Linux 版。依赖：第八批（复用它的分层宿主、逐帧绑定和套件拆包方式）。这一批也是模块化的检验：只新增 Godot 适配层，契约和设计模型不动。

验收：

- 同一份设计导出到 Cocos 和 Godot，局外流程和 HUD 行为一致（一致性表无新增分歧）。
- 只用手柄能走完标题、大厅、关卡选择、战斗、暂停、结算。
- 第八批之后，设计模型和玩法契约为 Godot 做的改动为零。

## 第十批：引擎代码框架完善、一致性与示例游戏

目标：兑现“核心循环的算法留空、所有按键交互齐全”，并用一个跨三个宿主的示例游戏证明整条链路。依赖：第八批、第九批。

| 包 | 内容 |
| --- | --- |
| X1 引擎框架 | 两个引擎工程都生成：World 接口的桩（每个方法都在，算法留空并带说明）、输入映射到动作的全部接线、事件到表现的插槽（哪个事件播什么动画、特效、音效由 `custom/` 填写）；接上 game-loop 后不改生成代码就能跑 |

## 外部模块的接口约定

M3E 只读下面这些文件，不 import 任何模块的实现；每份文件只有一个作者，都带版本号。这些模块不在本计划范围内，但第七批到第十批的验收依赖它们。

| 模块 | 要提供的文件 | 内容 | M3E 用在哪一批 |
| --- | --- | --- | --- |
| game-loop | 玩法契约 | 命令（参数、拒绝码）、事件、快照 Schema、时钟域、它接受的“外部事实”命令 | 第七批 J1 |
| game-loop | Transport 实现和 World 实现 | 低频走传输层，高频走 World 接口；开发时的本地服务 | 第七批 J2、第十批 X1 |
| game-loop | fixture | 确定的游戏状态 | 第七批 J3 |
| 数据模块 | 数值表 + Schema | 物品、角色、关卡参数、本地化文本；引用的实体 ID 和资产 ID 都已校验 | 第七批 J4 |
| 资产管线 | 资产清单 | 稳定的资产 ID → 文件、类型、尺寸、各平台变体、来源和授权 | 第七批 J5、第八批 E9 |
| Material Pro | m3e 材质包 | `.m3e-material.json`，版本 1 | 第七批 J6 |
| 中枢 | ID 注册表和契约索引 | 各模块的命名空间、契约版本；接收 M3E 的缺口文件 | 第七批 J7 |

开放问题：中枢放在哪个仓库（单独一个，还是放在 game-loop 里），在第七批开工前定。

已定的处理方式（2026-11-09，作者同意）：M3E 只依赖中枢两份文件的**格式**，不依赖它们放在哪里——

- 契约索引是一个 JSON 文件（各模块的命名空间、契约版本、契约文件的位置），读取路径是项目里的一项配置；
- 缺口文件写在导出产品里的固定位置（`.m3e/gaps.json`），同时列在导出报告里；
- 测试用仓库里的最小示例文件（第七批建在测试夹具里）。

中枢定下来之后只改那一项配置，不改代码。

两份格式已在第七批 J7 定下（细节见[导出](导出.md)“缺口文件”“中枢的契约索引”）：

- 契约索引：`m3e-contract-index` 版本 1，JSON Schema 在 `lib/hub/contract-index.schema.json`，最小示例在 `lib/hub/fixtures/contract-index.json`；`modules` 按模块 ID 列出 `namespace`、`contractVersion`、`contract`（相对索引的路径或 `https://` 地址）和可选的 `format`。读取路径是项目配置 `document.external.contractIndex`（默认项目文件旁边的 `contract-index.json`）。导出时用它检查玩法契约的版本，不一致是 `contract-version` 缺口。
- 缺口文件：`m3e-gaps` 版本 1，写在产品的 `.m3e/gaps.json`，每条 `{kind, module, ref, reason, detail, where[]}`；现有的种类是 `asset`、`game-*`（含快照字段 `game-snapshot` 和事件载荷 `game-payload`）、`data`（链接数据过期，J4 按 `LinkedData` 接口接入）和 `contract-version`。

## 风险、门禁与执行方式

**风险**

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 第五批契约只照着 Web 宿主定 | 第八批要返工 | 把“对第五批的要求”六条写进第五批验收 |
| 套件工作量被低估 | 引擎批次延期 | 参照第三批 D1–D5；先做游戏模板用到的组件，其余先走插槽并在报告里列出 |
| TS 和 GDScript 两份运行时语义分叉 | 同一份设计在两个引擎里行为不同 | 一致性表对两份运行时跑同一份用例；或改用嵌入 JS 运行时（K4 备选） |
| 引擎编辑器不能在 Linux CI 跑 | Cocos 构建检查缺失 | 单独的 macOS 或 Windows 任务；在它之前先做类型检查和预制体结构校验 |
| 逐帧绑定被用来写玩法 | 违反《边界与契约》 | 高频表达式只读、有上限；AI 边界评测加负例 |
| 外部模块未就绪 | 第七批以后无法验收 | 每个接口先写一个最小的示例文件，放进测试夹具 |

**门禁**：沿用现有全套（typecheck、lint、check:icons、check:icon-sets、check:versions、check:rn、check:miniapp、test、build、mcp:build、test:e2e）；第八批起加 `check:cocos`，第九批起加 `check:godot`；动到导出时跑 `check:product`。每项修复都要有在旧代码上失败的测试；旧文件打开外观不变。

**执行方式**：沿用前几批的多代理协作——协调者在集成分支上合并，每个工作包一个代理、一个分支、一个独立工作目录，按文件归属划分。第八、第九批的套件包可以并行；打印器和运行时包要先合入。每批结束更新 `docs/交接.md` 和 `docs/整改计划.md` 的进度记录，跑真实模型评测并存新基线。
