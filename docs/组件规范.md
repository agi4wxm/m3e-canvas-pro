# 组件规范

所有组件都按这份规范写。下面标了“自动”的约定由 `parts/contract.test.ts` 检查，违反就测试失败。现有组件见[组件清单](组件清单.md)，每个来源的组件由谁承担见[组件盘点](组件盘点.md)。组件负责什么、不负责什么，按[边界与契约](边界与契约.md)判断：组件把状态画出来、把意图送出去，不决定领域结果。

## 一句话规则

**一个组件只写一份定义。** 面板、属性面板、画布、预览、提示词和导出代码都读这一份。它是什么输入、发出哪些事件、哪些格子共用一个动作、演示什么，也写在这份定义里，不在别处按组件 ID 列名单。

**领域真值在组件外面。** 余额、是否已领取、抽中什么、是否支付成功从属性进来；组件只保存表现状态和有明确契约的界面草稿，领域演示只在显式的原型模式里运行。

## 文件放在哪

```text
parts/
  registry.ts      所有组件的注册表，两层和 19 个分类
  defs/*.ts        组件定义：纯数据，不引用 React
  defs/atoms.ts    盒子、矢量图形、单选按钮、状态圆点这几个原子
  defs/splits.ts   组合组件拆成原子时的原子树
  defs/retired.ts  退役的整块组件：改用什么，以及它们中原来没有拆分的原子树
  atoms.ts         拼原子树用的小函数（box、hbox、vbox、text、icon……）
  svg.ts           矢量图形的图形库和粘贴代码的清理
  kits/*.ts        组合件：只以原子树存在的组合组件，每个领域一个文件
  kits/shared.ts   组合件共用的：kit()/variant() 简写、看风格的判断、分组列表、分隔线、常用词
  widgets/*.tsx    M3E 没有现成组件时，自己写的组件
  widgets/host.ts  渲染方交给自带组件的东西：是否运行演示、交出输入值、发出事件
  widgets/sources.ts  每个自带组件在哪个文件
  catalog.ts       给 AI 看的组件清单
lib/kits.ts        组合件和拆分落到文档里：展开、排布、落点、按风格选变体
components/m3e/    shadcn M3E 组件库
```

## 两层：原子组件和组合组件

**原子组件**不能再拆：盒子、文字、图标、矢量图形、图片、按钮、输入框、开关、头像、徽章……**组合组件**由原子组成：搜索栏、列表行、卡片、应用栏……想要的组件面板上没有时，用原子在嵌套的盒子里拼出来，就像在 Figma 里嵌套自动布局框架。

每个分类属于一层，由 `parts/registry.ts` 导出：

| 导出 | 说明 |
| --- | --- |
| `CATEGORIES` | 19 个分类，按面板顺序，原子在前 |
| `CATEGORY_TIER` | 每个分类属于 `"atom"` 还是 `"composite"` |
| `tierOf(def)` | 一个组件（或组合件）属于哪一层 |
| `categoriesOf(tier)` | 一层里的分类 |
| `CATEGORY_TEXT`、`CATEGORY_ICON`、`TIER_TEXT` | 分类和层在四种语言里的名字、图标 |

| 层 | 分类 |
| --- | --- |
| 原子 | 基础（Basics）、控件（Controls）、指示（Indicators） |
| 组合 | 操作、表单、选择器、栏与导航（Navigation）、菜单与搜索、弹出层、反馈、布局容器、列表、数据与图表、电商与支付、社交与聊天、AI 对话、媒体、游戏、桌面软件 |

其他代码只通过 registry 读分类，不自己写分类名。

### 原子的约定

- **盒子 `box`**：通用框架。能放组件（`holds`），自动布局默认打开（竖排），宽高默认随内容（还没有随布局排列的内容时按自己的宽高画，画布和导出代码一样），没有标题和虚线框。它只画 `surface` 表面角色：`none`（默认，看不见）、`card`、`panel`、`field`（输入框的外框）、`bar`、`chip`、`button`、`sheet`、`overlay`、`well`。从面板手动加的盒子先是 `panel`，好看见、好往里放（`PartDef.seed`：手动加入时的初始属性，手动加的文字同样先随文字宽度）；模板、组合件和 AI 写的盒子没写表面就是 `none`。根节点带 `data-slot="box"` 和 `data-surface`，风格按表面角色打扮盒子，所以用盒子拼出来的组合组件跟着风格走。填充色、圆角和外观涂在根节点上。
- **盒子钉在屏幕边上 `pin`**：盒子在屏幕上站在哪：`none`（默认，正文里的一行）、`top`（钉在顶部）、`bottom`（钉在底部）、`floatingBottom`（悬浮在底部）。盒子的 `role` 由它算出（`role: (p) => …`，`none` 没有角色），所以钉住的盒子就是屏幕的栏，和真正的栏一样处理：整理（`lib/tidy.ts`）把它钉到那条边上、留在设备状态栏和手势条（安全区）之内，多条栏按原来的上下顺序叠在一起；风格的版式（`lib/styleLayout.ts`）把 `top`、`bottom` 的拉成正文一样宽（有侧边导航轨时就是轨旁边剩下的宽度），并且不再随内容（`hugWidth: false`），`floatingBottom` 的保持自己的宽度、最宽到正文的内容宽度，居中、离底边留风格的边距。它始终是盒子：风格的 `navAs` 只把真正的导航组件（`navigation-bar`、`navigation-rail`、导航标签页）换成另一种，组合件的标签栏在侧边导航轨风格里也留在手机底部，宽屏上也是底栏。`fullWidth` 对钉在顶部或底部的盒子为真。导出代码把钉住的盒子包在 `absolute inset-x-0 top-0 / bottom-0` 里、根节点宽 100%（不在边上时 `top-[y]`），长屏幕滚动时它和它里面的东西一起固定（预览同样）；提示词在它后面写明“固定在屏幕顶部/底部、与屏幕同宽、滚动时不动”。`pin` 只对不在自动布局里的盒子有意义：属性面板只在盒子不被布局排列时显示它（`PropDef.screen`），放进布局的盒子按布局排，提示词也不说它钉在哪。没有 `pin` 的旧文档和以前完全一样。
- **矢量图形 `svg`**：图形库（丝带横幅、爆炸星、波浪、六边形、盾牌、气泡尾巴、角花、闪光、超椭圆……）、一条路径（`path` + `viewBox`），或粘贴 SVG 代码。粘贴的代码由 `parts/svg.ts` 自己解析，只留下画图的元素和属性：脚本、样式、事件、`foreignObject`、图片、外部链接和 `javascript:`、`data:` 都去掉。颜色默认跟随文字色（`currentColor`），代码里自己写了颜色的照用。粘贴的代码也会随分享链接传给别人，所以还有这几条：
  - **地址**：属性和 `style` 里的值先解开实体（`&quot;` 就是引号）再检查。`url()` 只能是指向图内部分的 `url(#名字)`，不管怎么加引号；别的 `url()`（含引号、括号、换行写法）、`image-set()`、`image()`、`src()`、`cross-fade()`、`element()`、`attr()`、`expression()`、`@import`、`javascript:`、`vbscript:`、`data:`、反斜杠转义和控制字符，出现在哪个值里，那个值就整个去掉。只有 `fill`、`stroke`、`mask`、`clip-path` 能带 `url(#…)`。
  - **名字**：图里每个 `id` 都加上这个组件自己的前缀（由组件的 ID 算出，画布、预览、导出代码都一样），`url(#…)` 和 `use` 的 `href="#…"` 跟着改；指向图里没有的名字的引用去掉，重名的只认第一个，最外层 `svg` 的 `id` 不算图里的名字。两张图都把渐变叫 `g` 也各画各的。
  - **规模**：最多 4000 个元素、嵌套 64 层，更深的连同里面的内容一起去掉。`use`、遮罩、裁剪、图案（`fill`/`stroke` 指向图案时按涂到的元素数计）合起来最多比图本身多画 2000 个元素，超出的那条引用去掉；成环的引用和超过 8 层的连环引用也去掉。指向渐变不计数。
  - 清理永远不抛错；画不出来的组件由错误边界换成“无法绘制”（见“容错”）。
- **文字 `text`**：`fit: "auto"` 随文字宽度（放在横排里用），`fit: "fixed"`（默认）在宽度内换行，竖排拉伸时宽度由盒子给；`maxLines` 超出显示省略号。
- **输入框 `input`、多行输入 `textarea`**：`variant: "plain"` 没有边框、底色和内边距，外面的盒子就是输入框。它的 `data-slot` 是 `plain-input` / `plain-textarea`，风格对输入框的打扮落在外面的 `field` 盒子上，不落在它上面。多行输入的 `autoGrow` 随内容增高。
- **按钮**：`trailingIcon` 是文字后面的图标（模型选择的下拉箭头）；`button` 和 `icon-button` 有不带底色的 `ghost` 变体；`icon-button` 的 `iconFill` 用实心图标。
- 原子要能被组合：放进横排时不能强占固定宽度。没有宽度属性可读的原子写 `guess`，在画布量出真实尺寸前给排布一个估计。

## 加一个组合件

组合件是只以原子树存在的组合组件，放在 `parts/kits/` 里，每个领域一个文件，登记到 `parts/kits/index.ts` 的 `KITS`。

```ts
const box: KitDef = {
  slug: "prompt-box",           // 不能和任何组件重名
  name: "Prompt box",
  labels: { zh: "输入框", ja: "入力ボックス", ko: "입력창" },
  category: "AI",               // 一个组合层的分类
  icon: "chat",
  about: "a card holding a plain textarea over a row of buttons",  // 给 AI 看的一句话
  variants: [
    {
      key: "home",
      name: "Home",
      labels: { zh: "首页", ja: "ホーム", ko: "홈" },
      suits: (look) => look.group !== "desktop",   // 可选：哪些风格默认用它
      build: (look) => vbox({ surface: "card", width: 380, hugWidth: false, padX: 16, padY: 16, gap: 16 }, [
        area(say("Ask anything", "有问题，尽管问", "何でも聞いてください", "무엇이든 물어보세요")),
        hbox({ justify: "between" }, [iconButton("add", say("Add", "添加", "追加", "추가")), iconButton("arrow_upward", say("Send", "发送", "送信", "보내기"), { variant: "filled" })]),
      ]),
    },
  ],
};
```

- 只用原子组件，只有盒子能放东西（测试检查）。用 `parts/atoms.ts` 里的 `box`、`hbox`、`vbox`、`text`、`para`、`icon`、`iconButton`、`button`、`entry`、`area`……新文件里用 `parts/kits/shared.ts` 的 `kit(slug, name, [zh, ja, ko], 分类, 图标, about, 变体)` 和 `variant(key, name, [zh, ja, ko], build, { suits, span })` 简写，最外层盒子自动以组合件的名字命名。
- 每个组合件至少有一个变体适合 Material（没有 `suits`，或 `suits(MATERIAL_LOOK)` 为真），变体按顺序挑第一个适合的，所以默认的放在最前、不写 `suits`（测试检查）。
- 文字用 `say(en, zh, ja, ko)` 写四种语言，加入时按编辑器语言写入。
- 变体是同一个东西的不同组合方式。要跟风格走的写 `suits(look)`：`KitLook` 由 `lib/kits.ts` 的 `kitLookOf(theme)` 从主题算出，组合件代码里不写任何风格名。它有：风格的分组（`group`）；各类控件的配方（`field`、`bar`、`button`、`list`、`surface`、`toggle`、`nav`、`tabs`、`segmented`、`dialog`、`sheet`、`appbar`、`row`、`card`、`avatar`、`dialogue`）；窗口按钮在哪（`caption`：Mac 字体或手机产品的风格是左侧红绿灯 `lights`，Windows 字体、桌面软件、游戏和 Material 是右侧按钮 `buttons`）；是否紧凑、深浅色、边距。`shared.ts` 里有常用的判断：`isGame`、`isDesk`、`isDense`、`isIosLike`（居中提醒、分组列表、iOS 分段）、`isWeui`、`groupingOf`（分组列表是圆角卡片 `inset`、通栏 `flush` 还是不分组 `bare`）。`build(look)` 也能读它（比如分组列表的行按风格放进卡片）。跟屏幕一样宽的（顶栏、底栏）写 `span: "screen"`。
- 屏幕的栏写成钉住的盒子：最外层盒子带 `pin`（只有最外层可以带，测试检查）。顶部栏、游戏顶部信息栏、分段标题栏、模型选择栏、窗口标题栏、手机状态栏是 `top`；底部标签栏、购买栏、聊天输入栏、底部选项面板、贴底工具栏、编辑器状态栏是 `bottom`；悬浮胶囊标签栏、悬浮工具栏、iOS 分组选项面板是 `floatingBottom`（悬浮胶囊本身就是最外层盒子，不再套一层通栏的透明盒子）。栏里横排的中间文字写成占满剩余空间、只占一行（`para(…, { maxLines: 1 }, { grow: true })`）的文字，不要用 `push()` 撑开：风格换成更宽的字体（魂系、悟空的衬线字，赛博朋克的窄体，星露谷的像素字，消除休闲的粗圆体）时，是中间的文字被截短，而不是把行尾的按钮、资源胶囊挤出屏幕。
- 颜色要能跟着深浅色和风格变：盒子用表面角色和填充角色（`surface`、`inverseSurface`……），不要按放下时的深浅色写死“反色盒子”——文档之后切换深浅色时它会变成白盒子。按钮（`button`、`icon-button`）上不写填充色（测试检查）：有的风格把按钮画成没有底色的文字（魂系），会去掉填充色、却留下给填充色配的字色，字就看不见了；主操作用按钮自己的 `filled` 变体，由风格决定颜色。Codex 风格输入框就是跟着页面的面板，主按钮是风格的实心按钮（Codex 风格下正是黑底白字）。设置行的图标底块是涂了 `primary` 的 `well` 盒子，不是 `button` 表面。
- 画布上组合件的每个原子各画各的，不嵌在盒子的 DOM 里，所以文字不会从盒子继承颜色：放在有颜色的盒子上的字要自己写颜色角色（`on-primary`、`inverse`），不能指望“跟随外层”。
- 一组相邻的行用 `section(rows, look, textAt)`：分组的风格里是一个 `card` 表面的盒子，行之间的分隔线从文字处（`textAt`）开始（`insetRule`），iOS 是灰底上的圆角卡片，微信是通栏白底；Material 不分组。分隔线是 1px 高的盒子（`rule`），在竖排里会被拉伸，`separator` 原子的长度是固定的。
- 竖排只有在宽度不随内容时才拉伸子项（`lib/flow.ts`）。要拉伸的子项（分隔线、进度条）放在给了宽度的竖排里，或者竖排本身被外层拉伸。
- 节点可以带 `name`、`grow`（占满剩余空间）、`fill`（填充色角色）、`textColor`、`corners`、`look`。严格遵守风格时圆角和外观会被风格去掉，所以组合件不能只靠它们好看，主要靠表面角色和组件自己的变体。产品自己画的形状（冷却弧、星星、爆炸星、丝带、红绿灯）用矢量图形原子；外观（`lib/look.ts` 的预设，如游戏按钮的厚边 `pressedLip`、稀有度的 `goldFrame`、标题的 `gameTitle`）只是锦上添花。表面会被风格当成按钮打扮的（`surface: "button"`），有的风格画成没有底色的文字按钮，上面的字不要只靠 `on-primary`；要一个实心圆时用 `fill: "primary"`。
- 盒子不能叠放：角标、压在封面上的头像只能排在相邻的一行或一列里。
- 画廊 `/gallery?kits=1` 按画布同样的方式（先按估计排、量出真实尺寸后再排，直到不动）画出每个组合件的每个变体，当前风格选中的标 ★；`chosen=1` 只画选中的；`splits=1` 把每个可拆的组件和它拆出的树并排画出来。
- 盒子的宽高会自动和外层对上：被竖排拉伸、或在横排里占满剩余空间的盒子不再随内容（`settleSizes`），不用自己写。

加入文档由 `lib/kits.ts` 完成：`kitGroups(kit, look, lang, { variant, at, screen, theme })` 把树展开成分组（最外层盒子在前，其余用 `inFlow` 指向所在盒子），按估计尺寸排好，在手机上收窄到内容宽度；`landTree` 把它放进松手处的屏幕。最外层盒子钉在边上的（栏）不管在哪里松手都直接落到那条边：顶部的落在状态栏下、已经叠在顶部的栏下面，底部的落在手势条上、已经在底边的栏上面，悬浮的再留风格的边距、水平居中；通栏的落在侧边导航轨旁边，宽度是轨留下的宽度（`landTree` 的最后一个参数是画布上已有的东西）。编辑器里拖放和点击都是一步撤销，选中最外层盒子。

### 组合件记得自己是什么，换风格时重新组合

组合件的变体就是它的组合方式，是按加入时文档的风格挑的。为了让文档之后换风格时组合也跟着换（像整块组件靠 CSS 换装一样），最外层盒子带一个标记 `Group.kit`：

| 字段 | 说明 |
| --- | --- |
| `slug` | 哪个组合件 |
| `variant` | 现在是哪个变体 |
| `auto` | 变体是风格挑的（从面板点或拖组合件本身）；从变体菜单手动选的是 `false` |
| `sig` | 加入（或上次重新组合）时整棵树说了什么的签名（`kitSig`） |

签名算的是盒子里的一切：每个组件的 ID（`slug`）、属性、填充色、文字色、圆角、外观、备注、绑定的变量、在布局里的要求、里面各层的名字和显示/隐藏，以及嵌套关系和顺序。不算：各组件的 ID、位置、布局写下的宽高（尺寸）、点击跳转；最外层盒子自己的位置、钉在哪条边（`pin`）、名字、锁定、隐藏、显示条件、所在的布局和它在布局里的要求，这些是盒子自己的，重新组合时原样保留。签名按主题的规则读：严格遵守风格时被风格去掉的圆角和外观不算改动。

**什么时候重新组合：** 文档的主题变化让 `kitLookOf(theme)` 变了（选风格、打开规则、切深浅色、改控件配方或字体），编辑器在规则整理（conform）之前调用 `recomposeKits(doc, from, to, lang, { frames, widths })`，屏幕上和可复用组件定义里的每个组合件都看一遍：

- 签名和现在的内容一致（没人改过）：按新风格挑变体（`auto` 为真时重新挑；手动选的变体只要还在就保留），在原位置重建盒子里的一切。最外层盒子保留 ID、左上角位置、所在的自动布局和顺序、名字（人改过的名字）、锁定、隐藏、点击跳转；人改过的宽度保留（和原组合的宽度不同就算改过），否则用新组合的宽度。里面原子上的点击跳转按文字或图标找到新组合里说同样话的那一个（返回按钮还是返回按钮，同样文字的行还是那一行）。之后更新 `variant` 和 `sig`。新组合变高或变矮时，屏幕上它下面、和它横向重叠的自由组件（连同它们里面的东西）跟着上下移动同样的距离，免得被新的盒子盖住、收进盒子里；贴在屏幕底边的（底栏）不动。钉在边上的（`pin`）没人改过时跟新组合走（同一个组合件的变体可以一个悬浮、一个贴底），人改过的（和原组合的不同，包括改成 `none`）保留；加入时还没有 `pin` 的旧组合件重新组合后也不带 `pin`。钉在底部或悬浮在底部的盒子新组合变高或变矮时，保持底边不动、往上长。
- 改过（任何一个字、加进或拿出一个组件、改了里面一个颜色……）：完全不动。
- 没改过但不能重建的也不动，只按新规则重新签名：里面有原子被别处按 ID 引用（点击效果、条件、实例的覆盖）、或某个原子上的点击跳转在新组合里找不到唯一的去处、或新组合和现在一样。

重新组合和换风格是同一步撤销：选风格本来就是一步；切深浅色、改配方等主题修改本来不进撤销，但有组合件因此重建时会和这次修改合成一步。撤销整份文档的一步（换风格）时，画布上量过的尺寸全部作废重量，因为同一个盒子 ID 现在是另一种组合。切换编辑器语言时，部分常用词会被翻译，这不算改动：之前没改过的组合件按翻译后的内容重新签名。打开文件时 `lib/project.ts` 只保留形状正确的标记；导出代码、提示词和 AI 读的清单都不输出它。

### 拆分也按风格组合

`splitIntoAtoms(groups, itemId, lang, widths, look)` 把文档当前的 `KitLook` 交给拆分函数，拆出的树按风格画这个组件的样子组合（用和组合件一样的特征判断，不写风格名）：应用栏在标题居中的风格里拆成两侧等宽、标题居中（iOS 44 高、返回箭头带“返回”二字、按钮用强调色），大标题风格拆成按钮行加下面的大标题；列表在 iOS 的分组风格里拆成灰底圆角卡片上的行（分隔线从文字处开始、行尾有箭头），微信里是通栏单元格，桌面软件是细线分隔的紧凑行；对话框在 iOS 和微信里拆成窄的居中卡片、底部左右平分的按钮。不传 `look` 时是 Material，和以前一样。

## 让组合组件可以拆分

在 `parts/defs/splits.ts` 的 `SPLITS` 里按组件 ID 加一个函数，参数是组件当前的属性，返回同样外观的原子树：

```ts
"stat-card": (p) => vbox({ surface: "panel", width: px(p), hugWidth: false, padX: 16, padY: 16, gap: 4 }, [
  text(p.s("title"), "label", { color: "muted" }),
  text(p.s("value"), "headline"),
]),
```

registry 把它挂到组件定义的 `atoms` 上，属性面板就会出现“拆分为原子组件”。拆分（`splitIntoAtoms`）在原位置、原图层顺序换成这棵树：最外层盒子沿用组件的 ID、名字、测量宽度、点击跳转和填充色、文字色、圆角、外观，所在的自动布局也不变（`inFlow` 和它在布局里的要求：`flowSize`、`flowFill`、`alignSelf`、`flowAbsolute`、`flowMin`、`flowMax`、`flowSpan`）。按位置的点击跳转（`actions`）落到现在显示那个位置的原子上：列表的行、标签页、栏上的图标按钮；变量（`bind`）落到显示那个属性的原子上，比如搜索的 `value`、`placeholder` 落到里面的输入框。树的结构说得清的写在 `SPLITS` 旁边的 `SPLIT_TAPS` 里（每个位置对应树里的哪个原子、每个属性对应哪个原子的哪个属性）；没写的，位置找说同样文字或显示同样图标的唯一一个按钮，变量找显示同样文字的唯一一个原子；找不到的不保留。测试检查每棵树只有原子、属性都合法，并且保留组件显示的文字（按下后才出现的文字、只显示第一条的轮播除外），每个位置都有原子接住（拆出的树没显示的除外）。拆出的树要和组件一样大（差几像素以内）、同样的文字、图标和选中状态：应用栏 64 高、在屏幕自己的表面上（滚动后才是栏的表面），卡片的图片贴到边，搜索视图的每行 56 高、有阴影；在画廊 `splits=1` 里并排对照。独立站在屏幕上的栏（`role` 是 `top`、`bottom`、`floatingBottom` 的组件：应用栏、导航栏、结算栏等）拆开后，最外层盒子带上对应的 `pin`，仍然固定在原来那条边上；放在自动布局里的不加。

原子要给出不随属性变的估计尺寸（`guess`），组合件落下时才排得准：没有文字的开关、复选框、单选按钮，各尺寸的头像，标签和角标都有。

## 退役一个组件

把数据和行为留在自己里面、产品接不上后端的整块组件（一个列表自己增删、一个表单自己校验）退役，不删除；被更好的组件取代的旧组件（`resizable` 由分栏视图取代）也一样。现在退役的 12 个见[组件清单](组件清单.md)“退役的组件”。

1. 在 `parts/defs/retired.ts` 的 `RETIRED` 里写一句 `use`：改用哪些组合件和原子、数据放哪、点击调用什么；`with` 列出替代它的组合件和组件的 slug，面板里按旧名字搜时列出它们。registry 把它挂到定义的 `retired` 上。
2. 它要能拆：`SPLITS` 里没有的，原子树写在同一个文件的 `RETIRED_SPLITS`，槽位落在哪个原子写在 `RETIRED_TAPS`。拆出的树要和组件一样大、同样的文字（`e2e/retire.e2e.ts` 在画布上逐个量）。
3. 是列表的，在 `lib/retire.ts` 的 `ROWS` 里写怎样把它的行读成数据（字段名、每行的单元格，以及行上显示、但要从单元格算出来的东西，如头像缩写）。拆分时各行如果是同样的原子、同样的样子和点击，只有文字不同，就留一行做模板、按新建的数据集合重复；否则行保持为原子。展开后必须和不按数据重复的拆法逐个原子相同（`lib/retire.test.ts`）。
   不拆成原子、而是转成别的组件的（如 `resizable` 转为分栏视图），在 `RETIRED` 里写 `convert`（那个操作的名字）和 `why`（退役的原因），把操作登记在 `lib/core/ops/layout.ts` 的 `CONVERTS`：`split_retired` 和提示框就用它转换。
4. 模板里的用法改成 `parts/templates/atoms.ts` 的 `atomsOf(slug, props, extra)`：四种语言各拆一次再合成一棵树，组件的点击落在显示它的原子上，外观不变。
5. 运行 `bun run gen:agent`（AI 清单把它移到“Retired”表）、`bun run gen:rn`、`bun run gen:miniapp`。

退役的组件仍然在 `PARTS` 里：画布、预览、打开文件、拆分和导出都照旧认识它，旧文档不变。面板、AI 的 `list_parts` 和清单、`add_part`、`add_tree` 读的是 `OFFERED_PARTS`（不含退役的），加入退役组件会被拒绝并说明改用什么。拆分只在有人要求时发生：编辑器的提示框和属性面板、AI 和 MCP 的 `split_retired`、`split_into_atoms`，都是一步撤销；没有用迁移，因为旧组件照样能画，打开时改写文档反而会让作者没法撤销、也会让格式版本白白升高。

## 加一个组件

1. 在 `parts/defs/` 对应的文件里加一份 `PartDef`。能用 M3E 组件拼出来的，就只写定义。
2. M3E 组件拼不出来的（自己画的格子、动画、手势），在 `parts/widgets/` 写组件，并登记到 `modules.ts` 和 `sources.ts`。它能保存的只有表现状态和界面草稿（见下文“组件的状态和出口”）：领域结果从属性进来；用户输入的值、按下的事件从声明过的出口出去；演示一个领域结果（已领取、已发送、随机奖品）时声明 `demo`，只在原型里演。
3. 运行 `bun run gen:agent`，让 AI 也知道这个组件。
4. 如果它承担了某个来源的组件，更新 `docs/组件盘点.md`。

## 组件的状态和出口

### 三种状态

| 状态 | 例子 | 能不能放在组件里 |
| --- | --- | --- |
| 表现状态：只决定此刻画成什么样 | 动画进度、转盘转到哪、按下的波纹、逐字出现 | 能 |
| 界面状态：这台设备上界面走到了哪 | 选中的标签、展开收起、没提交的输入、排序偏好 | 能，但要有契约：初值从属性来，变化交出去，外部改了属性就跟着变 |
| 领域状态：产品里“真的是这样”的事 | 余额、库存、是否已领取、抽中什么、胜负、冷却、支付结果 | 不能。从属性进来；组件只发请求，结果由对面给出 |

判断依据是谁有权确认这件事成立（见[边界与契约](边界与契约.md)“三种状态”），不是有没有存下来。评分的编辑值、选座的草稿、签名是界面状态；“已领取”“已支付”不是。

### 受控值和草稿

- **受控值直接读属性。** 输入类组件的值来自属性（`value`、`checked`、`selected`……），属性变了就显示新值；用户改了就把新值交出去，不在组件里另存一份不跟随属性的副本。`useState(prop)` 只在挂载时读一次属性，绑定的数据变了也不跟着变，不能当受控值用。
- **输入用 `useValue`。** `parts/widgets/seed.ts` 的 `useValue(属性, host)`：有人接值时（预览、绑定的变量、表单字段：渲染方给了 `onValueChange` 或预览的 `input`）是受控的，显示的就是属性，改动只交出去，对面不接受（属性没变）时显示的也是没变的值；没人接值时（画廊、导出里什么都没绑定）属性只是初值，组件留一份草稿，属性变了就从新值重新开始。
- **`useSeeded` 只用于草稿的外部重置。** 它只在属性本身变化时同步，属性不变时不纠正组件里的值，所以不能代替受控值：对面拒绝了，组件里的假成功也不会消失。
- **草稿要讲清五件事。** 初值（属性）、当前值（组件里）、提交（事件，带上值）、取消或清空（组件里）、外部重置（属性变了就从新值重新开始）。数字键盘是例子：按键是草稿，每按一次交出当前值，确认时发出 `submit` 事件带上值，绑定的变量被改掉时草稿从新值重来。数据表格的搜索、排序、页码，日程的月份和日子，裁剪框也是草稿：从属性开始，每次改动发出事件（`search`、`sort`、`page`、`month`、`day`、`crop`），属性变了重新开始。
- **选中的行用稳定的键。** 组件里记着“哪几行勾上了、哪几张卡片选中了、演示里哪几行已读或删掉了”时，按行说的内容和同内容里的第几个（`keysOf`）记，不按行号记（`usePicked`）：数据重排后选中的还是那一行，那一行没了就自动去掉。两行文字相同也不会互相顶替（可排序列表）。
- **结果从属性进来，表现可以等。** 要看结果的组件分三段：发出意图（点击、事件）→ 等待（显示“处理中”）→ 结果从属性进来后落定，并发出“表现结束”的事件（抽奖的 `settled`、对话框的 `settled`）。表现上的随机可以（摇晃、闪烁），结果上的随机不行：`Math.random` 只能出现在演示的分支里（自动检查）。抽奖按下后等的是按下之后的回答：按下时已有的旧结果会马上播放，除非 `pending` 说新的在路上（按下的动作里把 `result` 设成 -1 或把 `pending` 设成真）；落定后可以再按，同一个奖连抽两次也会再转。
- **合计、价格、剩余时间来自数据。** 不从显示的文字里抠数字相加（选座的总价是 `total`，占比条的占比是数据里的一列，收支方向是数据里的一列）；倒计时按对面时钟上的截止时刻显示：`endsAt`（毫秒）加 `clockSkew`（对面的时钟比设备快多少毫秒），没给截止时刻时只把时长当文字画出来，不自己倒数，进出屏幕不会重新开始。

### 演示只在原型里

有些组件为了让原型能点，会自己演一个领域结果：优惠券点了就显示“已领取”，数字键盘确认后显示“已发送”，抽奖组件自己随机抽一个奖。这叫**演示**，规则是：

- 定义里用 `demo: { what, takenOverBy }` 声明：演的是什么，哪些属性接管它（`coupon` 的 `claimed`、`number-pad` 的 `sent`、抽奖的 `result`）。
- 只在**显式的原型模式**里演。组件默认是产品模式：没有渲染方说“演”，它就只显示属性给的状态、只发出请求。编辑器的预览和原型导出才打开演示；完整产品（monorepo）从不演示。
- 一旦接上真东西就停：`takenOverBy` 里的属性被绑定（变量或表达式），或者组件的动作里调用了接口、提交了表单（`lib/partContract.ts` 的 `demoTakenOver`）。所以接口拒绝领取时，预览里的优惠券也不会显示“已领取”。
- 产品里没接上的演示组件只会发出请求、等待结果，导出报告把它列为“依赖原型演示的组件”（`demo`）。

### 渲染方交给组件的东西

部件是一棵纯数据的树，画的时候由渲染方（画布、预览、导出的代码）决定模式、给出受控值和回调。自带组件从 `parts/widgets/host.ts` 拿这些：

```tsx
export function Coupon({ claimed: given = false, demo, onValueChange, onEvent, ...p }: { claimed?: boolean } & HostProps & Look) {
  const host = useHost({ demo, onValueChange, onEvent }); // 属性和预览给的 context 都能到这里
  const [claimedHere, setClaimedHere] = useState(false);   // 演示用的本地状态
  const claimed = given || (host.demo && claimedHere);     // 产品里只认属性
  …
  <Button data-tap="action" onClick={host.demo ? () => setClaimedHere(true) : undefined}>…</Button>
}
```

| 字段 | 意思 | 谁给 |
| --- | --- | --- |
| `demo` | 可以运行演示 | 预览按 `demoRuns(item, "prototype")` 给；原型导出在没被接管的演示组件上打印 `demo`；完整产品不给 |
| `input(value)` / `onValueChange` | 交出用户输入的值 | 预览写进字段、绑定的变量和表单；导出的 Web 写进绑定的变量 |
| `emit(name, payload)` / `onEvent` | 发出一个命名事件 | 预览运行 `Item.actions["on:<名字>"]` |
| `wired(slot)` / `wired` | 组件自己的控件（声明为 `own` 的槽位）上有没有接东西 | 预览按 `slotAction` 判断；导出的 Web 在接了动作的 `own` 槽位上打印 `wired={["like"]}` |

`useHost` 还给出 `controlled`（有人接值）和 `own(slot, run)`：组件自己的控件（红心、收藏、关闭、删除、表格行）按下时先做自己的事（演示、草稿），只有槽位上接了东西才算按到这个槽位，没接时按下不会变成“按了整个组件”，红心不会顺带打开商品页。

声明了 `input`、`events` 或 `demo` 的自带组件，签名里都要有 `demo, onValueChange, onEvent`（自动检查），需要 `own` 的再加 `wired`。

### 定义里的声明

| 字段 | 说明 | 例子 |
| --- | --- | --- |
| `input: { prop, kind, options? }` | 用户输入的值放在哪个属性、是哪种值：`text`、`number`、`bool`、`choice`、`choices`、`files`、`date`、`vec2`。预览、表单、绑定、导出都按它读写输入，不再按组件 ID 列名单（`lib/interact.ts` 的 `INPUT_PROP` 由它生成）。`choice` 存的是第几项，`options` 说从哪个属性里选（列表的行，或逗号分隔的文字；不写是 `items`），文字变量和表单字段里存的是选中项的文字（`lib/partContract.ts` 的 `optionsOf`）。值是列表的（标签、排好的行）在预览里按行存，在文字变量里一行一项 | `rating`：`{ prop: "value", kind: "number" }`；`color-palette`：`{ prop: "selected", kind: "choice", options: "colors" }`；`tag-input`：`{ prop: "items", kind: "choices" }`；`joystick`：`{ prop: "value", kind: "vec2" }`（`"x,y"`，-1 到 1） |
| `events: [{ name, label, labels, payload }]` | 组件发出的命名事件和它带的东西。动作存在 `Item.actions["on:<名字>"]`，表达式里读 `event.<字段>` | `number-pad` 的 `submit`（`event.value`）；抽奖的 `settled`（`event.index`、`event.label`） |
| `families: [{ prefix, label, labels }]` | 槽位族：一个动作回答所有 `<前缀>:N` 的槽位，存在 `Item.actions["<前缀>:*"]`，表达式里读 `slot.index`（第几个）和 `slot.key`。某个槽位自己有动作时用它自己的。改行（增删、排序）时槽位族的动作不动 | 列表行、按钮组、菜单、宫格的 `tab:*` |
| `demo: { what, takenOverBy }` | 见上文“演示只在原型里” | `coupon`、`number-pad`、六个抽奖组件 |
| `overlay: true` | 打开时浮在屏幕上，开关弹层的效果能作用于它 | 对话框、底部动作条、菜单 |
| `nav: true` | 目的地栏：点了哪一项，各屏幕上同样项目的栏一起记住 | `navigation-bar`、`navigation-rail`、`tabs` |
| 槽位的 `own: true` | 组件自己的控件：没接动作时按下不算按了整个组件（见上文 `own`） | 商品卡片的 `like`、动态的 `like` 和 `save`、文件列表的 `remove:*`、横幅和公告条的 `close`、数据表格的 `row:*`、签名板的 `clear` |

这些键在严格校验时只接受组件声明过的（`lib/core/ops/validate.ts`）；`set_action` 的 `slot` 可以是槽位、槽位族或事件；`describe_part`、`describe_node`、`list_parts` 把声明告诉 AI 和 MCP；属性面板“原型”标签页的格子条里，槽位后面是槽位族和事件（没有槽位的组件先是“整个组件”）。

**导出时**：预览已经运行事件和槽位族；Web、手机应用、小程序还不打印它们（统一解释器 `lib/actions` 接入后再打印），导出报告按“组件事件”（`event`）列出每一个，不悄悄丢掉。Web 把声明了输入的自带组件接到它绑定的变量上（`value` 加 `onValueChange`）。

### 字段状态

每个输入都有同一套字段状态，在部件定义上用 `field` 声明（`parts/fieldState.ts`）：

| 状态 | 属性 | 怎么显示 |
| --- | --- | --- |
| 禁用 | `disabled` | M3E 控件自己变灰、不可操作；自带组件由字段框架（`FieldFrame`）用 `<fieldset disabled>` 关掉里面的按钮和输入，按 M3 降到 38% |
| 只读 | `readOnly` | 显示值、可以聚焦，但改不了：M3E 控件用原生的 `readOnly`；滑块改成只显示给定的值；自带组件由字段框架挡住点按、输入、粘贴和拖放 |
| 必填 | `required` | 控件自己的 `required`（读屏会说“必填”），有标签的在标签后加一个只给眼睛看的星号；既没有原生必填也没有标签的自带组件，旁边加一个星号 |
| 加载中 | `loading` | 旁边一个加载圈和 `aria-busy`；按钮的加载圈在 M3E `Button` 里（`loading` 属性），同时不能再按 |
| 错误 | `error` + `errorText` | `aria-invalid` 和错误色；错误信息只在 `error` 打开时显示在控件下面（文本框、下拉选择显示在自己的说明行里） |
| 说明文字 | `helperText` | M3 的辅助文字：控件下面一行说明它是做什么的；出错时由错误信息顶替。文本框、下拉选择、字段、文件上传沿用原来的 `supporting`、`supporting`、`description`、`hint` |

- **声明。** `field: FIELD` 是整套，按钮、图标按钮、悬浮按钮用 `BUTTON_FIELD`（禁用和加载中），纸片、切换按钮、切换按钮组只声明禁用；属性名和包里不同的旧组件按状态写出它的属性（`field` 的错误信息一直叫 `error`：`{ errorText: "error", … }`）。定义里没写的状态属性由 registry 补上，标签、类型和日中韩名字都一样。声明了 `input` 的组件必须声明 `field`（自动）。
- **画法。** 部件的树用 `fieldValues(p)` 读状态，用 `fieldFrame(v, 控件, 选项)` 包上字段框架：选项说明控件自己能显示哪些（`holds`、`showsError`、`marksRequired`、`showsMessage`），框架只补它显示不了的。没有任何状态要框架显示时不包，所以旧文档、旧导出都不变；错误本身不会让框架出现或消失，表单打印出的代码因此是同一个控件，错误来去只改属性。
- **表单接线。** 表单的校验按声明设状态（`formStateProps`）：字段出错时打开 `error` 并写入 `errorText`（设计里已经有一行文字读 `form.errors.<字段>` 的，不再重复给控件，见 `lib/bindings/view.ts` 的 `messagesShown`）；接口契约里必填的字段设 `required`；提交中提交按钮 `disabled` 和 `loading`。预览、Web、手机应用、小程序四处都按这一个函数接，不按组件 ID 列名单。校验以接口契约为准：作者在组件上打开的 `required` 只做标记，不另加校验。
- **面板和工具。** 属性面板把状态放在单独的“字段状态”一节；给 AI 和 MCP 的属性 JSON Schema 里每个状态都注明是字段状态，`describe_part` 的声明里有 `fieldStates`，部件参考把整套写成 “field states”。
- **三端。** Web 打印部件的树，状态原样打印；手机应用和小程序套件里原生实现的输入（输入框、多行输入、文本框、开关、复选框、单选、单选组、滑块、选择、日期选择、输入组、文件上传、评分、按钮、图标按钮）接受同名属性：只读不可改、必填在标签后加星号、加载中显示加载圈、说明文字和错误信息显示在下面；悬浮按钮的禁用和加载、纸片和分段按钮的禁用、仅图标控件的 `ariaLabel` 也一样。时间选择在两个套件里接受这些属性但只画错误信息和加载圈之外的部分；画成原子树或占位的组件照旧报告差异。

### 表格

表格属性（`kind: "table"`）是 `{ columns, rows, spec? }`：`columns` 是表头，`rows` 是单元格，`spec` 是作者给的列结构，每列一项 `{ key, type?, width?, align?, format? }`（`parts/tables.ts`）。

- **按键读，不按位置读。** 每个以表格为数据的组件读哪些列，写在 `parts/tableColumns.ts`（键和类型，按默认表格的列序；图表的系列、看板的泳道、热力图的日期是数据自己的列，写成空的或只写前面固定的列），registry 把它交给属性定义的 `columns`。作者（或工具）给表格写了 `spec` 时，读出的表格按组件声明的键排好列（`lineUp`），组件因此按键读单元格；没有 `spec` 的表格不变。新代码用 `rowsByKey` 按键取单元格。没有声明也没有 `spec` 的，键由表头生成（“Due date” → `dueDate`）。面板在其他组件的表格下面列出数据里的列名，方便绑定。`table` 组件按列结构画：宽度、对齐（数字、金额、百分比默认靠后）、按类型写值（数字的小数位、金额的币种代码、百分比、日期、是/否）；没有列结构的表格画出来和以前一样。面板上 `table` 组件的数据下面有“列结构”逐列编辑（属性定义的 `structure: true`）。
- **绑定数据。** 表格属性可以绑定表达式：记录列表（接口列表 `data.orders.items`，或文档的数据集合 `collections.<名字>`，每行一个记录）按列的键排成行，列表的列表按位置，`{columns, rows}` 原样；最多 200 行；表头和列结构保留设计的。数据集合在表达式里是 `collections.<名字>`。预览按它显示；Web 产品、手机应用和小程序对绑定的表格仍显示设计的行，导出报告按“绑定”（`binding`）列出。
- **行跟着走。** 在面板上改表格的文字时，内容相同的行被认作原来那一行：按行挂的点击（`tab:N`）和选中项（`selectKey`）跟着它移动，删掉的行带走它的点击（`tableRowsPatch`）。以表格为数据又有选中项的列表（排行榜、会话列表、文件列表、播放列表、占比条列表），面板上按行的第一格选择选中行。
- **校验。** 写入的表格不能有比列多的单元格；`spec` 的键是字母开头的标识符，类型、对齐、宽度（24–960）都要合法。
- **列表行。** 绑定到数据的列表行除了文字、图标、图片，也保留 `variant` 和 `width`（用它们表示行状态的组件因此能从数据得到状态），预览和两个套件的 `rowsOf` 一致。

## 无障碍

| 约定 | 说明 | 检查 |
| --- | --- | --- |
| 仅图标的控件有名字 | 只有图标的按钮、切换按钮、悬浮按钮、按钮组和切换按钮组的项目、栏上的图标按钮、列表行尾的按钮都要有可访问名称，用它表达的意思（“返回”“更多”），不是图标名。`parts/a11y.ts` 的 `iconMeaning` 按 `ICON_WORDS` 把常用图标译成意思（再经 `p.say` 走多语言，没列出的图标读成词语，如 “View list”）；单个控件的组件带 `ariaLabel` 属性，作者可以覆盖 | 自动 |
| 每个输入都有名字 | 输入框、多行输入、选择、单选组、滑块、评分、数量加减……都要有可访问名称：可见的标签和控件关联，或者 `ariaLabel` 属性（读屏名称）。声明了 `input` 或字段状态的组件必须有可见标签属性（`label`、`title`、`text`）或 `ariaLabel`；设了 `ariaLabel` 后画出的每个控件都要有名字。自带组件里的多个控件按组命名：字段框架（`FieldFrame`）给它 `role="group"` 和这个名字。列表行尾的开关、复选框、滑块用行的文字命名；滑块的标签文字就是它的名字；同一屏放两个也不重复 `id`（用 `p.scope` 生成） | 自动 |
| 声明了角色就有键盘行为 | 写了 `role="radiogroup"`、`tablist`、`listbox`、`menu`、`tree`、`grid` 的，整组只占 Tab 顺序里的一站（选中的一项，没有就第一项），方向键在项目间移动，Home/End 到两头；单选组和跟随焦点的标签页移动时就选中。自带组件用 `parts/widgets/roving.ts` 的 `rove()`。`role="slider"` 要能用键盘到达并操作。做不到就不要声明这个角色：树形列表只画行和层级，所以是 `role="list"` 加 `aria-level`，不是 `tree` | 自动（一站和可到达），方向键的行为由 `rove` 的单元测试保证 |
| 读屏文字走多语言 | 组件自己说的读屏文字（“减少”“复制”“加载中”“评分”）用 `components/m3e/say.ts` 的 `useSay()`，部件定义里用 `p.say()`（`parts/labels.ts` 的 `COMMON_TEXT`），中、日、韩都要有；作者能用属性改 | 自动（`say.test.ts`、`parts/zh.test.ts`） |
| 只能用鼠标的操作有替代 | 拖动排序、左滑、下拉刷新、裁剪这类手势，要有键盘或按钮可以做到同一件事，隐藏的按钮不能还在 Tab 顺序里 | 评审 |

`parts/a11y.test.ts` 在每个组件画出的标记上检查前三条：一个组件违反就失败。它读的是静态标记，所以 Base UI 这类在挂载后才设好 Tab 顺序的基础组件，只检查“不超过一站”。手机应用和小程序里，`ariaLabel` 落到原生的 `accessibilityLabel`/`ariaLabel`；仅图标按钮的默认名字在两个套件里仍是图标名（套件没有词表），作者设了 `ariaLabel` 就用它。

**加之前先看有没有重复。** 能用现有组件加属性表达的，就加属性，不要新建。能用原子在盒子里拼出来的，写成组合件（见下文），不要再做一个整块的组件；整块的组合组件最好同时写好拆分用的原子树。

## 文档核心

文档只在一个地方改变：`lib/core` 的文档核心。编辑器的面板和画布、应用内的 AI、MCP 服务器都通过它读写同一份文档，所以三者看到的、能撤销的、能校验的都是同一套。它是纯 TypeScript，不引用 React 和 DOM，在浏览器和 Node 里都能运行（`lib/core/headless.test.ts` 在 Node 里只用操作搭出三屏应用、存成项目文件再打开、生成代码并导出项目）。

```text
lib/core/
  state.ts      CoreState：文档（画布上的屏幕和组件）、正在编辑的组件定义、会话（选中、测量尺寸）
  store.ts      DocStore：事务、撤销重做、变化事件、整份文档的打开、组件定义的编辑、切换语言
  op.ts         Op、OpCtx、OpError、Measurer、参数的 JSON Schema 和校验、风格规则
  ops/*.ts      各类操作：document、screens、nodes、layout、components、data（含变量和交互）、api（接口，见 docs/接口.md）、mocks（模拟库，见 docs/模拟库.md）、bindings（数据绑定，见 docs/数据绑定.md）
  ops/validate.ts  PropDef 和各字段的严格校验
  query.ts      outline、nodeTree、find、describeNode
  persist.ts    保存位置的适配器接口，和旧版的 localStorage 实现 localPersist
  projectFile.ts 项目文件的文本：适合版本管理的排版、图片放进文件、读回（见 docs/项目文件.md）
  react.ts      useStore：React 组件读 store 的 hook
```

### 状态

`CoreState` 有三部分：

| 部分 | 说明 |
| --- | --- |
| `doc` | 画布上显示的文档：和保存的 `Doc` 字段相同，主题总是存在。正在编辑组件定义时，`groups`、`frames` 是编辑定义用的那块屏幕 |
| `editing` | 正在编辑的组件定义：文档自己的屏幕和画布模式在这里等着，关闭定义时放回去 |
| `session` | 不保存的：选中的组件（`selection`，最后一个是面板显示的）、选中的屏幕（`frameId`）、测量出的尺寸（`widths`：`id` 宽、`id:h` 高、`id:base` 基线） |

`savedDoc(state)` 给出保存的文档：编辑定义时也是文档自己的屏幕，加上定义当前的样子；字段顺序和以前写进 `m3e:doc` 的完全一样。

文档自带的风格（`Doc.styles`，`lib/styles/custom.ts`）也是文档的一部分：读进来时（`loadInto`）先清理，主题按它们解析；每个操作按这份文档的风格上下文读（`styleContext(doc.styles)`，`lib/styles/book.ts`），操作内部更深处没拿到上下文的代码由同步的 `withDocStyles` 兜底，所以没有编辑器时（MCP、测试）读到的也是这份文档的风格。`set_custom_styles` 替换它们：正在用的风格被改时按新的样子穿上（字体、图标、形状、动效跟着变，没人改过的组合件重新组合），编辑器把连续编辑同一个风格合并成一步；`apply_style` 带上 `styles` 时在同一步里先换风格列表再套用。编辑器的 store 在每次变化时用 `setDocStyles` 把它们放进可读范围。

文档自带的图标（`Doc.icons`，`lib/docIcons.ts`）：编号 → SVG 标记，在任何接受图标名的地方写 `svg:<编号>`（图标原子的 `name`、按钮和列表行的 `icon`、导航栏的各个标签），和 Material Symbols 的名字并列。编号是用短横线连起来的小写词（`leaf`、`coffee-cup`，最长 40 个字符）。每个图标都经过矢量原子的清理（`parts/svg.ts` 的 `sanitizeSvg`，再由 `cleanToMarkup` 写出），文档不管从哪里进来（`loadInto`、`openProject`）都会再清理一次，不合格的丢掉，最多 200 个。`set_icon` 加入或替换一个（同一编号再写一次，用到它的地方都跟着变），`remove_icon` 删掉一个（会删掉作者的东西，要确认），结果里列出还在用它的组件；严格校验时，组件的图标属性写了文档里没有的 `svg:` 名字会被拒绝，并列出现有的。画的方式：`components/m3e/icon.tsx` 把 `svg:<编号>` 映射到 Iconify 的 `m3e-doc` 集合；编辑器的 store 在每次变化时、渲染页在拿到文档时用 `src/editor/docIcons.ts` 的 `setDocIcons` 把新的或改过的图标注册进去（`parts/icons.ts` 让用到它的组件重画，从不联网取它们），导出的项目由 `src/doc-icons.ts` 在启动时注册。编辑器面板里显示图标的地方（`components/Icon.tsx`）和图标选择器的“本文档”一栏也这样画。没有这个字段的旧文档不变。

文档的模拟库（`Doc.mocks`，`lib/mocks`，见 [模拟库](模拟库.md)）：接口在设计时由谁回答：种子和语言、每个模型字段的生成提示和条数、手工固定的记录、命名场景（新用户、大量数据、网络错误、慢网、未登录……）、文件库（图片、PDF、音频、视频）、实时脚本和登录方式。读进来时（`loadInto`、`openProject`）经过 `cleanMocks`；`lib/core/ops/mocks.ts` 的操作（`fill_mocks` 一步填好全部、`set_mock_model`、`add_mock_scenario`、`add_mock_file`……）检查它们指向的模型、字段、接口、通道都存在。预览为每次打开建一个模拟传输层（`createMockTransport`），预览的运行时经 `useMockTransport()` 调接口。没有这个字段的旧文档不变。

文档的接口（`Doc.api`，`lib/api`，见 [接口](接口.md)）：数据模型是 JSON Schema 2020-12，接口是 OpenAPI 3.1 的操作，实时通道是 AsyncAPI 3.0，加上鉴权和各环境的服务器地址，能原样导出 `openapi.yaml`、`asyncapi.yaml` 和模型的 TypeScript 类型，也能导入别人的规范。读进来时（`loadInto`、`openProject`）经过 `cleanApi`：形状不对的丢掉，大小有上限，键保持原来的顺序；`apiProblems` 列出引用、路径参数、重复的 operationId 等问题。`lib/core/ops/api.ts` 的操作（`add_model`、`add_endpoint`、`set_auth`、`add_channel`、`import_openapi`……）先把结果清理成读入时的样子，再拒绝任何会增加错误的改动，谁调用都一样；改的是文档字段，所以按整份文档留一步撤销。没有这个字段的旧文档不变。

屏幕和接口之间的绑定（`lib/bindings`，见 [数据绑定](数据绑定.md)）也在文档里：屏幕的数据源（`Frame.data`）、参数（`Frame.params`）和登录要求（`Frame.auth`），属性绑定的表达式（`Item.bind` 里以 `=` 开头的值），按数据重复（`Group.repeat.data`），表单（`Group.form`、`Item.field`），有加载中、空、出错、无权限设计的区域（`Group.states`，状态设计在 `Group.pane` 上），调用接口的效果。`lib/core/ops/bindings.ts` 的操作（`add_data_source`、`bind_expression`、`set_region`、`make_form`、`wire_screen`……）检查表达式能否解析、读的数据源和参数是否存在；数据源和参数改的是屏幕，其余改的是组件组，各一步撤销。读入时 `lib/bindings/clean.ts` 清理形状；没有绑定的旧文档不变。

### 操作

每个操作是一个 `Op`：

```ts
export const setTitle = op<{ title: string }>({
  name: "set_title",                         // 工具名，snake_case
  summary: "Sets the app's name.",           // 给模型看的一句话
  args: S.obj({ title: S.str() }, ["title"]), // 参数的 JSON Schema
  label: () => "Title",                      // 撤销步骤的名字
  run: (s, a, ctx) => ({ state: withDoc(s, { title: a.title }), history: "none" }),
});
```

- `run(state, args, ctx)` 是纯函数：读状态，返回新状态（`result` 报告新 id、数量等），不改传入的对象。`ctx` 给出测量尺寸（`ctx.widths`，来自 store 的 `Measurer`：编辑器用画布量出的尺寸，没有画布时用组件自己的估计 `guessMeasurer`）、语言、新 id（`ctx.newId`）、调用方（`origin`）和是否严格校验（`strict`）。
- 做不到时抛 `OpError`：`code` 是 `bad_args`、`not_found`、`locked`、`refused`、`invalid_value`、`nothing_to_do`、`busy` 之一，`message` 是给人和模型看的英文说明，说清楚哪里不对、可以取什么值（`button has no prop "colour". Its props are: …`）。`nothing_to_do` 表示已经是要求的样子，不算错误，也不留撤销步骤。
- AI 和 MCP 调用时（`strict`）先按 `args` 的 Schema 校验参数，再由操作按 `PropDef` 校验属性（种类、选项、范围）、颜色角色、外观（`cleanLook`）、跳转目标、变量和条件是否存在。编辑器自己的面板只写它显示的东西，不做这些校验，行为和以前一样。
- 文档被风格的规则约束时（`isStrict`），每个操作之后都按 `conformItem` 去掉风格决定的东西（圆角、风格以外的外观），谁调用都一样；AI 调用时直接写风格决定的属性会被拒绝并说明原因。
- 调用方可以给新东西指定 id（`id`、`groupId`）；不给时用 `ctx.newId`。store 给了 id 来源（`counterIds()`）时，操作里所有新 id（包括 lib 内部用 `uid` 生成的）都来自它，同样的操作序列得到完全相同的文档。
- AI 和 MCP 调用的操作在结束时把自动布局排好（和编辑器绘制后排的一样），所以没有编辑器打开时保存的也是排好的样子。

`OPS` 是给工具用的操作清单（`opByName` 按名字找）。编辑器自己的手势（松手落下 `drop_part`、粘贴、拖动图层）也是操作，但它们要的参数只有编辑器手里有，不在清单里。

### 事务、撤销和调用方

```ts
store.transact("Build the screen", "ai", (tx) => {
  const { id } = tx.run(ops.addScreen, { name: "Cart" });
  tx.run(ops.addKit, { slug: "search-bar", screen: id });
});
store.undo(); // 整个回合一步撤销
```

- `transact(label, origin, fn, { history })` 全有或全无：`fn` 抛错时状态回到开始时，历史不变。事务里再开事务是同一个事务的一部分；里面的事务出错只回滚它自己。`run(op, args, opts)` 是只有一个操作的事务。
- 撤销步骤（`history`）：`auto`（默认）在改动前留一步，改动超出画布内容（主题、变量、标题……）时留整份文档的一步；`step` 只留画布内容（屏幕、组件、定义、数据）；`whole` 留整份文档；`{ coalesce: key }` 和同一个 key 800ms 内的上一步合并；`none` 不留，属于上一步（拖动过程、量完尺寸后的排布）。操作自己可以要求 `whole`（换风格）或 `none`（不重组组合件的主题修改、标题、变量），后者只对编辑器自己（`user`、`system`）单独运行的操作生效：AI 和 MCP 做的事总能撤销。
- `checkpoint(label, { whole, coalesce })` 现在就留一步，给分几次完成的手势用（拖动开始时留一步，之后的移动用 `update` 不留）。
- `undo()`、`redo()` 返回步骤的名字；`view().history` 给出能否撤销重做和步骤名。最多 100 步。
- 整份文档的一步被撤销时（换风格、打开文件），测量的尺寸作废重量，正在编辑的定义结束，定义里等着重做的步骤一起丢掉（它们是那块已经不在的屏幕上的步骤）。
- `subscribe(fn)` 收到每次变化：`origin`（`user` 编辑器里的人、`ai` 应用内的 AI、`mcp` MCP 客户端、`system` 编辑器自己的排布和测量）、`label`、`changedIds`（改动的屏幕、组件组、组件、定义、数据集、变量，其余字段是 `doc:字段名`）、`kind`（`edit`、`undo`、`redo`、`replace`、`session`、`history`）、是否新留了一步（`step`）、是否整份文档（`whole`）。`useStore(store)` 用 `useSyncExternalStore` 读 `view()`。
- `replace(value)` 打开整份文档（文件、分享链接、AI 的草稿）：没有标明 `trusted` 时先经过 `openProject`，不是项目的一律拒绝；打开是一步撤销。`load(doc)` 是编辑器读回自己保存的副本，不留步骤。
- `openDefinition(id)` 把组件定义作为画布唯一的屏幕打开，文档自己的屏幕和历史在 store 里等着；定义有自己的历史；`closeDefinition()` 放回文档，定义改过时在文档历史里算一步，一次撤销全部收回。
- `translate(lang)`：切换编辑器语言时，画布和历史里每一步的种子文字、屏幕的默认名字一起翻译，组合件按翻译后的内容重新签名，不算改动。

### 编辑器怎样用它

编辑器（`src/Editor.tsx`）不再有自己的文档状态：屏幕、组件、主题、数据、变量、标题、选中和测量尺寸都从 `useStore` 读，改动都走操作（加组件和组合件、删除、移动、属性和外观、自动布局、屏幕、风格、可复用组件、数据集合、变量、拆分、整理、转为自动布局）。拖动过程这样的纯界面过程留在编辑器里，但也通过 `checkpoint` 和 `update` 写进 store，撤销粒度、合并方式和以前一样。保存位置由 `persist.ts` 的 `PersistAdapter` 决定（`read`、`write`、`writeBefore`、`assets`、`lock`）。编辑器默认用 `lib/projects` 的多项目存储（见下面“项目和保存”）；原来的 `localPersist`（`m3e:doc`、`m3e:doc:before`、图片放 IndexedDB、一个标签页编辑）仍然可以传给 `Editor` 的 `persist`，浏览器禁止 IndexedDB 时编辑器也会退回它。`read` 可以是异步的：读完之前启动遮罩一直盖着入门草图，不写任何东西，标签页也不可编辑，所以链接里的设计或按键不会落在马上要被替换的文档上。

`src/Editor.tsx` 只负责把各部分接起来和页面布局；每件事在 `src/editor/` 里各有一个 hook 或模块，彼此只通过参数（store、ref、回调）相连：

### 加一个操作

1. 放进对应的 `lib/core/ops/*.ts`，用 `op({ name, summary, args, label, run })`。逻辑尽量调用已有的 lib 函数，不要重写；需要尺寸用 `ctx.widths`，需要新 id 用 `ctx.newId` 或调用方给的 id。
2. 找不到东西抛 `not_found`，锁定的抛 `locked`，已经是要求的样子抛 `nothing_to_do`，参数不对抛 `invalid_value` 并说清楚可以取什么。`ctx.strict` 为真时校验调用方写进文档的每个值（`ops/validate.ts` 有现成的）。
3. 选中、选中的屏幕这种会话状态需要跟着变时，用 `withSession` 写进返回的状态。
4. 给 AI 和 MCP 用的，加进 `ops/index.ts` 的 `OPS`；在 `lib/core/ops.test.ts` 加正常路径、校验错误和风格规则的测试。
5. 编辑器里原来直接改状态的地方改成 `runOp(op, args, { history })`，`history` 和原来的撤销粒度一致。

### 工具注册表

- 每个工具（`Tool`）有名字、分组（`read`、`edit`、`style`、`data`、`generate`）、给模型看的说明、输入的 JSON Schema、结果的说明、是否只读（`readOnly`）、是否会删掉作者的东西（`destructive`）。
- `OPS` 里的每个操作自动成为一个工具，参数沿用操作的 Schema，浅的对象参数（`set_item` 的 `patch`、`set_theme` 的 `patch`、`set_layout` 的 `props`……）在 `schema.ts` 里展开字段。读取工具在 `read.ts`：大纲（可选屏幕和深度）、查找、单个组件、屏幕、选区、组件和组合件和模板的目录（`describe_part` 给出属性的 JSON Schema）、风格（含文档自己的风格和严格规则）、外观字段和预设、各图标家族的图标名、可复用组件、数据和变量、截图。`apply_ops` 把一批操作放在一个事务里，全有或全无，一步撤销。没有执行任意代码的工具。
- `createRegistry({ groups, extra, only, readOnly })` 选出一部分给客户端；`toolDefs` 是给模型的工具定义；`toolGuide` 由注册表写出简短的使用说明，智能体的系统提示词和 MCP 的说明都用它。
- `executeTool(store, name, args, { origin, history, onWrite, renderer, signal, gen })` 先按 Schema 校验参数，再运行；从不抛错，返回 `{ ok, result, images }` 或 `{ ok: false, error: { code, message, hint } }`，`code` 是操作的 `OpError` 代码或 `unknown_tool`、`unavailable`、`aborted`、`failed`、`declined`（作者拒绝了删除），`hint` 告诉模型下一步怎么做。`nothing_to_do` 算成功。`isDestructiveCall` 判断一次调用（包括批量里的）会不会删掉作者的东西。
- 报错要便宜：模型常猜错的名字按本意读（`aliases.ts`）：点击位置按属性名（应用栏的 `leading`/`trailing` 是 `icon`/`icon2`）、行的序号（`0`、`tab1`）或文字找；按钮的 `text` 是 `label`、图片的 `url` 是 `src`、图标的 `icon` 是 `name` 等，真名也给了时不动。只针对一个部件、要求 `id` 的操作（`set_props`、`split_into_atoms`……）收到只有一项的 `ids`，或 `itemId`、`nodeId`、`part`、`target` 时按 `id` 读；要求 `ids` 的收到一个 `id` 时按 `[id]` 读；`split_into_atoms` 什么都没给而正好选中一个部件时拆它。这一步在按 Schema 校验之前（`Tool.prepare`），单独调用和 `apply_ops` 里都一样；给新部件起名的 `id`（`add_part`）不受影响。枚举报错只列一次可选值并给出最接近的（`"large"` → `"lg"`）；很长的列表（全部操作名）只给最接近的那个。`apply_ops` 失败时其余操作照样检查一遍，再整批撤回，报错列出每个失败的操作（`ops[2] (set_item): …`），并说明其余操作没问题、只改这些再发。
- 图片（`lib/core/images.ts`）：智能体和 MCP（严格模式）给图片属性、列表行的图片、实例的图片覆盖、屏幕的 `backgroundImage` 只能用 `data:image/…`（PNG、JPEG、GIF、WebP、SVG）和项目自己的 `m3e-asset:` 图片；外链被拒，提示用 `generate_image`、`generate_svg` 或图标。参数里的 SVG data URL 一律先过 `sanitizeSvg` 再写回。编辑器自己的面板不受限。截图时加载不了的图片（外链失效、不是图片、不允许复制）画成灰块，截图结果里列出 `skipped` 和说明，不再整张失败。
- 组件定义：`describe_node` 能读组件定义里的部件（带 `component` 和可覆盖的键 `overrideKeys`）和组件本身；`list_components` 给出每个部件的文字和 `overrideKeys`（`部件 id/属性 = 定义里的值`，开关另列），可以直接拿去 `set_overrides`。`make_component` 之后部件在组件定义里、不在屏幕上：改它们用 `edit_component {id, ops}`（`lib/core/ops/definition.ts`），把 `set_props`、`set_item`、`add_part`、`add_tree`、`remove_nodes`、`set_layout`、`move_into` 等改部件的操作放在定义上运行，就像在画布上打开了这个定义（`definitionOpened`，嵌套规则照样检查），再像关闭定义那样放回去，所有实例跟着变；全有或全无，一步撤销，也能放进 `apply_ops`。参数先按定义读别名；里面有删除时算破坏性调用。对屏幕上找不到、其实在某个组件定义里的部件调用 `set_props` 等，报错会说它在哪个组件里、该怎样用 `edit_component`。
- 没有画布量尺寸时（Node、MCP 的文件后端），改动后按估计尺寸再排一次布局，所以新加进布局的组件不会停在容器的角上。`add_part` 没给 `at` 时，应用栏、导航栏、标签栏、固定在边上的盒子落到自己的边（叠在已有的栏后面），FAB 落到右下角、底部栏之上。
- `Renderer` 是截图的接口：`screenshot(屏幕或组件的 id, { scale, onSkipped })` 给出 PNG data URL，没画出来的图片地址交给 `onSkipped`。编辑器的实现（`useScreenshots.ts`）和导出屏幕图片一样在屏幕外按 1:1 画；组件从它的屏幕里裁出来。截图只嵌入这块屏幕的文字真正用到的网页字体（`src/editor/shotFonts.ts`：按每段文字的字体列表、字重、字形和字符，对照页面样式表里的 `@font-face` 及其 `unicode-range`，只取用到的子集文件，每个文件一个会话取一次，通常来自浏览器缓存），所以文字和画布上一样宽，不会因为后备字体更宽而被截断；以前全部嵌入要 12–16 秒，现在一两秒。导出屏幕图片、项目缩略图和 MCP 文件模式的渲染页都走同一个模块，渲染页先等主题的字体加载好再测量和绘制。
- `icons.generated.ts` 是各图标家族离线能画的图标名，由 `bun scripts/gen-tool-icons.ts` 从打包的图标集生成，测试检查它是最新的。
- `ToolEnv.attachments` 是作者在这段对话里附的图片（`{ id: "ref1", dataUrl, w, h }`），读参考图的工具按 id 取；MCP 客户端可以直接传 `data:image/…` 地址。`ToolEnv.pixels` 换掉解码图片的办法（默认浏览器自己解码，Node 里读 PNG）。

### 生成和复刻用的工具

| 工具 | 分组 | 做什么 |
| --- | --- | --- |
| `add_tree` | edit | 一次放下一整棵树：盒子（表面、横排/竖排/网格、间距、内边距、对齐）里装原子和别的盒子，每个节点可以带 `id`、`name`、`props`、`grow`、`fill`、`textColor`、`corners`、`look`、`action`、`bind`、`showWhen`、`flowSize` 等。逐节点按组件的属性和字段校验，错误带节点路径（`tree.children[2].props.colour`）；只有带自动布局的容器能有 `children`；点击效果可以指向树里的其他节点。可以落在屏幕的某一点、放进一个盒子的布局、或找空位；最外层钉在边上的盒子落到那条边。一步撤销，也能放进 `apply_ops`；之后 `make_component {ids: [根]}` 存成可复用组件。文字没写 `fit` 时：横排里随文字宽度，拉伸的竖排里按宽度换行 |
| `add_custom_style` | style | 把一个自定义风格加进 `Doc.styles`（同键名替换；没写键名时按名字生成，所以同名再写一次就是修改），`wear` 时同一步穿上。一律经过 `validateCustomStyle`，结果列出校验改了什么、还有哪些颜色没通过可访问性检查（`lib/styles/access.ts`，风格照样可用） |
| `generate_style` | generate | 文本模型按描述和/或参考图（`reference: "ref1"`）写一个自定义风格：系统提示词列出格式、内置风格、字体、图标家族、配方目录和可读性要求，描述里有材质（纸张、皮革、霓虹、像素……）时要求写 4–10 条规则画出来：重复渐变的横线和格子、径向渐变的颗粒、虚线和双线描边、发光和压印阴影，屏幕背景也可以用渐变叠出纹理；校验出对比度、配方、规则等问题时把问题发回去改一次（继承的内置风格原有的问题不算）；仍然看不清的文字色、边线和主色文字按规则修好（写在 `loud` 里的也修）；再经 `add_custom_style` 加进文档并默认穿上。`refine: 键名` 加 `feedback` 按截图后的意见修改。应用内的智能体每回合最多调用 2 次（`ToolEnv.gen.styles`），第三次返回 `refused`，提示改用 `add_custom_style` 修改已写好的风格或结束回合 |
| `sample_colors` | read | 量一张图（附图、屏幕或组件的截图）：尺寸（附图还给出每 dp 几个像素）、主要颜色和占比、每个区域的底色/平均色/第二色、每个点的颜色。确定性的，按 16 级量化后合并相近色 |
| `compare_to_reference` | read | 把屏幕截图和参考图并排交回给模型（参考图在前），再按网格逐格比较底色，列出差得最多的格子（屏幕上的 dp 位置、两边的颜色）和总体相似度 0–100 |
| `generate_svg` | generate | 画矢量图形；`kind: icon` 是单色、随文字色的图标。带 `icon: "编号"` 时存成文档自己的图标 `svg:<编号>`，可以用在导航栏、按钮、列表行这些只接受图标名的地方：`replace` 指向图标原子时给它换上新名字，给了位置时在那里放一个图标原子，都没给时只存下来，结果里有 `icon` |
| `set_icon`、`remove_icon` | generate 工具集 | 存下（或替换）、删掉一个文档自己的图标，SVG 由调用方给出（文本模型写的、MCP 客户端带来的），清理规则和矢量原子一样 |
| `generate_image` | generate | 画图片；`background: true` 和 `screen` 时作为整个屏幕的背景（屏幕的场景组件，已有场景就换它的图） |

复刻截图的流程写在系统提示词里：先读结构和尺寸（截图一般每 dp 2–3 像素），用 `sample_colors` 量颜色而不是猜，必要时 `generate_style` 从图里做风格，然后一块一块（或整屏一次）`add_tree`，装饰和插图用 `generate_svg` / `generate_image`，最后 `compare_to_reference` 对照、列出差别并修改，最多三轮。

**深色模式开关**：`add_var {type: "bool", drives: "dark"}` 让这个布尔变量就是应用的深色模式（一份文档最多一个，`update_var {drives: null}` 取消）。开关的 `checked` 绑定它，或点击效果里 `toggleVar` / `setVar` 它。预览开始时它等于预览当前的模式，改它就切换深浅色，预览栏自己的深浅色按钮也改它；导出的项目里 `src/runtime.tsx` 用 `useColorMode()` 让它和颜色模式同步。没有这个字段的旧文档不变。

### 智能体的一个回合

- 计划（先说一两句要做什么）→ 用工具做（尽量用 `apply_ops` 批量）→ 截图看改过的屏幕 → 批评 → 修。默认最多 30 次模型调用、每回合最多 2 次绘图、最多 2 次 `generate_style`（`refine` 也算一次）。模型没看改过的屏幕就结束时，回合把改过的屏幕（最多两个）截图给它看一次。
- 预算（`lib/agent/budget.ts`，`runTurn` 的 `limits` 可改，由应用执行，不靠模型自觉）：每次模型调用的输出上限（各服务商都有默认上限，OpenAI Responses 和 Claude 是 32000；请求要得更多时压到 `stepOutputTokens`）；整轮总 token 200 万（每次模型调用都算，工具自己发起的子任务，比如 `generate_style` 写风格、用代码画 SVG，也从这里扣，不再各拿全额）；整轮最多 150 次工具调用（跨步骤和自查，超出的调用不执行，模型收到“没有执行”的结果）；附图 24 MB；单个工具回答 8 MB（超出时图片换成一行说明）、整轮工具回答 64 MB；整轮 15 分钟。流式请求超过 180 秒一个字节都没收到（含等响应头，保活也算收到）按 408 断开，还没显示内容时照常重试，已经显示过就不重放。到了任何一项上限，回合以 `limit` 结束并说明是哪一项（`LimitReached`），已做的改动和到步数上限时一样保留。作者按停止不算上限。
- 一个回合是一步撤销：每个工具调用都以 `history: "none"` 运行，第一次改动落下后用 `checkpoint(label, { from })` 从改动前的状态留一步。编辑器在回合进行中不锁画布，作者可以穿插自己的编辑；`lib/agent/ledger.ts` 从回合开始听 store，把回合自己的改动（来源 `ai`，后面紧跟的布局整理等 `system` 改动算它的）按片段记成补丁，和作者（或 MCP 客户端）的改动分开。作者在回合中间改过东西时，一步撤销不能正好收回这个回合，回合就不给“一步”，面板的撤销改用下面停止时的办法：只收回回合自己的改动，保留作者的。
- 删除前先问（`lib/agent/guard.ts`）：一次调用会删掉作者的大量内容（清空画布、删屏幕、累计删掉 10 个以上组件、删可复用组件或有数据的集合；选中的部分不算），或者拿走名字看不出的东西（`lib/tools/removals.ts`：数据集合少了行或字段、行被整批换掉、变量、变量模式连同其中的值、组件属性，替换作者的自定义风格或文档图标、模拟库的固定记录被删或整批换掉）时，先在当前文档的一份草稿副本上试跑每个写入的调用，算出会删什么（生成工具不重复调用模型，按参数判断：`generate_style {refine}` 改写已有风格、`generate_svg {icon}` 重画已有图标；新写的风格不会按模型挑的键名覆盖已有风格，而是另起 `-2` 这样的键名），回合暂停，对话面板里弹出“允许 / 不要”。比较的基准是“作者现在的工作”：当前文档去掉本回合自己的改动（ledger 的 `baseline`），所以回合自己做的东西随便改，作者在回合期间新加的也受保护。
  - 行和固定记录按内容比，不按条数：有自己 id（集合里叫 `id` 的字段、记录的 `id`）的按 id 认，没有的按内容摘要认，一半以上的格子没变算编辑过的同一条；少了、或者条数不变但大半被换成别的，才算拿走。改一两个字段、调换顺序不会弹窗。
  - 授权绑定到具体目标：每个屏幕、组件、行、字段、模式、风格、图标……都有稳定的键（`TakenKey`）。“允许”只覆盖当时展示的那些键，之后的调用要拿走别的东西会再问；等待回答期间文档变了（作者又加了东西），回答只算数到展示过的范围，这次调用重新计算，拿得更多就再问。
  - 请求明确要删时（`plainlyAsksToRemove`：四种语言的“删除、清空……”；同时说“重做、重新设计、作り直し、다시”的，或说“不要删除、别删、don't delete、削除しないで、삭제하지 마、保留”的都不算明确），只免问请求里点了名的东西（屏幕、组件、集合等的名称或 id，拉丁字母按整词），不是整个回合都不问。
  - 审查本身出错（试跑或比较抛了异常）时，这次调用不执行，模型收到原因；不会当作“什么也没拿走”。
  - 不要：这次调用不执行，模型收到 `declined` 和“保留内容，先问作者”的提示。停止回合等于不要。`runTurn` 的 `confirm` 回答这件事；没有它（无界面）时一律不要，评测用 `--destructive allow|decline` 选。系统提示词把“含糊又要删大量内容时先问一句再结束回合”放在规则第一条并给了例子。
- 停止：中止正在流的请求和正在运行的工具，对话回到回合之前（下一次请求不带被停止的那一轮）。回合自己的改动按片段从后往前撤回（`TurnLedger.revert`）：作者之后没碰过的回到原样；作者之后改过的保留作者的样子；回合新加的东西如果作者的内容在用（放进了它的容器、站在它的屏幕上、按 id 引用了它）也保留。历史同时改写（`DocStore.rebaseHistory`）：回合自己的步骤去掉，作者期间留下的步骤里去掉回合的改动，所以撤销、重做都不会带回被停止的结果。面板如实说明：全部撤回（作者期间有编辑时说明“你的编辑保留”）、部分撤回（列出保留的东西和原因）、没能撤回，或期间打开了另一个文档所以没有撤回。服务商出错、拒绝或回复过长时，已做的改动保留为一步，可以撤销或重试，错误用 `aiErrorText` 说成人话。
- 常用组件速查：`lib/tools/atoms.ts` 从注册表写出 24 个最常用的组件（box、text、icon、image、svg、button、icon-button、input、textarea、switch、checkbox、radio、slider、chip、avatar、badge、progress、separator、app-bar、navigation-bar、tabs、item、card、fab）的属性（按类型分组，枚举列出可选值、默认值在前，数字带取值范围如 `width 40–1600`，列表带行数如 `items (3–5 rows)`）和点击位置，放在系统提示词末尾（约 5.4 KB、1.3k token，随系统提示词一起缓存），并写明这些组件不必再查。模型不用每回合先 `describe_part` 查这几个原子；其他组件仍然用 `describe_part`。
- 上下文：系统提示词在整段对话里不变（服务商可以缓存）；每次请求前附上紧凑的大纲（太长时减少深度）、选中的组件或屏幕、写字用的语言，以及风格是否严格：文档严格遵守风格时告诉模型风格的规则和外观里哪些字段会留下，不严格时告诉它全部外观字段都可以用。选择框、下拉菜单、日期选择器在画布上是展开画的，提示词让模型不要为了展开的菜单挪动组件（自动布局现在按收起的尺寸排，展开的部分悬在后面的组件上，见“自动布局”）。
- 对话只追加，模型写的东西（加密或签名的推理、调用、文字）从不改动；作者撤销了上一回合时，下一回合开头告诉模型。唯一的例外是图片：对话里超过 6 张图片时，除最后 3 张外都换成一行文字（`prunePictures`，只动用户消息和工具结果里的图片部分），一次放掉几张，所以大多数请求的开头和上一个请求相同，缓存还能命中；放掉的就不再发送。
- 附图：对话面板和 Cmd/Ctrl+K 提示栏都能粘贴、拖入或选择图片（最多 4 张，缩到长边 2048 以内）。图片随这次请求发给模型，消息里写明 `ref1 (宽×高 px)`；整段对话的附图都按 id 交给工具。
- 工具集：所有工具的定义每次请求都要发（全部约 58 KB），所以分成几组（`lib/agent/toolsets.ts`）：`build`（读取和搭建，总在）、`layout`、`screens`、`components`、`style`、`data`、`api`（接口：模型、接口、鉴权、实时通道、导入规范）、`mocks`（模拟库：生成提示、条数、固定记录、场景、模拟文件、实时脚本、模拟登录，读取记录和试调接口）、`generate`、`reference`。一段对话开始时只给 `build`（约 25 KB）和请求里的说法要的组。说法按四种语言逐组列在 `CUES` 里：`yes` 是表示要这组的短语（英文按整词），`no` 是先从请求里去掉的相似说法（“Codex-style 的输入框”“按当前风格”不要风格组，标签的图标不要绘图组，“画布”“画面”不是画，“검색”里的“색”不是颜色，“navigation drawer”不是跳转），宁可漏掉：漏掉的组模型用一次 `load_tools` 补上，多给的组每次请求都要多发。`sets.test.ts` 用四种语言的真实说法逐条检查，`bun scripts/toolset-bytes.ts` 打印十个典型请求带的工具字节数（收紧后平均约 27 KB，以前约 35 KB）。附了图再加 `reference`、`style`、`generate`；模型需要别的组时调用 `load_tools`，从下一次请求起加上。组只增不减：下一回合没用到新组时发出的工具和上一回合完全一样，缓存不断；中途加载一组只让一次请求没有缓存。系统提示词按组列出全部工具名，不随加载变化；任何操作不加载也能放进 `apply_ops` 里调用。
- 对话随项目保存：消息（推理原样）、面板上的回合（不含截图）、加载过的工具集和附图存进项目数据库的 `kv`（键 `agent:conversation:<项目 id>`），刷新或重新打开项目后接着用；“新对话”清空它。
- 按需加载：AI 标签页（`AgentPanel`）随标签页第一次打开时加载；智能体、服务商层和工具注册表在第一次发送请求（或起草整个应用）时才加载，编辑器启动时不带它们。
- 面板显示计划、每个工具（用 `lib/i18n/agentTools.ts` 的四语名称，原名在悬停提示里）和结果、删除前的询问（等待时是“允许 / 不要”卡片，之后一行写明允许了还是保留了内容）、模型看过的截图、改动摘要（屏幕和组件的增删改、移动、文档字段）、token（含缓存和推理）和用时，回合结束后可以保留、撤销或重试。Cmd/Ctrl+K 打开提示栏，针对选中的东西提要求。
- 设置：服务商、模型、推理强度（低、中、高）；默认文本模型 `gpt-6.1-sol`，图片 `gpt-image-2.6-sunburst`。密钥默认只在当前标签页的会话里保留（`sessionStorage`），浏览器长期存储（`localStorage` 的 `m3e:ai`）只存其余设置；打开“在此浏览器中记住密钥”才把密钥一起存下，关掉时删掉。以前已经存了密钥的设置照旧算记住。密钥不进文档、分享链接、对话记录和评测产物；服务商的报错复述了密钥时，显示前换成 `[key]`。
- 旧的单字段写入（屏幕说明、组件行为）和场景绘图的回答回来时先核对（`src/editor/aiLanding.ts`）：同一份文档、目标还在（中间删掉又用同一 id 新建的不算）、要替换的字段和请求时一样，才写进去；作者期间改过这一项时不覆盖，提示里给“改用 AI 的回答”；目标不在了就丢掉并说明；同一目标的新请求取代旧的。离开编辑器时文字请求和绘图都取消。整个应用的草稿和其他一次性操作（屏幕说明、组件行为、场景图）作为快捷操作留在面板里；草稿也改成流式请求，并按文档自己的严格程度处理风格。

### 产品层：接口、绑定、模拟库

作者不写代码，智能体（和 MCP 客户端）要能从“把这个列表连上接口”“加登录”“做一个记账小应用”一路做到能运行的产品。它知道的东西在三处：

- **工具说明**（`lib/tools/registry.ts` 的 `PRODUCT_GUIDE`，系统提示词和 MCP 的说明共用，约 1.5 KB）：按顺序做——契约（先 `get_api`；从屏幕推出模型和 REST 接口：列表 `GET /things` 游标分页、`GET /things/{thingId}`、`POST /things` 的请求体带校验规则、错误是 problem+json；登录是公开的 `POST /auth/login` 再 `set_auth`；非英文的画布给字段写 `title`，表单和标签显示它；给了规范就 `import_openapi`）→ 绑定（`wire_screen`；已经设计好的列表就地绑定：数据源、`set_repeat {data}`、`bind_expression`、去掉多余的示例行、`set_region`；点一行用 `set_action {to, params: {thingId: "item.id"}}`；表单用 `make_form`；按钮调用接口用 `call` 效果；`set_screen_auth`）→ 状态（按产品的话改四个状态的设计）→ 模拟库（`fill_mocks`、按要求加场景、实时脚本）→ 检查（带场景的截图、`try_mock`）。
- **大纲**（`lib/core/query.ts`，每回合附上）：文档有接口时多一行 `api: 3 models, 5 endpoints, sign-in login; mocks: 5 scenarios`；屏幕那行写出数据源、参数和登录要求（`[data products=listProducts; params productId; auth required]`）；组件那行写出按什么重复（`repeats data.products.items`）、区域（`region of products, showing empty`）、状态设计（`empty design`）、表单（`form of createProduct`）、输入框对应的字段（`field=email`）。
- **工具集**（`lib/agent/toolsets.ts`）：`api`、`bindings`、`mocks` 各有四种语言的说法；另有一组“把产品做成真的”的说法（wire it up、connect … to the API、real data、只给登录用户看；连上接口、绑定数据、需要登录；APIにつないで、ログインが必要；API에 연결、로그인 필요），一次加上 `api` 和 `bindings`；说到接口又说到屏幕、页面、表单、按钮时也加上 `bindings`。贴进来的规范文件（``` 代码块）不参与判断。只画一个登录页（“按当前风格加一个登录页”）、只加一个接口（“加一个列出商品的接口”）不会多带工具。`bun scripts/prompt-bytes.ts` 打印系统提示词的字节数和十一个产品请求带的工具集与字节数。

**截图带场景和状态**：`screenshot {id, scenario}` 按预览的方式画屏幕——模拟库在这个场景下回答（`""` 是正常回答），数据源加载、按数据重复、绑定的文字读进去、区域显示数据所处的状态；结果里的 `data` 说明每个数据源拿到了什么（状态、条数、错误）、每个区域显示哪个状态、发了哪些请求。`params` 是打开屏幕时的参数，没给时用参数的示例，再没有就用模拟库里第一条记录的 id。`screenshot {id, state: "empty", region?}` 让区域（或其中一个）显示某个状态的设计。核心是 `lib/bindings/headless.ts`（`previewScreen`、`regionsShowing`），和预览同一个引擎、视图和 `liveGroups`，纯 TypeScript；`Renderer.screenshot` 多了 `doc`/`widths`，画的是这份临时的文档（编辑器的 `useScreenshots`、MCP 连编辑器时的面板、文件模式的无头 Chromium 都支持）。没有截图能力时（MCP 文件模式没装 Playwright）带场景的调用仍然返回 `data`。

**`wire_screen` 的两处改进**：列表带 `detail` 而详情页还没有参数时，按列表的“取一条”接口（`/products/{productId}`）给详情页声明 `productId`，所以先连列表还是先连详情都行；详情和行里的标签用字段的 `title`（没有时才用字段名拆成的英文词）。

**点击带的参数自动声明**：`set_action`、`add_tree` 里打开某屏的点击带了那个屏幕还没声明的参数（`params: {productId: "item.id"}`），参数就声明到那个屏幕上；`add_data_source` 的参数写成 `params.名字` 时也一样。以前这在批量里会整批失败（评测里三次），模型得先 `set_screen_params` 再重发。

**区域的状态设计互不“装着”**：几个状态设计叠在区域的同一处，按实测尺寸时前面的设计在几何上包住后面的，`heldBy` 把后面的算成它的内容，导出的代码就把空状态写成 `state === "loading" && state === "empty"`（永远不显示，`apps/web` 类型检查报 TS2367）。现在被某个自动布局排着的部件只属于那个布局（`lib/tokens.ts` 的 `heldBy`），评测导出后的类型检查最先发现它。

**带场景截图的排版**：`previewScreen` 只把数据读进部件、去掉条件不成立的部件，排版和显示哪个状态页留给画布；空列表的行和它的重复留在内容页上。无头截图画另一版文档时按实测尺寸排两遍（`mcp/src/render.ts`），否则第一次排版前没量过的部件会画偏。

**删减**：`update_endpoint`、`update_mock_scenario`、`update_channel` 的参数和对应的 `add_*` 相同，只在 `add_*` 上写说明（操作仍然逐个校验），产品请求少发约 3 KB。

### 加一个工具

1. 会改文档的，先做成操作（见“加一个操作”），加进 `OPS` 就自动成为工具。模型需要多知道的一句话写进 `lib/tools/ops.ts` 的 `MORE`；对象参数的字段在 `schema.ts` 的 `DEEPER` 里展开；会删掉作者东西的加进 `DESTRUCTIVE_OPS`。
2. 只读的写在 `lib/tools/read.ts`（读图片的在 `reference.ts`），用 `tool({ name, group: "read", description, input, readOnly: true, destructive: false, run })`，加进 `READ_TOOLS`。找不到东西抛 `ToolFailure("not_found", 说明, 提示)`。
3. 要调用模型的写在 `lib/tools/generate.ts`，加进 `GENERATE_TOOLS`：用 `env.gen` 的设置和每回合的预算，把 `env.signal` 传下去让停止生效，往文档里放东西走操作，结束时调用 `afterWrite`。
4. 在 `lib/tools/tools.test.ts`（生成和复刻用的在 `generative.test.ts`）里加测试：在 Node 里用 `guessMeasurer` 跑通，以及出错时的代码和提示。智能体的行为在 `lib/agent/agent.test.ts`、`sets.test.ts` 里用 `scriptedAdapter` 测，界面在 `e2e/agent.e2e.ts` 里用 `page.route` 假装服务商。
5. 给它在 `lib/i18n/agentTools.ts` 写四语名称（测试检查每个工具都有），想好它属于哪个工具集（`lib/agent/toolsets.ts`，默认按分组）。

## 项目和保存

浏览器里可以有多个项目，存在 IndexedDB 的 `m3e-projects` 数据库（`lib/projects/db.ts`），每次改动是一个事务，文档和它引用的图片一起写进去或都不写：

| 存储 | 键 → 值 | 说明 |
| --- | --- | --- |
| `projects` | id → `ProjectMeta` | 项目列表显示的：名字、创建和修改时间、最近打开时间、屏幕数、风格、第一屏的缩略图、绑定的文件、放进回收站的时间 |
| `docs` | id → `{ json }` | 文档的 JSON，大图片换成 `m3e-asset:` 引用（`lib/assets.ts`） |
| `befores` | id → `{ json }` | AI 草稿或链接替换掉的设计，等作者保留或撤销 |
| `refs` | id、`id#before` → 引用列表 | 每份文档引用的图片，用来找出没人用的图片 |
| `assets` | `m3e-asset:…` → data URL | 图片，按内容命名，所有项目共用一份；没有任何文档引用时清掉 |
| `files` | id → `FileRecord` | 项目绑定的文件或文件夹（句柄、上次写出的大小、时间和哈希） |
| `kv` | 键 → 值 | 记账：旧版文档是否已经迁移；智能体的对话（`agent:conversation:<id>`，项目彻底删除时一起删掉） |

- **标签页开哪个项目**：地址里的 `?project=<id>`，没有就开最近用过的，一个都没有就新建一个；打开后地址里一定带上 id，刷新还是同一个项目。启动时路由在下载编辑器代码的同时读项目（`lib/projects/opening.ts`），组件的绘制代码按这个项目的文档预取。
- **一个项目一个编辑的标签页**：每个项目一把 Web Lock（`m3e:project:<id>`）。同一个项目的第二个标签页只读（对话框里可以去项目主页换一个项目），不同项目的两个标签页都能编辑。
- **迁移**：这个版本第一次启动时，旧版的 `m3e:doc` 原样（同一段 JSON）成为第一个项目，名字取文档标题；`m3e:doc:before` 成为它待确认的设计；旧的 `m3e-assets` 数据库里的图片复制过来。检查和迁移在一个事务里，两个标签页同时启动也只迁移一次。旧数据一样不删：退回旧版仍能打开；图片在新库里找不到时还会去旧库读（只读的后备，保留一个版本）。
- **修改时间**：只有人（或 AI、MCP）的改动才更新项目的修改时间；打开后编辑器自己的排版、第一次按新版写回，不算修改。
- **项目主页**（工具栏最左边的项目名、项目菜单、只读对话框、手机的设置面板都能进入）：搜索、按最近/名称/创建时间排序、新建、在本页或新标签页打开、重命名、创建副本、下载项目文件、删除。删除先放进回收站，8 秒内可以撤销，离开主页或撤销时间过去后彻底删除（连同它在 `kv` 里的 AI 对话，键由 `projects.ts` 的 `projectKvKeys` 列出）；其他标签页正在编辑的项目不能删除。列表的变化通过 BroadcastChannel 告诉其他标签页。
- **切换项目就是跳到它的地址**：编辑器里的一切（历史、选中）都为新项目重新开始；AI 对话是每个项目自己的，跟着项目回来。跳之前先把正在写的存完，并更新当前项目的缩略图。
- **保存到文件或文件夹**、重新连接、外部修改的检测、打开和拖入文件：见 [项目文件](项目文件.md)。

## 文档怎样打开

文件和分享链接统一走 `lib/project.ts` 的 `openProject`：拆开 `m3e-project` 信封，按版本运行 `MIGRATIONS`，再校验结构。以后改格式时，在 `MIGRATIONS` 里加一步。

- 其他格式、版本号更高的文件，以及含 `component` 以外 Kind 的文件，一律拒绝，画布不变。
- 组件定义不存在的（比如改过 ID），文件照常打开，这个组件显示 “Unknown part”。这是全新项目，不保留旧 ID 的转换。
- 屏幕的宽高在打开时（`lib/core/state.ts` 的 `loadInto` → `cappedFrames`）限制在 3840 以内、长屏的长度在 15360 以内，和 `add_screen`、`resize_screen` 允许的一样；没有超出的文档原样打开（同一个数组）。
- **外部图片**（`lib/outside.ts`、`lib/outsidePolicy.ts`、`src/editor/useOutsideImages.ts`、`components/OutsideBanner.tsx`）：别人做的文档里指向其他网站的地址（`http:`、`https:`、`//`）一显示，浏览器就会去取，那个网站就知道谁在什么时候打开了它。所以和邮件客户端一样，打开文件（新项目或替换画布）、打开分享链接时，文档里有这样的地址，就先不加载：图片属性、列表行的图片、视频和音频的地址画成空的占位，网页组件不加载，屏幕的描图不显示；画布上方的横幅说明原因，“加载外部图片”之后才加载，“暂不”只把横幅收起。选择记在项目的列表项里（`ProjectMeta.outside`：`blocked` / `allowed`），项目打开时在交给编辑器文档之前就设好（`ProjectsPersist`），所以第一次绘制也不会去取；创建副本时一起复制。`data:` 图片和项目自己的 `m3e-asset:` 图片不受影响；在这里新建的项目没有这个字段，和以前一样加载；导出的项目不读它。挡住的地方只有 `PartView` 和描图两处：截图、缩略图、导出屏幕图片都经过 `PartView`，所以同样不取。

```json
{ "format": "m3e-project", "version": 2, "document": {} }
```

写文件统一走 `lib/core/projectFile.ts`：键排序、两格缩进、一行一个节点，同一份文档总是写出相同的字节。格式的完整说明见 [项目文件](项目文件.md)。

## 自动布局

`parts/flow.ts` 是属性定义，`lib/flow.ts` 负责排布。组件的位置仍然存在文档里，所以预览、对齐线和图层不用另外处理；开了布局的容器每次改动后重写这些位置。做法对照 Figma 的自动布局。

- 谁属于哪个容器写在 `Group.inFlow`，所以内容超出容器时也不会掉出来。放在容器里的组件、布局刚打开时已在容器里的组件，都会自动归入。
- 顺序就是文档里的顺序，只有拖放能改变它。
- 还没量过尺寸的组件不参与排布，否则会按猜测的尺寸排错。
- 导出的代码把这些内容嵌套进容器，写成真实的 flex 和 grid，子项的要求写在包住它的一层 `div` 上（`flex-1`、`self-*`、`col-span-*`、`min-w-[…]`、`absolute`）。给编码代理的提示词也逐个写出这些要求和对应的类；绝对定位的子项不列在排布顺序里，而是写在“叠在容器上”一节，带上相对容器左上角的位置。

容器的属性：

| 属性 | 说明 |
| --- | --- |
| `layout` | `free`（关闭）、`row`、`column`、`grid` |
| `gap`、`gapY` | 间距；`gapY` 是换行后行与行、网格行与行之间的距离，不写就等于 `gap` |
| `padX`、`padY` | 左右、上下内边距 |
| `padTop`、`padRight`、`padBottom`、`padLeft` | 单独一边的内边距，写了才生效，没写的边用 `padX`、`padY` |
| `align` | 横穿排布方向的对齐：`start`、`center`、`end`、`stretch`、`baseline`（文字基线，只对横排和网格有意义） |
| `justify` | 沿排布方向的分布：`start`、`center`、`end`、`between`、`around`、`evenly` |
| `wrap`、`columns` | 横排换行；网格列数 |
| `hugWidth`、`hugHeight` | 宽、高随内容 |

子项写在 `Item` 上，旧文档里没有就按原来的规则：

| 字段 | 说明 |
| --- | --- |
| `flowSize` | `{ w, h }`，每个方向 `fixed`（自己的尺寸）、`hug`（随内容，只对开了布局的容器）、`fill`（占满布局给的空间）。不写时，沿排布方向看 `flowFill`，横穿方向看容器的 `align` 是不是 `stretch` |
| `flowFill` | 旧写法：沿排布方向占满剩余空间，等于该方向的 `fill` |
| `alignSelf` | 只对这一个子项改横穿方向的对齐 |
| `flowAbsolute` | 绝对定位：不参与排布，留在放下的位置，跟着容器移动；离开所在的布局后自动取消（拖出容器、直接拖进另一个布局、粘贴到别的屏幕后按位置归入别的布局） |
| `flowMin`、`flowMax` | `{ w, h }`，布局给它定尺寸（填充、随内容）时不小于、不大于这个值 |
| `flowSpan` | 在网格里跨几列 |

- **随内容的容器里填充：** 沿排布方向没有剩余空间可分，按自己的尺寸；横穿方向按其他子项撑出的尺寸拉伸，和 Figma 的“填充容器”一样。全部子项都填充时按各自尺寸。
- **基线：** 画布量出每个组件第一行文字的位置（取字形框高度的五分之四处），没有文字的组件按底边算，和浏览器的规则一致。
- **面板：** 设计面板的“布局”一节（`components/DesignPanel.tsx`，控件在 `components/FlowPanel.tsx`）：方向、换行，宽高各选固定、随内容、填充（随内容只对开了布局的容器，填充只对放在布局里的组件），不固定时的最小最大值，3×3 对齐格和间距、间距方式、拉伸和基线、内边距（左右/上下或分边），放在布局里的组件的自身对齐和网格跨列；“位置”一节里是脱离布局（绝对定位）。选中开了布局的容器时，画布上的内边距和间距也可以直接拖（`components/LayoutHandles.tsx`）。
- **展开画的选择框和菜单：** 从触发器左上角展开的部件（选择框、组合框、下拉菜单、右键菜单、菜单栏、导航菜单、搜索建议、级联菜单）由 `parts/registry.ts` 的 `viewOf` 包进 `Overhang`（`parts/contained.tsx`）：收起的部件不可见地占位，测量、自动布局、对齐和选中框都按它的尺寸；展开的部分从左上角悬在后面的组件上。日期选择器的日历在画布上同样悬在输入框下面，预览里画真正的选择器，点一下才展开。围着触发器展开的（提示、气泡卡片、悬浮卡片、分割按钮、提示条）仍按展开的框占位。

### 分栏视图

`split-view`（`parts/defs/containers.ts`，模型在 `lib/split.ts`）：两个栏左右并排或上下排列，同时可见，中间一条访客能拖的分隔条。邮件的列表和正文、文件树和编辑区、编辑区和下面的终端都用它。

- **两个栏是真正的盒子。** 每个栏是一个带纵向布局的 `box`，`Group.inFlow` 指向分栏视图，`Group.splitPane` 写明是第一栏还是第二栏；栏里放什么都行，再放一个分栏视图就得到三栏、四栏或网格。分栏视图只决定两个栏沿主轴各多长（`splitSizes`），`lib/flow.ts` 给栏定尺寸和位置后，栏自己的自动布局排里面的内容，所以拖分隔条时内容跟着重排。栏里超出栏的部分在画布和预览里都裁在栏内（`paneClips`），和导出的面板一样。
- **为什么只做两栏：** 一个分隔条就是一个数，能一一对应到输入、变量绑定和每个平台的分隔组件；多栏靠嵌套。
- **和标签页不是一回事：** `dock`、带状态的区域用 `Group.pane` 表示“只显示当前页”；分栏的 `splitPane` 是另一个字段，没有任何规则会因为一栏而藏起另一栏。打印器也分开处理（Web、RN、小程序各有一条分栏的分支，不走标签页的可见性规则）。
- **栏的完整性由文档核心保证：** 每个操作结束后 `withSplitPanes` 检查一遍，缺栏的分栏视图补一个空栏，指向分栏但不是栏的组件归还自由，指向不存在的分栏的栏变成普通盒子。栏不能单独删除、移动、复制、编组或包进别的布局（`refusePanes`，报错说明该改分栏视图或栏里的内容）；东西不能直接放进分栏视图本身，要放进某一栏。复制分栏视图时连同两栏和栏里的内容一起复制；删除分栏视图时和其他容器一样，栏和里面的内容留在原处，成为普通盒子。

属性：

| 属性 | 说明 |
| --- | --- |
| `orientation` | `horizontal`（左右）、`vertical`（上下） |
| `split` | 设计稿里第一栏的占比，0–100，按分隔条留下的空间算；画布上拖分隔条、面板、`set_split` 写它 |
| `minFirst`、`maxFirst`、`minSecond`、`maxSecond` | 每栏沿主轴的最小、最大尺寸（像素，0 表示不限）；限制互相矛盾时第一栏保住最小值 |
| `collapsible`、`collapsedSize`、`collapsed` | 哪一栏可以折叠（`none`、`first`、`second`）；折叠后留多少（0，或 56–80 的图标条）；开始时是否折叠。拖到最小值和折叠尺寸的中点以下也会折叠 |
| `divider`、`handle` | 细线（1 像素）或间隙（8 像素）；是否画握把 |
| `compact`、`breakpoint` | 自身宽度窄于断点（默认 600）时上下堆叠（`stack`），或保持不变（`keep`）。按组件自己的宽度判断，不按窗口；切换的是库的方向，所以拖动也按新的轴算 |
| `persist` | 是否记住访客拖出的比例（见下） |
| `width`、`height` | 尺寸 |

**比例的两种含义和持久化：**

- `split` 是设计，存在文档里。画布上的分隔条（`components/SplitHandles.tsx`）写它：可聚焦的 `role="separator"`，带名称（“第一栏与第二栏之间的分隔条”）、方向、`aria-valuenow`、范围；拖动吸附到整数百分比（Shift 5%，再按 Alt 10%）、50% 和最小最大值，双击回到一半，方向键每次 1%（Shift 5%），Home、End 到最小最大值，Enter 折叠可折叠的一栏。一次拖动、一次双击、一串方向键各是一步撤销。只有选中分栏视图或它里面的组件时才显示，嵌套的每一层各一条。
- 访客在预览或导出的应用里拖出的比例是访客自己的界面状态，不进文档：分栏视图声明为输入（`input: { prop: "split", resets: ["collapsed"] }`），值就是第一栏的占比；拖动时按动画帧更新，栏里的内容随之重排，松手时发 `resize` 事件（`event.split`、`event.collapsed`）。访客的值一出现，设计稿的“开始时折叠”就让位给它。每次打开屏幕都从设计稿的比例开始。
- `persist: true` 时在访客自己的设备上记住比例：Web 用 `localStorage`（键 `m3e-split:<组件 id>`，浏览器不让存时下次照样从设计开始）；小程序用 `Taro.setStorage`；手机应用的套件没有自己的持久存储，只在应用运行期间记住，导出时作为差异报告（`input`）。编辑器的预览从不记住：每次打开预览都是第一次访问（`PartHost.remember: false`）。
- 绑定数字变量时（`bind: { split: 变量 }`），拖动时按动画帧写入变量，变量被别处改了分隔条就跟过去；拖动自己写出的值回来时不会把分隔条拉回去。

**各端：** Web 打印成 `SplitView`（`parts/widgets/Split.tsx`，基于 react-resizable-panels 4.19.1，4.16 起修好了缩放下的拖动距离），两个栏各是一个 `ResizablePanel`，尺寸写成带单位的字符串（占比 `"30%"`，限制 `"240px"`；库把裸数字当像素）；分隔条就是库的分隔条（方向键、Home、End、Enter、双击复位）。预览的屏幕按比例缩放，拖动距离由库按缩放换算；屏幕设置了滑动跳转时，按在分隔条上的拖动不算滑动。手机应用和小程序打印成各自套件里的原生 `SplitView`（两个 `View` 加一条手指拖动的分隔条，读屏可以调节；窄屏默认上下堆叠）。

**操作（编辑器、AI、MCP 共用，参数有 JSON Schema）：** `add_part` 加分栏视图时同时建好两栏，返回 `panes.first`、`panes.second`；`add_tree` 里分栏视图的两个孩子就是两栏（必须是带布局的盒子，必须正好两个）；`set_split {id, split?, collapsed?}` 改设计稿的比例和折叠；其余属性用 `set_props`；`convert_to_split_view {id}` 把旧的 `resizable` 换成分栏视图。

**旧的 `resizable`：** 已退役（`retired`，`with: ["split-view"]`），定义和画法保留、不改。它只是演示组件，两个面板里只有一行字，压在上面的组件不会跟着分隔条走；旧文档照旧打开、外观不变，Web 导出逐字节不变。新设计用 `split-view`：属性面板的“转为分栏视图”（同 `convert_to_split_view`，一步撤销）把它换成同样大小、方向和比例的分栏视图，按每个组件的中心点把压在两个面板上的组件移进对应的栏，面板里改过的文字留成一行文字。不在打开文档时自动转换：那样会改写作者的文档而无法撤销，也会平白升高格式版本。它走退役组件的统一机制（见“退役一个组件”）：组件面板、`list_parts` 和 `public/agent.md` 的目录不再列出它（agent.md 的“Retired”表里有），`add_part`、`add_tree` 拒绝并指向 `split-view`，面板里搜“Resizable”列出分栏视图；它的 `convert` 是 `convert_to_split_view`，所以画布上方的提示框和 `split_retired` 把它转为分栏视图（和其余退役组件同一步），`split_into_atoms` 拒绝并指向转换。

### 整理、整理所选和转为自动布局

三个命令共用 `lib/structure.ts` 读出的结构：

1. **XY 切分：** 能用一条水平线把一组部件分开的地方，切成上下几段；每段再用竖线切成左右几列；每块再换方向切，直到只剩一个部件。哪条直线都分不开的（风车形摆放），按“中线落在同一行、左右并排”分行。
2. **网格：** 连续几行、每行同样个数的相似部件（同一个组件，或宽高相差不到两成）合成网格，几列同样个数的相似部件也一样。最后一行可以少几个。
3. **排列：** 一组里的间距取中位数，落到间距阶梯上（风格的 `gap` 和 `tight`，相差 15% 以内取阶梯值，否则取 4dp 网格），所有间距统一。对齐看这组部件本来最接近共用哪条线：竖排比较左边、中线、右边，横排比较上边、中线、下边和文字基线；已经对齐到像素的保持，否则横排默认居中、竖排默认靠左，除非另一条线明显更接近。一行里有一个空档比最窄的空档宽三倍以上（且至少 32），就在那里分成两组，两组各贴一端，像标题和右边的操作按钮。

- **整理**（`lib/tidy.ts` 的 `tidyFrame`）：栏、FAB、弹窗、侧边栏、场景图和锁定的部件照旧按规则摆放；其余部件按上面的结构一段一段排在页边距之间。单个部件保持原来靠哪边；同一列里较窄的部件多数靠哪边（左、中、右），没有正好对齐到页边距或中线的部件就跟着靠哪边，一列不混用对齐。一行有大空档就两端对齐；跨过大半宽度的一行均匀铺满（是否跨过大半宽度按原来的和排紧后的宽度一起判断，整理后再整理结论不变）；排成一行比内容宽度还宽的，拆成上下几段。网格跨过大半宽度就铺满内容宽度，横竖用同一个间距。有意叠在一起的部件当作一个整体：大半（六成以上）压在另一个上面的（容器上的部件、图片上的文字），或小部件压在大部件的角上（图标上的角标）；只是蹭到别的部件边缘的（压在输入框边框上的开关）当作摆歪了，分开排。放不下的段留在原处，不会被推出屏幕。整理会在自己的结果上再读一遍，直到不再移动，所以对整理过的屏幕再整理什么都不动（严格遵守风格时每次改动后都整理，不会出现第二次跳动）。
- **整理所选**（`lib/align.ts` 的 `tidyUpParts`，Ctrl+Alt+T）：把选中的部件按所在的行排成一行、一列或网格，横竖各用一个间距，左上角不动。只有每行个数相同（最后一行可以少）、每列是相似部件时才排成网格；不是网格的，每行各自排匀，行与行上下排开。间距落到间距阶梯上，但不超出所选部件原来的范围（最多多出落到阶梯上的几像素）；互相压住的部件保持原样，不会被排到别的部件上。整理过的再整理什么都不动。只选了一个部件或选中的是屏幕时，Ctrl+Alt+T 整理所在的屏幕。
- **转为自动布局**（`lib/flow.ts` 的 `suggestAutoLayout`，Shift+A）：把读出的结构变成嵌套的容器：段变成竖排，行变成横排（有大空档的行用两端分布，外层其他部件至少一样宽时填满外层的宽度，否则保持自己的宽度），网格变成网格（各列等宽后会比原来宽很多的，改成上下几行），都随内容。只选一个没开布局的容器时，给它自己打开布局，内边距取内容离边缘的距离（上下、左右各自相等时写 `padX`、`padY` 并去掉以前单独设的边，否则四边分别写），以前设的行间距、分布方式和换行也去掉。屏幕面板里的“整屏转为自动布局”对屏幕上除栏、FAB、弹窗、侧边栏和场景图以外的部件做同样的事。新容器现在是不带标签、填充和边框的 `container`，组件和属性写在 `LAYOUT_BOX` 一处。

### 对齐线

拖动和拉尺寸时（`lib/guides.ts`，画在 `components/SmartGuides.tsx`）：

- 边缘和中线吸附到同一屏幕上其他部件的边缘和中线，以及屏幕的边缘、页边距和中线，画出对齐的线。
- 和相邻部件之间的距离等于它们已有的间距，或正好在两个部件中间时吸附过去，用粉色标出每段相等的间距。
- 标出到上下左右最近部件（没有就到屏幕边缘）的距离。
- 选中部件后按住 Alt 指向另一个部件，显示两者之间的距离；指向空白处显示到屏幕边缘的距离。
- 距离数字是带白边的小标签，放在不压住其他部件内容的位置：线中间被挡住就沿线挪开，整条线都被挡住就放到旁边。
- 拖进开了自动布局的容器时，容器自己排位置：不再吸附、不标距离，而是在将要落下的位置画一条 2px 的强调色插入线（横排竖线、竖排横线，网格按行），和松手后的位置一致。
- 线宽始终是 1 个设备像素，标签不随缩放变大变小。拖动开始时算好所有候选线，移动时只查找，四十个屏幕的文档也不卡。按住 Ctrl（或 Cmd）不吸附；不在线上时仍落在 4dp 网格上。

## 交互

动作存在 `Item.action`（整个组件）和 `Item.actions`（按键：槽位 `tab:2`、槽位族 `tab:*`、事件 `on:submit`，见上文“定义里的声明”）。`Action` 除了跳转，还可以带 `effects`（显示、隐藏、切换、开关弹层、设变量、改属性、提示条，以及调用接口、重新加载数据、加载下一页、提交表单、退出登录）和 `when`/`else` 条件；条件、设变量的值、跳转给屏幕的参数（`ActionBody.params`）都可以是表达式（见 [数据绑定](数据绑定.md)）。每个效果、条件、触发方式、事件和槽位族、迟到的回答的规则写在 [交互规则](交互规则.md)：数据模型和唯一的解释器在 `lib/actions`；一致性表在每个宿主上各跑一遍，列出还没照规则做的地方。今天预览的判断和执行还在 `lib/interact.ts`，导出项目时由 `lib/printBehaviour.ts` 写成代码，第四批改为都调用 `lib/actions`。变量存在 `Doc.vars`，组件属性通过 `Item.bind` 绑定。带 `drives: "dark"` 的布尔变量就是应用的深色模式：设它、切换它（效果或绑定的开关）就切换深浅色，预览和导出的项目都一样（见“AI”里的“深色模式开关”）。

### 原型

原型沿用 `Item.action(s)`，只是多了几个字段（`lib/tokens.ts`，读写在 `lib/prototype.ts`）：

| 字段 | 说明 |
| --- | --- |
| `Action.trigger` | 不是点击触发时：`{ on: "hover" }` 指针移入，`{ on: "delay", ms }` 进入屏幕后多少毫秒 |
| `ActionBody.overlay` | 目标屏幕放在当前屏幕上面，而不是替换它；返回、点外面或 Esc 关闭 |
| `ActionBody.scrollTo` | 一个组件的 id：当前屏幕的内容滚到它可见（`to` 为 `none`） |
| `ActionBody.motion` | Figma 的动画：`kind`（instant、dissolve、move、push、slide）、`dir`（新屏幕移动的方向 left、right、up、down）、`easing`（out、in、inOut、linear、spring）、`ms`。有它时 `transition` 自动取最接近的旧过渡（`transitionOf`），只认旧过渡的地方（旧版本）照旧能播 |
| `Frame.flow` | 流程起点和它的名字：预览的屏幕菜单列出各个流程，没有选中屏幕时从第一个流程开始；导出的项目也从第一个流程开始 |

`set_action` 的参数里可以写这些字段，严格校验时检查触发和动画的形状、浮层的目标是屏幕、滚动到的组件存在；`set_flow_start` 设流程起点。文件读回时（`lib/project.ts`）形状不对的字段去掉，其余保留。预览（`components/Preview.tsx`）按触发运行：指针移入调用、屏幕出现后计时，浮层画在当前屏幕上面，动画按方向、缓动、时长播放，返回时倒放。

每种动画的姿态（新屏幕从哪里进来、旧屏幕去哪里、时长和缓动、弹簧）在 `lib/screenMotion.ts`：它没有任何 import，预览直接用，导出的项目复制一份用，所以两边播的是同一份动画。`lib/tokens.ts` 的 `Motion`、`Transition`、`SLIDE_SPEC` 和 `lib/prototype.ts` 的 `EASING_CURVE`、`DIR_OFFSET` 都从这里转出。

导出的项目里（`lib/printBehaviour.ts` 写代码，`lib/runtimeSource.ts` 写运行时）：

- **触发**：组件自己的交互是指针移入时写成 `<Pressable onHover={…}>`，延迟时写成 `<Pressable after={毫秒} onAfter={…}>`，都不再是点击；插槽里的交互仍是点击。计时从屏幕可以使用时开始（`App.tsx` 的 `Page` 通过 `ScreenContext` 告诉它），屏幕在离开或被浮层盖住时暂停，浮层关闭后重新计时，和预览一样。
- **浮层**：`openOverlay("屏幕", 过渡, 动画)` 把屏幕放在当前屏幕中间，下面是压暗的背景；`back()` 先关浮层，点背景或按 Esc 也关；去别的屏幕时浮层关闭。被盖住的屏幕 `inert`。
- **动画**：`go("屏幕", 过渡, { kind, dir, easing, ms })`，运行时记在历史里，返回时倒放；尺寸不同的屏幕之间仍是淡入淡出。`MotionConfig reducedMotion="user"` 让系统要求减少动态效果时位置直接到位。屏幕外层带 `data-move`（动画的种类），方便检查。
- **滚动到**：目标组件带 `data-part="名字"`，`scrollTo("名字")` 在正在使用的屏幕里找它（`[data-active]`），平滑滚到可见处，减少动态效果时直接跳过去；之后再去目标屏幕。
- **流程**：运行时的 `FLOWS` 列出各个流程起点，应用从第一个开始；地址里的 `?flow=名字` 从那个流程开始，`startFlow(名字)` 重新开始一个流程。
- 动画的种类、触发的毫秒数在打印前再用 `cleanMotion`、`cleanTrigger` 清一遍，过渡不是已知的就按 `slide`；屏幕、组件、变量、流程的名字都是转成字母数字的键，文字一律用 `str()` 写成字符串。
- 不用这些的文档，`App.tsx`、`runtime.tsx` 和以前一个字节都不差（`lib/exportPrototype.test.ts` 用几个夹具的摘要守着）。

### 变量

`lib/variables.ts` 是变量的集合、模式和绑定：

- **集合和模式**：`Doc.varCollections` 列出集合（`{ id, name, modes: [{ id, name }], dark? }`），变量的 `collection` 指向一个集合，没写或指向不存在的集合就在默认集合（`DEFAULT_COLLECTION`，只有一个模式，改过之后才写进文档）。变量的 `value` 是它在集合第一个模式下的值，其他模式的值在 `modes` 里（`valueIn`）。旧文档的变量没有集合，照常打开，样子不变；类型多了 `color`，值是颜色引用（角色或十六进制）。
- **哪个模式**：`modeFor` 依次看屏幕自己的选择（`Frame.varModes`）、文档的选择（`Doc.varModes`）、应用处于深色模式时集合的 `dark` 模式、集合的第一个模式。`varValues(doc, frame, dark)` 给出一块屏幕上每个变量的值。
- **绑定设计字段**：`Item.bind` 除了属性名，还可以是 `@fill`、`@text`、`@stroke`（颜色变量）和 `@opacity`、`@radius`、`@rotation`（数字变量）。`boundItem(item, values)` 把它们画成填充层、文字颜色、描边颜色、不透明度、四角圆角、旋转。画布的每块屏幕、预览的每块屏幕、截图和 PNG 导出都用 `components/boundValues.ts` 的 `BoundValues` 给出当时的值，`PartView` 画之前套用；属性的绑定仍只在预览里生效（`lib/interact.ts` 的 `liveItem`）。
- **预览**：`PreviewState.set` 记下点击或输入写过的变量，它们在每块屏幕上都是写进去的值；其余变量按那块屏幕的模式取值（`screenVars`），深色模式开关同样切换跟随深色模式的集合。
- **导出**：绑定的设计字段都写成读 CSS 变量：填充 `var(--m3e-v-名字, 值)`，文字颜色和描边同样（文字颜色还写进它读的 `--md-sys-color-on-surface` 两个角色），不透明度 `clamp(0, var(--m3e-v-名字, 值) / 100, 1)`，圆角和旋转同样夹在面板的范围里；括号里的值是这块屏幕在浅色时的值，变量还没定义时用它。名字是 `cssNameOf`，同名时加序号（`Behaviour.cssVarOf`）。这些字段读在 look 里的 `cssVar`（填充、文字、描边）和 `look.vars`（不透明度、旋转、圆角），只有导出时由 `boundItem` 写上，`cleanLook` 只认字母数字和连字符。
- **运行时**（`src/runtime.tsx`）：有多个模式的集合列在 `SCREEN_MODES`：每块屏幕浅色和深色时各显示哪个模式，导出时按 `modeFor` 算好；`MODE_VALUES` 是每个变量在各个模式下的值；`BOUND` 是绑定了设计字段的变量和它的 CSS 变量名。`App.tsx` 的每块屏幕（还有放弹层的舞台）用 `varStyle(屏幕)` 定义这些 CSS 变量；点击或输入写过的变量记在 `written` 里，在每块屏幕上都是写进去的值，其余按屏幕的模式取值，`useApp()` 在屏幕里给出的 `vars` 也是这样（和预览的 `screenVars` 一样）。深色模式由驱动深色模式的变量决定，没有这个变量时跟着应用的颜色模式。变量的初始值仍是文档模式下的值。
- **操作**：`add_var`、`update_var`（`collection`、按模式 id 或名字给的 `values`）、`add_var_collection`、`update_var_collection`（改名、给出模式列表、`dark`）、`remove_var_collection`、`set_var_mode`（文档或某块屏幕），`bind_prop` 的 `prop` 可以是 `@` 开头的字段。它们改动整份文档，一步撤销。

### 约束

没有自动布局的盒子里的组件可以设 `Item.constraints`（`{ h: left|right|stretch|center|scale, v: top|bottom|stretch|center|scale }`，`lib/constraints.ts`）。盒子改尺寸时（`set_item`/`set_props` 改了宽高、画布上拖尺寸手柄），设了约束的组件保持到边的距离、居中、跟着拉伸或按比例缩放；没设的仍固定在左上，和以前一样。`align_to_parent` 把一个组件对齐到装着它的这种盒子，没有就对齐到屏幕。

## 复用、数据和变体

- 可复用组件在 `Doc.components`，实例是带 `instanceOf` 的 `Group`（`lib/instances.ts`）。
- **变体**：`Doc.componentSets` 列出变体集（`{ id, name, props: [{ name, values }] }`），作为变体的组件带 `set` 和 `variant`（每个变体属性的取值），名字按取值写成 `属性=值, …`。`add_variant` 复制一个组件做新变体：零件和 id 不变，所以覆盖的键（`itemId/propKey`）在变体之间通用；`update_component_set` 改名、改属性和取值（`was` 改属性名，`renamed` 改取值名，变体跟着改）；`set_variant_values` 改一个变体的取值，两个变体不能取同一组值。
- **实例替换**：`swap_instance` 把实例换成别的组件（`swappedInstance`）：路径相同的覆盖保留，对不上的按零件类型和名字（`component|label`）找，找不到的去掉；属性值按 id、再按名字和类型保留；替身容器的尺寸换成新组件的。实例面板按变体属性选值时用 `variantMatching` 找最接近的变体。
- **组件属性**：组件的 `props`（`ComponentProp`：`text` 的目标是覆盖键，`bool` 的目标是组件里的组 id，`swap` 的目标是嵌套实例的组 id），实例在 `Group.properties` 里按属性 id 设值。展开时（`propertyEffects`）文字属性像覆盖一样写进零件，但手工覆盖优先；布尔属性为假时去掉目标组和它排着的组；替换属性把嵌套实例换成别的组件。操作是 `set_component_prop`、`remove_component_prop`、`set_instance_props`，`reset_overrides` 去掉实例的覆盖和属性值。
- 旧文档没有这些字段，照常打开；`lib/project.ts` 读回时清理它们的形状。
- 数据集合在 `Doc.collections`，容器用 `Group.repeat` 按行重复第一个子项（`lib/collections.ts`）。集合可以带 `model`，指向接口的一个数据模型（`Doc.api.models`），说明这些行是它的示例：模拟库把这些行（按字段的类型读成数字、布尔、列表）排在这个模型的记录最前面，其余按它的 Schema 生成；改名、删除模型时跟着改。
- `Group.repeat` 也可以是 `{ data: 表达式 }`：按接口返回的列表重复（`data.products.items`），每份副本的组件带运行时的 `Item.scope`（`item`、`index`）。画布画 `sample` 份（副本半透明）；`expandDoc` 把它原样留给预览，预览按加载到的数据展开（`lib/bindings/view.ts`），导出（下一阶段）写成 `map`。有 `Group.states` 的容器只把内容页（`pane` 0）的第一个子项当模板（`templateOf`）。
- 区域（`Group.states`）借用 Dock 的标签页机制：`lib/flow.ts` 的 `panesOf` 把状态当作标签页，`outOfPane` 只按布局（`inFlow`）把其他状态的设计和它们里面的东西拿掉——各状态的设计叠在同一个位置，按几何“包含”会把正在显示的设计也算进去。
- 这两者都通过 `lib/expand.ts` 的 `expandDoc` 展开成普通组件，画布、预览、提示词和代码都看展开后的结果。
- 同一屏幕的不同尺寸用 `Frame.variantOf` 关联（`lib/variants.ts`），每个尺寸的排版各自独立。

## 导出项目

`lib/exportProject.ts` 把文档变成能安装运行的项目，打成 zip：每个屏幕一个文件（`lib/codegen.ts`），加上按文档生成的 `src/runtime.tsx`（`lib/runtimeSource.ts`）。文档用到原型的触发、浮层、动画、滚动到时，`App.tsx` 和运行时多出这些部分，并从 `src/lib/screenMotion.ts` 取动画；用到流程时多出 `FLOWS`；有多模式的变量或绑定了设计字段时多出变量的表和 `varStyle`。什么都没用的文档写出的和以前一样。组件文件不列清单，从屏幕的 import 一路走下去，走到什么就复制什么，所以组件里新增的 import 不用另外登记；走不到文件就报错，不写出坏项目。放到别处的文件要加进 `lib/exportSources.ts` 的 glob。

点击、变量、条件怎样写成代码在 `lib/printBehaviour.ts`：组件定义不用改，只读 `props` 的 `tree` 会被按不同取值各画一次，不同的地方变成表达式。


## 已知限制

- **没开自动布局的容器：** 内容要完全落在容器里才算在内，压在边上的不跟着移动。旧的 `resizable` 拖动时上面的组件不会跟着变；要放内容的分栏用 `split-view`（见“分栏视图”）。
- **分栏视图：** 只做两栏，多栏靠嵌套；窄屏只有上下堆叠和保持不变两种，还没有“变成标签页”“只显示一栏”；手机应用记住比例只在运行期间。
- **屏幕本身不是自动布局：** 整屏要流式排布时，用屏幕面板里的“整屏转为自动布局”，或放一个全尺寸容器并打开布局，或者用“整理”。除自动布局的内容外，导出的代码仍按屏幕绝对定位，变体按窗口宽度切换，不是单一页面自适应。
- **预览里的尺寸：** 组件的测量值来自画布，预览里文字变长时，横排布局不会重新排。
- **基线是估算的：** 浏览器不直接给出文字基线，画布取第一行字形框的五分之四处，不同字体可能差一两个像素；可复用组件实例和数据重复的行没有基线，按底边对齐。
- **固定和随内容：** 普通组件的“随内容”只对开了自动布局的容器有效；文字等组件的宽度是一个数值，在布局里选“固定”就是保持这个数值。
- **转为自动布局：** 新容器用的是 `container`，还不是 `box` 原子组件；换成 `box` 时改 `lib/flow.ts` 的 `LAYOUT_BOX` 一处即可。读出的结构只看位置，不看语义，叠放的部件会当成一个整体放进布局里。
- **整理：** 只移动部件，不改尺寸（风格的宽度规则除外）；结构推断只看摆放的位置，摆得太乱时会按行来读。
- **复制的代码：** 只提示要复制哪些自带组件文件。“下载项目”会把屏幕用到的文件都带上。
- **导出项目：** 屏幕上设置的滑动切换不会导出；主题的 `emphasized` 不生效，编辑器里也一样；运行时才知道名字的图标仍然向 Iconify 请求。
- **可复用组件：** 实例的大小就是定义内容的大小，自动布局只放置它，不拉伸也不让它填充剩余空间，也没有尺寸手柄。列表行的文字和容器的属性不能覆盖。导出的代码是展开后的普通组件，不生成可复用的 React 组件。
- **数据重复：** 画布上只有第一行是真实组件，其余行是淡显的副本。
- **模板：** 面板缩略图是示意图，不是真实绘制。模板文字按插入时的语言写入，之后切换语言不跟着变（公共词表里的词除外）。
- **图层：** 只有顶层行可以重命名；文字组件在图层里都显示为“文字”。
- **原型：** 连线手柄只连到屏幕，返回和外链在原型标签页里设。有槽位的组件（列表行的图标等）在画布上连的是整个组件的点击。导出的项目里，延迟触发的计时跟着组件：组件被隐藏（条件不满足、被切换掉）时计时取消，再出现时重新开始，预览则只在屏幕出现时开始一次。预览的屏幕菜单可以选流程，导出的项目用地址里的 `?flow=` 或 `startFlow()`；预览里 Backspace 和左方向键返回（焦点在输入框、下拉、滑块、标签条这类自己处理这两个键的控件上时不算，输入法组合中的按键也不算），导出的项目没有。
- **变量：** 组件内部自己渲染、不在树里的颜色不受填充绑定影响。某个模式下变量的值类型不对（比如颜色变量的值不是颜色）时，那个字段在导出的项目里保持导出时这块屏幕的值。
- **变体：** 变体集没有 Figma 那样的总画布，每个变体单独打开编辑；组件属性按组件定义，同一变体集的各变体各有一份（新变体复制时带上）。
- **手机版编辑器：** 没有模板和组件标签，完整功能在桌面宽度上。
- **模态侧边栏：** 布局只占收起时的宽度，展开后盖在内容上。复制出去的代码（不是“下载项目”）要自己用 `onDismiss` 接上关闭。
- **场景图：** 是图片或循环 GIF，不会对操作做出反应；GIF 分辨率较低；热区要在表格里填百分比，不能在画布上拖；画风靠相同的文字描述保持，不能保证同一角色每次长得一样。分享链接带不了本地生成的图片。
- **没有实物的组件：** 动画、相机和地图只是占位外观；语音消息和视频通话没有真实音视频；图片裁剪不生成新图片；抽奖组件在原型里的演示概率均等、结果不保存，产品里等 `result` 给出结果；图表默认是示例数据。
- **出口：** 事件和槽位族目前只在预览里运行，三端导出报告列出它们但还不打印；把组件拆成原子时，事件和槽位族的动作不保留。只有一部分组件已经声明了输入、事件和演示（评分、数量加减、数字键盘、优惠券、抽奖、八个基础输入），其余自带组件按报告第 3 章在第三批逐个改。
- **平台外观：** iOS、Miuix 等平台的组件都按 M3E 外观绘制。登录和支付按钮不带品牌标志。
- **性能：** 40 个屏幕的文档拖动一帧约 30ms，能用，但达不到 60 帧。
- **盒子：** 表面角色改成 `none` 的空盒子在画布上看不见，只在选中时有框；可以在图层里找到。图层不按盒子嵌套显示。
- **组合件：** 落下时只按估计尺寸排一次，画布量出真实尺寸后再排，第一帧可能略有跳动。拖着走时不吸附对齐线。拆分时，拆出的树没有显示的位置，它的点击跳转不保留：通知栏的多条公告、剧情对话框的多句台词只拆出第一条，后面的公告和还没轮到显示的选项没有原子接住。变量绑定在没有原子单独显示的属性上（如标签页、导航栏选中第几项）时不保留。滚动时收起（`collapseOnScroll`）只对 FAB 有效，可拆的组件里没有 FAB。拆出的是 Material 的组合方式：风格重新排布组件的地方（如 iOS 应用栏的标题居中）不跟着拆，风格只按表面角色打扮拆出的盒子。叠在图片上的角标和头像在拆出的树里排在相邻的一行，所以略高。
- **退役的组件：** 只有各行拆出来完全一样（只有文字不同）的列表才变成数据集合，未读的通知、分组的联系人、混排的设置、不同状态的待办保持为原子行；行上显示的文字要是某个单元格原样的文字（或 `ROWS` 算出的列）才能变成 `{{字段}}`。拆开后购物车的合计、件数和待办的完成数是拆分时的文字，不再变化；登录表单的校验提示不拆出来。可复用组件定义里的退役组件不在画布的提示框里计数，打开定义（或 `edit_component`）后用 `split_retired` 拆。没拆的旧文档导出到 Web 时仍用组件自己的代码（手机应用和小程序画成原子树）。模板里原来的退役组件换成了它们在默认风格下拆出的原子树：风格包里专门写给这些组件的样式（游戏风格的背包格子和任务条 `[data-slot=inventory-cell]`、`[data-slot=task-bar]`，ChatGPT、Claude、Codex、Discord 等风格的消息输入栏 `[data-slot=chat-composer]`，微信等风格的设置分组标题）不再作用于模板，模板在这些风格里按原子各自的样式画；在默认风格里和以前一样。
- **图标：** 有些 Material 图标没有描边版（如 `arrow_upward`、`graphic_eq`），不带实心标记时画不出来；组合件里这类图标都用了 `iconFill`。

## 外观和效果

组件的外观写在 `Item` 上，不写进 `props`：`fill`（填充角色）、`textColor`（文字角色）、`corners`（四个圆角）和 `look`（效果）。`parts/appearance.ts` 把它们画到组件声明的 `appearance.target` 节点上，画布、预览、导出代码和提示词读的是同一棵树，所以看到的就是导出的。数据和 CSS 的换算都在 `lib/look.ts`。

| 效果 | 字段 | 怎样画 |
| --- | --- | --- |
| 填充叠层 | `fills`：纯色、线性、径向、角向，每层两个以上色标；`clearFill` 去掉组件自身的填充 | `background-image`，第一层在最上面 |
| 描边 | `stroke`：粗细、颜色、实线/虚线/点线、内侧/居中/外侧、四边分别设置 | 实线用 `box-shadow` 画，不占位置，跟着圆角走；虚线和点线用 `outline` |
| 阴影 | `shadows`：x、y、模糊、扩展、颜色、内阴影；空列表表示无阴影 | `box-shadow`，描边在最上面 |
| 高度 | `elevation`：0 到 4 | 风格的卡片造型决定每一级的样子（`--look-elev-N`），没有规定时用 M3 的高度 |
| 模糊和玻璃 | `blur`、`glass`、`glassSaturate` | `filter: blur()`、`backdrop-filter` |
| 混合、滤镜、变换 | `blend`、`opacity`、`filter`、`rotate`、`transform`、`clip` | `mix-blend-mode`、`filter`、`rotate`/`scale`/`skew`，都不占位置 |
| 文字 | `text`：颜色、字号、字重、字间距、行高、大小写、斜体、装饰线、阴影、描边、渐变 | 写在被绘制的节点和其中每个直接含文字的节点上；渐变文字给每段文字包一层 `span`，只裁切到字形，不碰组件的表面 |
| 纹理 | `texture`：噪点、纸张、圆点、网格、条纹、斜纹、棋盘格、碳纤维、扫描线、交叉线、网点 | 叠在填充上、文字下的 `background-image`；噪点和纸张是内联 SVG，只接受十六进制墨色 |

约定：

- **颜色只有两种写法。** M3 角色的 kebab-case 名称（`primary`、`on-surface`、`surface-container-high`），可带透明度（`primary/40`）；或者十六进制（`#rgb`、`#rgba`、`#rrggbb`、`#rrggbbaa`）。角色跟着风格和深浅色变，十六进制是作者自己的颜色。其他字符串（`red`、`var(...)`、`url(...)`）一律不认。
- **打开即清洗。** 文件、分享链接和 AI 的回答都经过 `cleanLook`：类型不对的字段去掉，数字收进范围，认不出的字符串丢弃，不会因为外观拒绝整个文件。绘制时再校验一次，所以浏览器里自存的副本也不会把任意字符串带进样式。
- **旧字段照旧。** `borderWidth`、`borderColor`、`shadow`、`opacity`、`glass`、`rotate`、`gradientTo`、`gradientAngle`、`font` 的绘制结果和以前完全一样（`lib/look.test.ts` 逐条对照）。同时给了新旧两种时以新的为准：`fills` 代替 `gradientTo`，`shadows` 代替 `shadow`。面板显示旧字段换算成的效果，改动后写成新字段。
- **状态层不受影响。** 外观只写内联样式，不碰 `::before`，按钮的悬停和按下仍由 M3E 的状态层负责。内联的 `box-shadow` 会盖过按钮悬停时的阴影变化。
- **严格遵守风格时**（`lib/styleRules.ts`），`look` 只保留 `opacity`、`rotate`、`transform`、`blur`、`blend` 和 `elevation`，面板也只显示这些。表面、描边、阴影和文字效果由风格决定。
- **预设**（光泽按钮、玻璃、霓虹、立体按钮、游戏标题、金色边框、纸张等）写的是普通字段，套用后仍可逐项修改。套用预设会替换效果，保留不透明度和变换。

已知限制：组件内部自己渲染、不在树里的文字（比如自带组件从属性里取的标签）拿不到渐变文字和字号，只继承颜色、阴影和描边；`elevation` 在导出项目里依赖 `src/style.css` 中的 `--look-elev-N`，复制出去的单个屏幕代码只有 M3 的默认高度；屏幕背景还不能用效果。
