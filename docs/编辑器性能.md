# 编辑器性能

大文档下编辑器每次交互做多少工作，怎样量，量出来是多少。对应审查报告 13.1 的 ED-2：先建基线，再改订阅和测量，阈值按实测定。

## 怎样量

```
bun run bench:editor                                   # 构建后用 vp preview 起一个，开 40 屏（1000 个部件）的文档
bun run bench:editor -- --base http://127.0.0.1:4173   # 用已经在跑的编辑器
bun run bench:editor -- --screens 10 --reps 20 --json out.json
bun run bench:editor -- --base <vp dev 的地址> --breakdown   # 再按组件名列出渲染最多的组件（开发服务器才保留组件名）
```

脚本是 `scripts/bench-editor.ts`，在无头 Chromium 里（Playwright，和端到端测试一样另装）通过分享链接打开一份大文档：
`--screens` 个手机屏，每屏一个顶栏加 24 个常用部件（按钮、纸片、开关、复选框、徽标、标签）。每种交互先做一遍热身，再各做
`--reps` 遍，报每遍的平均值：

| 列 | 含义 | 怎样数 |
| --- | --- | --- |
| commits | React 提交次数 | DevTools 全局钩子（生产构建的 React 也会调用它） |
| rendered | 这些提交里真正重新渲染的组件数 | 遍历提交后的 fiber 树，和 React DevTools 判断“这次渲染了”的方法一样 |
| measured | 隐藏测量层里读取的盒子数 | 包装 `getBoundingClientRect`，只数测量层（`[data-measure-layer]`）里的元素 |
| baselines | 重新读取的文字基线数 | 包装 `Range#getClientRects`，同样只数测量层 |
| paint med / worst | 输入事件到它处理完后下一帧的时间，中位数和最大值（毫秒） | 事件捕获阶段记 `timeStamp`，`requestAnimationFrame` 之后的任务里取当前时间 |
| long | 交互期间超过 50 ms 的长任务合计（毫秒） | `PerformanceObserver("longtask")` |

数渲染要遍历整棵树，会拖慢时间，所以计数和计时分两轮跑，计时那一轮不遍历。数字和机器有关，只比较同一台机器上的两次运行。

最后一行另开一页：预览一个绑定了每帧数据的 HUD（`e2e/frames.e2e.ts` 的 `hudDoc`：20 个敌人的血条和伤害数字、一个冷却，[数据绑定](数据绑定.md)“每帧绑定”），页面给预览一个每帧都在变的世界（`window.m3ePreviewWorld`），稳定后数 60 帧里 React 的提交和渲染次数，以及血条有几帧画得不一样。

## 结果

2026-11-08，开发容器里的无头 Chromium（软件渲染，CPU 与其他任务共享），生产构建，40 屏 1000 个部件，每种交互 12 遍。
“之前”是第二批开始时的集成分支（7711ab7，只加了测量层的 `data-measure-layer` 标记以便计数），“之后”是本次修改。

| 交互（每遍） | 提交 之前 → 之后 | 渲染组件 之前 → 之后 | 读取盒子 之前 → 之后 | 下一帧中位数 ms 之前 → 之后 | 长任务 ms 之前 → 之后 |
| --- | --- | --- | --- | --- | --- |
| 选中一个部件 | 3 → 3 | 10969 → 2044 | 3000 → 0 | 173 → 104 | 128 → 51 |
| 切换左侧标签页 | 1.2 → 1.1 | 3171 → 951 | 1000 → 0 | 95 → 72 | 77 → 31 |
| 指针划过部件（7 次移动） | 6.9 → 7.8 | 21385 → 4164 | 5833 → 0 | 92 → 41 | 76 → 6 |
| 滚轮平移画布 | 2 → 2 | 3666 → 694 | 1000 → 0 | 40 → 10 | 9 → 0 |
| 在部件的标签里打一个字 | 21 → 22 | 11034 → 2127 | 3000 → 1 | 178 → 112 | 179 → 98 |
| 拖动一个部件（6 次移动） | 14 → 14 | 31525 → 4456 | 10667 → 2 | 94 → 49 | 412 → 81 |
| 打开文档（整个过程） | 36 → 33 | — | 13682 → 5254 | 部件全部上画布 5.6 s → 4.7 s | 5462 → 4355 |

之前每次提交都把 1000 个部件全部量一遍（选中一次 3 次提交就是 3000 次读取），不管这次提交改了什么；画布上每个部件也随根组件
一起重新渲染。之后只量变了的部件，画布只重绘自己的输入变了的分组。

打字那一行的 22 次提交里大部分是尺寸手柄跟随部件新尺寸的逐帧动画（每次只渲染 `SizeHandles` 一个组件），不是重复的全量工作。

## 改了什么

- **只量变了的部件**（`src/editor/useMeasure.ts`、`src/editor/measureBook.ts`）。部件该量的情况：新加的；画它的条目（item）或它所在屏幕的
  尺寸变了；它的盒子自己变了尺寸（每个盒子用 `ResizeObserver` 盯着边框盒，图片、懒加载的组件、样式表改了尺寸都会在下一帧前量到，
  不用等别的渲染）；浮层落定或组件模块到达（`m3-remeasure` 事件，同一次提交里来的多个事件合成一次）；字体加载完成或测量被清空
  （`setWidths({})`、整份文档换掉）时全部重量。选中、开面板、指针移动不读任何盒子。先把要量的都读完再写回，读写不交错。
- **基线缓存跟着字体走**：字体加载完成会把基线缓存整个作废，同样外框尺寸、换了字体的部件也重新读基线（之前按 id 和宽高命中，
  字体变了也取旧值）。
- **缓存跟着部件走**：删掉的部件同时从基线、尺寸、输入缓存和测量结果里去掉；删了再加大量部件后缓存回到当前部件数。
- **画布分组按自己的输入重绘**（`src/editor/render.tsx` 的 `sameGroup`）：一个分组只在它自己的位置、所在屏幕尺寸、它的部件的测量值、
  选中与按下状态、空位和偏移变了时才重新渲染；按下部件的处理函数通过 ref 取最新的，没重绘的分组也调到当前的函数。面板里的
  `Icon` 也改成 props 不变就不重绘。
- **按需订阅**（`lib/core/react.ts` 的 `useStoreSelector`）：只用到文档一部分的组件只订阅那一部分，选中、测量、历史变化不会让它们重绘。
  MCP 按钮只在截图期间读文档，外链图片横幅只读屏幕、部件和定义。编辑器根组件仍然读完整的状态（它显示的几乎就是全部），省下的是
  根组件每次渲染的代价。

### 每帧绑定

2026-11-09，同一类开发容器，生产构建：预览 20 个血条、20 个伤害数字和一个冷却，世界每帧都变，60 帧里 **0 次提交、0 个组件渲染**，血条 60 帧都画得不一样（值由帧循环直接写进 DOM，`components/preview/frames.ts`）。端到端测试 `e2e/frames.e2e.ts` 把它定为验收：世界在变、画面跟着变的那一秒里提交数必须是 0。

## 验收和阈值

端到端测试 `e2e/measure.e2e.ts` 固定了不依赖机器的部分：选中、切换标签页、指针划过不读测量层的任何盒子；在一个部件的标签里打字只读
这一个部件；字体加载事件后所有部件的基线重新读取而尺寸不变；测量层里一个盒子自己变大，不经过任何渲染，画布上的部件也跟着变大。
`src/editor/measureBook.test.ts` 覆盖缓存规则：删掉大量部件后缓存回到当前部件数，换字体后同尺寸也重读基线。

时间类的阈值只适用于同一台机器，不放进 CI。按上面的实测，在这类环境里 1000 个部件时建议：选中一个部件下一帧中位数不超过
150 ms，切换标签页不超过 100 ms，指针划过不超过 60 ms，滚轮平移不超过 25 ms，打字不超过 150 ms；超过时先用 `--breakdown` 看是哪些组件在渲染。

## 还没做的

- 编辑器根组件仍然订阅整个 store，选中一个部件时右侧面板、左侧面板的磁贴（约 330 个）、每个屏幕标题上的尺寸切换仍然随根组件渲染。
  进一步拆分需要把面板移到各自订阅的子组件里，属于更大的结构调整。
- 选中时剩下的时间大部分在浏览器的绘制和图层合成（1000 个部件、每个分组一个动画层），不在 React。
