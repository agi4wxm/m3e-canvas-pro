# 后端

完整产品导出（见 [导出](导出.md)）里的 `server/` 是从接口契约（[接口](接口.md)，`Doc.api`）生成的后端骨架：Node + TypeScript + Fastify。路由、校验、类型、错误、鉴权、分页、上传、实时通道都由契约生成；业务逻辑是自定义代码（人或 AI 写），只写在 `server/src/handlers/` 和 `server/src/custom/`。`contract-tests/` 拿运行中的后端对照契约检查。

代码在 `lib/export/targets/server.ts`（后端工作区）、`lib/export/targets/contractTests.ts`（契约测试工作区），它们共用 `lib/export/server/`：

```text
lib/export/server/
  contract.ts     契约在后端眼里的样子：每个接口的路由、参数、请求体、响应、实际生效的 security、分页；每个实时通道
  schemas.ts      给校验器用的 JSON Schema：引用指向定义文档，请求 / 响应两种视图
  examples.ts     契约测试的请求用的示例值：契约自己的示例优先，否则由模拟库的生成器（lib/mocks）按 Schema 生成
  typesSource.ts  src/generated/types.ts：模型、每个接口的类型（Operations）、每个通道的类型（Channels）
  runtime.ts      src/generated/ 里和契约无关的运行时（路由、校验、错误、鉴权、上传、分页、实时、文档）
  comments.ts     契约里的文字写进注释时的规则
```

## 生成的结构

```text
server/
  package.json        生成（合并）：fastify、@fastify/cors、multipart、websocket、swagger、swagger-ui、ajv、ajv-formats
  build.mjs           生成：esbuild 打包成 dist/main.js
  .env.example        生成：环境变量的说明
  src/main.ts         生成：读 .env、启动、优雅退出
  src/app.ts          生成：buildApp()，按顺序装好错误处理、校验器、CORS、上传、文档、custom/setup、路由、通道
  src/generated/      生成，每次导出重写，不要改
    contract.ts       OpenAPI / AsyncAPI 文档、校验用的模型定义、安全方案、实时前缀、健康和文档的路径
    operations.ts     每个接口的数据：方法、Fastify 路由、参数、security、请求体、各状态码的响应、分页
    channels.ts       每个实时通道的数据：地址、方式、收发的消息和它们的 Schema
    types.ts          模型的 TypeScript 类型、Operations、Channels
    handlers.ts       Handler<"接口">、Context、Channel<"通道">、publish()；引入 handlers/ 下的每个文件
    routes.ts         把每个接口注册成 Fastify 路由：鉴权 → 参数、查询、请求头校验 → 请求体 → 处理函数 → 响应
    errors.ts         HttpError 和 notFound() 等、notImplemented()、problem+json 错误处理
    auth.ts           从请求里取凭证、按 security 要求调用 custom/auth.ts
    validation.ts     ajv（JSON Schema 2020-12）：请求、响应、实时消息的校验
    uploads.ts        multipart 读取（UploadedFile）、fileReply()（文件响应）
    pagination.ts     ctx.page、ctx.paginate()、encodeCursor / decodeCursor
    realtime.ts       WebSocket / SSE 通道
    docs.ts           健康检查；开发时的 Swagger UI
    config.ts         环境变量
    server.test.ts    后端自己的测试：路由齐全、404、401、400 带 pointer、健康、文档
  src/handlers/<operationId>.ts        自定义：每个接口一个，先抛 notImplemented()（501），注释里是这个接口的契约
  src/handlers/channels/<通道>.ts      自定义：每个实时通道一个，先拒绝连接（关闭码 4501）
  src/custom/auth.ts                  自定义：authenticate(credential) → User | null
  src/custom/db.ts                    自定义：数据层（先给了内存表 table()，不强加数据库）
  src/custom/setup.ts                 自定义：插件、钩子、契约外的路由
```

自定义文件导出的名字和签名是固定的约定（`export default` 的处理函数、`User`、`authenticate`、`setup`），生成的代码只用这些。

## 处理函数

```ts
import { notFound } from "../generated/errors";
import type { Handler } from "../generated/handlers";
import { products } from "../custom/db";

const getProduct: Handler<"getProduct"> = async (ctx) => {
  const found = products.get(ctx.params.productId);
  if (!found) throw notFound("没有这个商品");
  return found; // 类型是契约里 200 的 Product
};

export default getProduct;
```

`ctx` 里有：`params`、`query`、`headers`、`body`（都已按契约校验，查询参数补上了默认值）、`user`（需要鉴权的接口一定有）、`page` 和 `paginate`（分页接口）、`respond(status, body)`（契约列出的其他状态码）、`request`、`reply`、`log`。返回值就是成功响应（契约里的第一个 2XX：POST 默认 201、DELETE 无内容 204）。类型都来自 `src/generated/types.ts` 的 `Operations["getProduct"]`：返回契约不允许的东西就通不过类型检查。

- **错误**：一律是 RFC 9457 problem details（`application/problem+json`）。处理函数抛 `HttpError` 或 `badRequest()`、`unauthorized()`、`forbidden()`、`notFound()`、`conflict()`、`unprocessable(detail, errors)`；`errors: [{ pointer: "#/price", detail }]` 逐个字段说明。请求不符合契约 → 400，`errors` 里每条有 `pointer`（请求体里的位置，或参数名）、`detail` 和 `in`（`body`、`query`、`path`、`header`）。其他抛出的东西 → 500，只说“Internal Server Error”，日志里记下堆栈。还没写的接口 → 501，日志里只有一行 info，不打印堆栈。开发时处理函数抛出契约没有列出的状态码会记一条警告。
- **响应校验**：开发时（`NODE_ENV` 不是 production）每个响应发出前按契约检查，不符合就变成 500，`errors` 说哪里不对；生产环境不检查（`VALIDATE_RESPONSES` 可以单独开关）。
- **分页**：`x-m3e-pagination` 的约定。`ctx.page` 是请求要的那一页（`{ style: "cursor", cursor, limit }` 或 `{ style: "offset", offset, limit }`，参数名按契约，`limit` 默认取参数 Schema 的 default，没有则 20）；`ctx.paginate(列表)` 从内存里的列表切出这一页，字段名按契约（`items`、`nextCursor` / `total`）；查数据库时用 `encodeCursor` / `decodeCursor` 做不透明的游标（不是这个后端给的游标 → 400）。
- **上传**：`multipart/form-data` 的文件字段是 `UploadedFile`（`filename`、`mimetype`、`size`、`data` 是 Buffer），其他字段按 Schema 转换类型后校验；文件超过 `UPLOAD_MAX_BYTES` → 413，类型不在 Encoding 的 `contentType` 里 → 415，缺必填文件 → 400。`application/x-www-form-urlencoded`、纯文本、`application/octet-stream` 之类的二进制请求体也能收（二进制是一个 `UploadedFile`）。
- **文件响应**：契约里响应是 PDF、图片等时，处理函数返回 `fileReply(数据, { contentType, filename })`（`src/generated/uploads.ts`）；有 `filename` 时带 `Content-Disposition`（RFC 6266，中文名也行）。

## 鉴权

接口的 `security`（没写时用契约的默认值，`[]` 表示任何人可调用，`{}` 表示可以匿名）决定谁能调用。生成的代码从请求里取凭证：`Authorization: Bearer …`（http bearer、OAuth2、OpenID Connect）、`Authorization: Basic …`、请求头 / 查询参数 / Cookie 里的 API 密钥，然后调用 `custom/auth.ts` 的 `authenticate(credential)`：返回 `User` 或 `null`。没有凭证 → 401（带 `WWW-Authenticate: Bearer`），凭证不被接受 → 401（`error="invalid_token"`），在 `authenticate` 里抛 `forbidden()` → 403（比如 scope 不够，`credential.scopes` 是接口要的 scope）。鉴权在读请求体之前做。新导出的 `authenticate` 抛 `notImplemented()`：带凭证调用需要鉴权的接口得到 501，所以新骨架的契约测试是“待实现”而不是失败。登录接口（`x-m3e-auth` 的 `login`）本身是普通接口：它的处理函数签发令牌，放在契约规定的字段里（默认 `accessToken`、`refreshToken`）。

## 实时通道

AsyncAPI 的通道挂在实时前缀下（契约里 dev 服务器实时地址的路径，比如 `ws://localhost:8081/realtime` → `/realtime`；没有时 `/realtime`；环境变量 `REALTIME_PREFIX` 可改），例如 `/realtime/rooms/{roomId}`。

- **WebSocket**：每一帧就是一条消息的 JSON payload，和契约写的完全一样（不加信封）；服务器按通道的 `receive` 消息逐个校验，匹配到哪个就是哪条消息。不是 JSON → 关闭码 1007，哪条都不匹配 → 1007，通道不收消息 → 1008，二进制帧 → 1003。
- **SSE**（`x-m3e-transport: sse`）：`event:` 是消息名，`data:` 是 payload 的 JSON；每 15 秒一个注释行保活。
- 处理函数 `Channel<"room">`：`onConnect(connection)`（抛错拒绝：`HttpError` 的状态码 + 4000 作为关闭码，比如 4401、4403、4501；SSE 直接回 problem+json）、`onMessage(connection, { message, payload })`、`onClose(connection)`。`connection.send(消息名, payload)` 只能发契约里服务器 `send` 的消息；`publish("room", { roomId }, "chatMessage", payload)`（`src/generated/handlers.ts`）发给通道上所有（参数相同的）连接，HTTP 处理函数里也能用。开发时发出的消息也按契约校验。
- 连接的用户：`Authorization: Bearer` 请求头，浏览器不能设请求头时用查询参数 `access_token`（RFC 6750），同样经过 `authenticate`；没有令牌时 `connection.user` 是 undefined，由 `onConnect` 决定要不要拒绝。

## 安全的默认值

生成的骨架默认做到这些（`server/src/generated/server.test.ts` 逐条检查，`bun run check:product <文件夹> shop` 在构建出的后端上再查一遍）：

- **鉴权先于一切**：需要鉴权的接口在读请求体之前鉴权；新导出的 `authenticate` 回答 501，写好之前任何带凭证的请求都进不去，不带凭证的是 401。
- **错误不泄露**：`HttpError` 以外抛出的东西一律 500，只说 “Internal Server Error”，堆栈只进日志；不合契约的请求是 400，逐个字段说明。坏的 Cookie 编码按原样交给 `authenticate`，不会变成 500。
- **CORS**：开发时只有本机的开发服务器，生产时一个也没有，直到 `CORS_ORIGINS` 列出应用的地址；`*` 允许任意来源，但不带 Cookie。
- **回答的类型**：每个回答都带 `X-Content-Type-Options: nosniff`；文件回答（`fileReply`）的类型是浏览器会执行脚本的（SVG、HTML、XML）时带 `Content-Security-Policy: … sandbox`，用户上传的 SVG 直接打开也不能在 API 的源上运行脚本。
- **日志里没有凭证**：请求地址里的 `access_token`（实时通道）和放在查询参数里的 API 密钥写进日志前换成 `[redacted]`。
- **实时通道不会把后端弄崩**：关闭连接的原因按 UTF-8 截到 123 字节（WebSocket 的上限；以前处理函数抛出较长的中文错误会让 ws 抛错，整个进程退出），关闭码不合法时直接断开；处理函数的 `onClose` 同步抛错、已经结束的 SSE 再写入都只记日志。
- **上限**：请求体 1 MB，上传单个文件 `UPLOAD_MAX_BYTES`、最多 20 个文件、200 个字段，WebSocket 一帧 1 MB。

要由自定义代码（人或 AI 写）补上的（导出的 `AGENTS.md` 的 “Security” 一节同样写给 AI 编程助手）：

- `authenticate` 真正校验令牌（签名、过期、受众），密码只存慢哈希，比较密钥用常量时间；不要在日志里写令牌和整个请求体。
- 按记录授权：`ctx.user` 只说明是谁，处理函数要检查他能不能读写这条记录。
- 上传的 `mimetype` 是客户端说的；要紧时检查内容，存放时用自己起的名字，不用客户端给的 `filename` 当路径。
- 实时通道的 `onConnect` 决定谁能连；没有令牌的连接没有 `user`。WebSocket 不检查 Origin（凭证只认令牌，不认 Cookie）。
- **没有限流**：上线前在 `custom/setup.ts` 里加（如 `@fastify/rate-limit`），至少覆盖登录、发短信邮件、花钱的接口。
- 契约的 `pattern` 对每个请求都要执行：嵌套而可选的重复（`^([a-z0-9]+[._-]?)*$`）遇到不匹配的长字符串可能要指数时间，会卡住整个进程。模式写简单，给字段 `maxLength`，在设计里改。
- 上线时：`npm start`（或 `NODE_ENV=production`）、`HOST=0.0.0.0` 放在终止 TLS 的反向代理后面、`CORS_ORIGINS` 设成应用的地址，密钥只放环境变量。

## 校验的细节

- 校验器是 ajv 的 JSON Schema 2020-12（OpenAPI 3.1 的方言）加 ajv-formats；契约里 ajv-formats 不认识的 `format`（比如 `phone`）照样接受。
- 路径参数、查询参数、请求头、表单字段是文本，按 Schema 转换类型（`"2"` → 2，单个值 → 数组）；JSON 请求体不转换；响应和实时消息只检查不改。请求里缺的字段按 Schema 的 `default` 补上。
- 模型统一放进一个定义文档，引用改成指向它；**请求视图**里 `readOnly` 的字段不算必填，**响应视图**里 `writeOnly` 的字段不算必填。指向不存在的模型、外部文件的引用，和不是正则表达式的 `pattern` 在生成时去掉（导出的警告里列出），不会让后端启动失败。
- Fastify 不能按原样路由的路径（含 `*`、参数后面紧跟字母）和与别的接口重复的路由不注册，导出时给出警告，契约测试把它报为失败。

## 契约测试

```bash
npm run contract -w contract-tests                          # 自己启动后端，逐个检查
npm run contract -w contract-tests -- --strict              # 待实现（501）也算失败
npm run contract -w contract-tests -- --only listProducts,createProduct
npm run contract -w contract-tests -- --base-url http://127.0.0.1:3001   # 检查运行中的后端
CONTRACT_TOKEN=… CONTRACT_API_KEY=… CONTRACT_BASIC=user:pass npm run contract -w contract-tests
npm test -w contract-tests                                  # 同样的检查，Vitest；CONTRACT_BASE_URL、CONTRACT_STRICT=1
```

每个接口的请求来自契约的示例（媒体类型的 `example` / `examples`、参数的 `example`、Schema 的 `examples` / `default` / `enum`），没有时按 Schema 生成（必填字段，加上有示例的可选字段），上传带一个小 PNG。请求经过生成的客户端（`packages/api` 的 `createApi`，multipart 等非 JSON 请求体用它的 `request`）发出。判定：

| 结果 | 条件 |
| --- | --- |
| **implemented** | 状态码是契约列出的（精确、`4XX` 这类、或 `default`），响应体通过它的 Schema（JSON）或类型对得上（文件、文本），没有内容的响应确实没有内容 |
| **pending** | 501；需要鉴权的接口没有给凭证时回 401（说明鉴权生效了，但接口本身没测到）；实时通道关闭码 4501 |
| **failing** | 契约没列出的状态码、响应体不符、5XX、给了凭证还被 401/403、不需要凭证却回 401 以外的错、连不上；实时通道收到不符合契约的消息或被 1007/1008/1011/4xxx 关闭 |

最后打印汇总（`contract: 2 implemented, 11 pending, 0 failing`）。默认 pending 不算失败（新骨架是绿的），`--strict` 时算。实时通道：连上（有令牌时带 `access_token`），发一条契约里服务器接收的消息（示例或生成的），在 `--window` 毫秒（默认 500）内收到的每条消息都要是服务器发送的某条消息。

## 重新导出

- 生成的文件每次重写；处理函数和 `custom/` 只在不存在时写一次。
- 契约加了接口：多出一个 `server/src/handlers/<新接口>.ts` 桩，别的文件都不动。
- 契约去掉了接口：它的处理函数文件**留在原处**，不再被引用，导出报告里列为孤儿（`customOrphans`，编辑器里“设计里已经没有的东西的自定义代码”），每次导出都会报，直到删掉它。孤儿文件仍能通过类型检查（`Handler<"不存在的名字">` 是宽松的类型），不会让构建变红。接口又回来时，原来写的处理函数直接接上。
- 改了 operationId 等于去掉旧的、加上新的：把旧文件里的代码移到新文件。

## 给 AI 编程助手

导出的 `AGENTS.md` 有 “The server (server/)” 一节（`lib/export/targets/server.ts` 的 `serverAgents`）：只能写哪些文件、处理函数怎么写、错误、分页、上传、实时、鉴权钩子、持久化的选择（不强加 ORM：先用内存表，再选 SQLite、PostgreSQL 加查询构建器或 Prisma，用 `npm install <包> -w server` 安装）、怎样运行和严格地跑契约测试，以及契约有问题时怎么办：不绕过契约、不改生成的代码，说明需要的改动，在设计里改（接口标签页、应用内 AI、MCP 的 `update_endpoint` 等）再导出。

## 检查

`bun run check:product <空文件夹> shop` 对商店的契约真的安装、构建、启动后端：未实现的接口回 501 problem+json，不符合契约的请求回 400（带 pointer），需要鉴权的接口不带凭证回 401；契约测试全部 pending、`--strict` 失败；然后像 AI 助手一样写好 `listProducts`、`createProduct`（内存表）和 `authenticate`，类型检查、ESLint、Prettier、构建都通过，`--strict --only listProducts,createProduct` 通过；再导出时这些文件一字不变；契约加一个接口只多一个桩、别的什么都不报；去掉一个接口时它的处理函数留下并报为孤儿，后端仍能通过类型检查。CI 的 product 任务跑 `proof` 和 `shop` 两个。

## 已知限制

- 查询参数只支持 `form` + `explode`（重复的键是数组）；`deepObject`、`spaceDelimited`、`pipeDelimited` 和参数的 `content` 写法不解析。Cookie 参数不校验。
- 一个接口有多种请求体媒体类型时，按 JSON、multipart、表单、第一个的顺序取一种来校验和生成类型，其他类型的请求体原样收下。
- 实时通道的鉴权只认 bearer 令牌（AsyncAPI 自己的 `securitySchemes` 和操作的 `security` 原样保留在契约里，后端不读）；通道地址参数在契约测试里一律用 `example`。
- 契约测试的示例值由模拟库的生成器（`lib/mocks/generate.ts`，见 [模拟库](模拟库.md)）生成：契约自己的示例优先，只填必填的（和有示例的）字段，列表尽量短，不给 null，英文，日期围绕固定时刻，所以同一份契约导出的文件不变。`pattern` 只支持简单正则，复杂的正则没有示例时可能生成不符合的值。
- 响应头（比如 201 的 `Location`）不生成、不校验，处理函数用 `ctx.reply.header()` 自己设。
