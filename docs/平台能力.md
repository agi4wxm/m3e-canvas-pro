# 平台能力

支付、第三方登录、内购、定位、扫码、推送、分享、剪贴板、打开链接、选文件、统计、生物识别、音视频通话，以及地图、相机、通话画面这类视图，和后端业务、玩法规则一样，**M3E 不做真实实现**（见[边界与契约](边界与契约.md)）。它只做四件事：

1. 定义能力接口：输入、输出、事件、失败类型（JSON Schema）。
2. 在设计里表达“什么时候调用、结果怎么呈现”：每种结果（完成、取消、失败、拒绝授权、不可用、超时、未实现）都有设计。
3. 预览里用模拟结果驱动这些界面，能按场景一键切换，并在请求记录里看到每一次能力调用。
4. 导出类型定义、注册表和只写一次的适配文件、插槽文件，由人或 AI 接真正的 SDK。

M3E 不嵌 SDK，不放密钥，不判定结果，不写权限声明。唯一的例外是不需要账号、没有产品逻辑的通用能力（打开链接、复制、分享、选文件，Web 上还有定位）：各端有默认适配，但也走同一个接口，可以覆盖。

代码在 `lib/capabilities/`：`types.ts`（类型）、`catalog.ts`（能力目录）、`registry.ts`（注册表）、`mock.ts`（模拟结果）这四个文件不依赖别的代码，原样复制进导出产品的 `packages/capabilities`；`clean.ts`（读文件时的清理）和 `doc.ts`（文档用到了哪些能力）只在编辑器里。操作在 `lib/core/ops/capabilities.ts`，读取工具 `list_capabilities` 在 `lib/tools/capabilitiesRead.ts`，界面文字在 `lib/i18n/capabilities.ts`。

## 能力目录

标准能力由 M3E 内置，每个带版本（`version`，现在都是 1）。`kind` 是 `call`（调用：由效果 `invoke` 发起，回答一次）、`event`（平台自己发来的事件）或 `view`（画在屏幕上的视图：接收属性，发出事件）。

| 能力 | 形式 | 输入 | 输出或事件 | 失败类型（另加 `not-implemented`） |
| --- | --- | --- | --- | --- |
| `payment.pay` | 调用 | `orderId`*、`amount`、`currency`、`method`、`payload`（后端签好的支付参数） | `{ status: "submitted" }`：只代表已提交 | `cancelled`、`failed`、`unavailable` |
| `iap.purchase` | 调用 | `productId`* | `{ receipt, productId, transactionId }`（交给后端校验） | `cancelled`、`failed`、`unavailable` |
| `auth.oauth` | 调用 | `provider`*（apple、google、wechat、alipay、paypal、stripe、github、facebook、x、line、kakao、other）、`scopes` | `{ provider, code }` 或 `{ provider, idToken }`（再调登录接口） | `cancelled`、`failed`、`unavailable` |
| `location.current` | 调用 | `accuracy`（low、balanced、high） | `{ lat, lng, accuracy }` | `denied`、`unavailable`、`timeout` |
| `scan.code` | 调用 | `formats` | `{ text, format }` | `cancelled`、`denied`、`unavailable` |
| `push.register` | 调用 | — | `{ token, platform }`（再调后端注册） | `denied`、`unavailable` |
| `push.opened` | 事件 | — | `{ route, params, data }` | — |
| `share.open` | 调用（通用） | `title`、`text`、`url` | `{}` | `cancelled`、`unavailable` |
| `clipboard.write` | 调用（通用） | `text`* | `{}` | `failed`、`denied` |
| `link.open` | 调用（通用） | `url`* | `{}` | `failed` |
| `file.pick` | 调用（通用） | `accept`、`multiple`、`source`（album、camera、file） | `{ files: [{ name, type, size, url }] }` | `cancelled`、`denied` |
| `analytics.track` | 调用 | `event`*、`props` | `{}` | 从不失败（`silent`：失败和未实现都当作完成） |
| `biometric.verify` | 调用 | `reason` | `{ ok }` | `cancelled`、`unavailable` |
| `rtc.call` | 调用 | `room`*、`video` | `{ callId }`；画面是 `rtc.view` | `failed`、`denied`、`unavailable` |
| `rtc.view` | 视图 | `name`、`connected`、`status`、`mic`、`camera`、`speaker`、`startedAt`、`image` | 事件 `connected`、`ended`、`muted {muted}` | — |
| `map` | 视图 | `label`、`center {lat,lng}`、`zoom`、`markers [{id,title,lat,lng}]`、`route [{lat,lng}]`、`selected` | 事件 `markerTap {id}`、`regionChange {center, zoom}`、`longPress {lat, lng}` | `unavailable` |
| `camera` | 视图 | `facing`（back、front）、`mode`（photo、video、scan）、`state`（live、denied、unavailable）、`denied` | 事件 `captured {file}`、`scanned {text, format}` | `denied`、`unavailable` |

（* 是必填参数。）任何调用在适配代码还没写的时候都回答 `not-implemented`，设计里也要为它准备一个样子（通常是“功能即将开放”一类的提示）。`list_capabilities` 列出每个能力的参数、结果和失败类型，以及文档用到了哪些、模拟库怎样回答。

## 文档模型

`Doc.capabilities`（可以不写）：

```json
{
  "uses": ["push.opened"],
  "own": [{ "name": "acme.ticket.scan", "kind": "call", "summary": "…", "args": { "type": "object", "properties": { "gate": { "type": "string" } }, "required": ["gate"] }, "result": { "type": "object", "properties": { "ticket": { "type": "string" } } }, "failures": ["cancelled"] }]
}
```

- 设计里调用了的能力（`invoke`）和画出来的能力视图（`map`、`camera`、`video-call` 组件）都算“用到”，不必写进 `uses`；`uses` 只列此外用到的（平台事件 `push.opened`，或只在代码里调用的）。
- `own` 是产品自己的能力，格式和目录一样（名字最多四段，每段小写字母开头，如 `acme.ticket.scan`）。标准能力的名字不能再声明。
- 读文件时形状不对的丢掉，不认识的字段保留（`lib/capabilities/clean.ts`），最多 100 个自有能力、100 个 `uses`。项目文件里它和其他文档字段一样按键排序写出，没有它的文档字节不变。

### 效果 `invoke`

```json
{ "do": "invoke", "capability": "payment.pay",
  "args": { "orderId": "response.id", "amount": "response.amount" },
  "then": { "to": "result", "params": { "orderId": "response.id" } },
  "catch": { "to": "none", "effects": [{ "do": "setVar", "var": "payIssue", "value": "", "expr": "error.type" }] } }
```

- `args` 的每个值是表达式，在这一步读；读成空的不发。
- `then` 在能力做到了时运行，读 `result`；`catch` 在没做到时运行，读 `error`：`error.type` 是失败类型，`error.capability`、`error.message` 是能力名和说明。按类型分支的办法：在 `catch` 里把 `error.type` 写进变量，再用 `showWhen` 显示各自的设计。`then` / `catch` 不接受 `when`、`else`。
- 嵌套在调用的回答里时，外层的 `response` 照样读得到（上例的 `then` 读 `response.id`）。`invoke` 和 `call` 共用 4 层的嵌套上限。
- 运行规则和调用接口完全一样（[交互规则](交互规则.md)的“调用能力”）：不等回答；回答在点击那一屏运行；重新开始后的回答丢弃；同一组件再次调用同一能力时旧回答让位；访客已经离开时效果照常运行、跳转不再发生。
- 校验（`set_action`、`apply_ops`、MCP）：能力必须是目录里的或文档声明的 `call`；`args` 的名字必须是能力的参数，必填的不能少；表达式要能解析。
- 编辑器：效果面板的“调用平台能力”，选能力、填参数、设计 `then` 和 `catch`；选 `payment.pay` 时提示“完成只代表已提交”。
- 提示词（导出的说明文字）写成“调用平台能力 payment.pay”。

### 能力视图

`map`、`camera`、`video-call` 三个组件是能力视图（`PartDef.capability` 是 `map`、`camera`、`rtc.view`）：

- 属性就是能力的输入：地图的中心（`lat,lng`）、缩放、标记点（表格：Id、Title、Lat、Lng，可以绑定数据）、选中的标记（它的输入）、是否连成路线；相机的镜头、拍什么、显示为“画面 / 被拒绝 / 不可用”和被拒绝时的文字；通话的接通、麦克风、摄像头、扬声器和接通时间（来自后端）。
- 事件就是能力的事件：`on:markerTap`（读 `event.id`）、`on:regionChange`、`on:longPress`；`on:captured`（读 `event.file`）、`on:scanned`（读 `event.text`）；`on:muted`、`on:ended`。
- 画布和预览画的是替身：静态底图上按坐标摆的标记，点标记发出 `markerTap`；相机和通话是外框和按钮。相机拍照、扫码和通话计时只是原型演示（`demo`），产品里不演。
- 导出时每个能力视图得到一个只写一次的插槽（见下）。

## 预览：模拟结果与请求记录

预览里的 `invoke` 由模拟库回答（`lib/capabilities/mock.ts`），规则在 `Doc.mocks.capabilities`（所有场景）和场景的 `capabilities`（只在这个场景）：

```json
"mocks": {
  "capabilities": { "location.current": { "fail": "denied" } },
  "scenarios": [
    { "id": "pay-cancelled", "name": "支付已取消", "capabilities": { "payment.pay": { "fail": "cancelled" } } },
    { "id": "pay-success", "name": "支付成功", "ops": { "getOrder": { "patch": { "status": "paid" } } } }
  ]
}
```

- 一条规则是 `{ result?, fail?, message?, delayMs? }`：`result` 盖在目录的示例结果上，`fail` 让它以这个类型失败，`delayMs` 是等多久（默认 300 毫秒）。
- 没有规则时回答目录的示例：支付 `{status: "submitted"}`，定位是数据语言所在城市的坐标，扫码是一段固定网址，第三方登录带上请求的服务方，选文件从模拟库的文件库里按 `accept` 挑（没有就给一张占位图），声明了的自有能力回答它的示例；既不在目录也没声明的回答 `not-implemented`。
- **场景描述处境，不描述规则**：“支付成功”场景只是让后端的订单接口回答“已支付”（`patch`，见[模拟库](模拟库.md)），“支付已取消”只是让支付界面被关掉；能力本身从不决定订单是否已支付。
- 预览栏的场景切换同时换能力的规则；切换后还没回答的能力调用作废。没有接口、只有场景的文档也能切换。
- 请求记录面板把能力调用和接口请求按时间排在一起：能力名、完成（ok）或失败类型、结果的摘要、耗时（`data-preview-log-invoke`）。
- `link.open` 在预览里回答后真的在新标签页打开网址，和“打开链接”的跳转一样。
- 操作 `set_mock_capability {capability, scenario?, result?, fail?, message?, delayMs?, clear?}`，一步撤销；模拟库面板之外，AI 和 MCP 用它设置。

## 支付：以订单状态为准

客户端 SDK 的回调不能作为“支付成功”的依据，界面上的“成功”只能来自后端的订单状态：

```text
提交订单（call createOrder，后端返回订单号和签好的支付参数）
  → invoke payment.pay（只代表“已提交”或“已取消”）
  → 支付结果页：数据源 getOrder(params.orderId)，按 data.order.value.status 显示 已支付 / 处理中 / 失败
  → 后端收到支付平台的回调后改订单状态；结果页“刷新状态”重新加载
```

购物流程模板 `shop-flow` 就是这样做的（单独的 `order-success` 模板也带上订单的契约和场景；单独的 `checkout` 只有界面，“提交订单”留给作者接）：

- 结算页“提交订单”：先清掉上次的问题、标记“正在提交”（按钮文字绑定 `vars.paying`），调用 `createOrder`；它的 `then` 调用 `payment.pay`，参数读 `response.id`、`response.amount`；`payment.pay` 的 `then` 带着订单号去“支付结果”；`catch` 把 `error.type` 写进 `payIssue`，结算页按它显示“支付已取消”“支付没有成功”；`createOrder` 失败显示“订单没有创建成功”。
- 支付结果页是一个按 `order` 数据源显示状态的区域：加载中、加载失败各有设计；数据到了以后按订单状态显示“支付成功”（`paid`）、“支付处理中”（`pending`、`processing`，带“刷新状态”）或“支付失败”（`failed`、`cancelled`，带“返回结算”）。
- 模板带着它依赖的契约一起加进文档（文档里没有同名的才加）：模型 `Order`（`status` 由后端设置）、接口 `createOrder`（`POST /orders`）和 `getOrder`（`GET /orders/{orderId}`），变量 `payIssue`、`paying`，以及下面六个场景。
- 结算页的正文是一列，三条提示是列里的行：没显示的不占地方，预览里不留空洞。

六个场景每个对应一个设计，在预览栏里逐一切换（`e2e/capabilities.e2e.ts` 逐个点过）：

| 场景 | 怎样做到 | 看到的设计 |
| --- | --- | --- |
| 支付成功 `pay-success` | `getOrder` 的回答盖上 `status: "paid"` | 结果页“支付成功” |
| 支付处理中 `pay-processing` | `status: "processing"` | 结果页“支付处理中”和“刷新状态” |
| 支付提交中 `pay-submitting` | `payment.pay` 等 60 秒才回答（支付界面一直开着） | 结算页按钮“正在提交…” |
| 支付已取消 `pay-cancelled` | `payment.pay` 以 `cancelled` 失败 | 结算页“支付已取消” |
| 支付未完成 `pay-declined` | `payment.pay` 以 `failed` 失败 | 结算页“支付没有成功” |
| 支付失败 `pay-failed` | `status: "failed"` | 结果页“支付失败”和“返回结算” |

“按接口填充”加的“网络错误”场景让 `createOrder` 失败，结算页显示“订单没有创建成功”；“慢网”下能看到结果页的“正在确认支付结果…”。没有场景时，新建的订单是“待支付”，结果页显示“处理中”。

支付相关的组件（报告 2.4）：

- `checkout-bar` 不再自己切换“已下单”：合计、件数由属性给出，按钮只是槽位，`placed`（已下单）由属性给出，只有原型演示里按下会自己变；图标的开关是每行的 `variant`（on / off）。
- `brand-button`：`provider`（服务方）和 `intent`（`signin` 登录 / `pay` 支付）两个设置，按各家规范的颜色和文字画（“使用微信登录”“Apple 支付”……），不画标志（产品里由 SDK 的官方按钮画）；按下应当调用 `auth.oauth {provider}` 或 `payment.pay`，没有接上时导出报告列为 `capability`。
- `number-pad`：输入（金额或密码作为值），确认是带值的事件 `on:submit`（读 `event.value`）；“已发送”由 `sent` 属性（对面的结果）决定，只有原型演示会自己显示。
- `subscription`：选中的方案是输入（`selected`，每个方案是槽位 `tab:N`，槽位族 `tab:*`），按钮是槽位 `action`，把选中的方案带出去（比如 `iap.purchase {productId: …}`）。

地图路线模板：地图是能力视图，“使用当前位置”调用 `location.current`，取到后地图以它为中心（`center` 绑定 `vars.here`），被拒绝、取不到各有提示（和结算页一样放在正文的列里，不显示时不留空洞），行程卡片的“开始导航”调用 `link.open` 打开地图网页，不再自己显示“导航中”。钱包模板的“支付”调用 `scan.code`。

## 导出

只有用到能力的产品才有这些（没有用到的导出逐字节不变）：

| 产物 | 种类 | 内容 |
| --- | --- | --- |
| `packages/capabilities` | 生成 | `src/engine/capabilities/`（`lib/capabilities` 的四个文件原样复制）；`src/generated/types.ts`（每个能力的参数、结果、事件、视图属性的类型，`CapabilityMap`、`Capabilities`、`ViewSlotProps`）、`used.ts`（用到的能力、产品自己的能力）、`mocks.ts`（模拟规则）；`createAppCapabilities()`、`fail()`、`createMockCapabilities()`（`./mocks`，只在开发和测试时用）；自带测试 |
| `apps/*/src/custom/capabilities.ts` | 只写一次 | `export const capabilities: Capabilities = {}`，注释列出用到的能力。没写的能力回答 `not-implemented`，开发版在控制台说一次去哪里写，做法和后端处理函数先回答 501 一样 |
| `apps/*/src/generated/capabilities.ts` | 生成 | 注册表：自定义适配优先，再是平台默认，最后 `not-implemented`；运行时创建时接上它（`createRuntime({ capabilities: registry })`） |
| `apps/*/src/generated/platformCapabilities.ts` | 生成 | 通用能力的平台默认：Web 是 `window.open`、`navigator.clipboard`、`navigator.share`、文件选择框、`navigator.geolocation`；手机端是 `Linking`、`Share`、`expo-document-picker`；小程序是 `Taro.setClipboardData`（打开链接也是复制链接，小程序打不开外部网页）、`Taro.chooseImage` / `chooseMessageFile`。需要权限声明的（手机端和小程序的定位、相机）不给默认 |
| `apps/*/src/custom/slots/<名字>.tsx` | 只写一次 | 能力视图的真实实现：拿到设计给的属性（和替身一样）、尺寸、`onEvent`，在 `children` 里是设计的替身，写好之前就画它 |
| `apps/*/src/generated/slots.ts` | 生成 | 只引用每个插槽文件固定的默认导出；屏幕画 `<StoreMap center={…} markers={[…]} width={380} height={240}>{替身}</StoreMap>` |
| `AGENTS.md` | 生成 | “Platform capabilities”一节：适配写在哪里、怎样失败、不能在适配里决定结果、插槽、怎样用模拟验证 |

插槽的名字取自部件名（组的名字，否则组件的名字，如 `MapPlaceholder`），只有非 ASCII 的名字时用 `MapView`、`CameraView`、`RtcViewView`，重名加数字；同一份设计每次导出相同，重新导出不丢。生成的代码只引用插槽文件固定的默认导出，所以自定义代码写成什么样都接得上（第 9.3 节的插槽机制；第四批把它推广到所有占位组件）。

三端的应用都运行 `invoke`：产品 Web 打印 `useInvoke()`，手机端由生成的 `effects.ts` 交给运行时，小程序由套件的屏幕运行时运行；结果、失败、迟到的回答都按 `lib/app` 的 `Runtime.invoke` 处理。原型 Web 导出没有能力层（不打印）。导出报告的 `capability` 种类列出：能力视图（插槽还要写）、没有平台默认、要写适配的调用、目录和产品都没声明的能力、没有调用 `auth.oauth` / `payment.pay` 的登录或支付按钮。

## 智能体

应用内 AI 的提示词和工具指南（`BOUNDARY_GUIDE`）、`public/agent.md` 和 MCP 的说明都写明：平台能力用能力调用和能力视图表达，每个 `invoke` 都要设计 `catch`；支付按上面的三步走，结果页按订单状态显示，不要从按钮直接跳到“支付成功”。评测有一项真实模型任务 `payment-flow`（`evals/boundaryTasks.ts`，见 [evals/README.md](../evals/README.md) 的“支付流程”）：带微信支付按钮的结算页，作者只说“接上微信支付，付完在支付结果页显示这笔订单的结果”，检查下单、`createOrder` 之后调用 `payment.pay`、结果页只在支付回答之后打开并带上订单号、`payment.pay` 有 `catch`、结果页按订单状态显示。基线在 `evals/baselines/2026-11-08-stage3/`。

## 测试

- `lib/capabilities/capabilities.test.ts`：目录完整、有类型和失败类型，支付的结果里没有“已支付”；注册表在没有适配时回答 `not-implemented` 并只提示一次、适配和默认的顺序、`fail()` 的类型、超时、统计从不失败；模拟结果按示例、文档规则、场景规则回答，带上请求的参数，从文件库挑文件，重新开始后作废，并记录；读文件时清理；文档用到了哪些能力；操作的校验（不存在的能力、缺少必填参数、多余参数、视图不能调用、`then` 不接受 `when`）、声明 / 使用 / 模拟 / 删除，一步撤销。
- 一致性表（`lib/actions/consistency/rows.ts`）的“调用能力”八行：完成后读 `result`、失败读 `error.type`、未实现、不等结果、参数在那一步读、下单后调用支付、访客离开后的回答、重新开始后的回答；在解释器、预览、两种 Web、手机端套件和小程序套件上运行，已知分歧见[交互规则](交互规则.md)。
- 评测：`evals/boundary.test.ts` 用操作把支付流程做一遍好的（全部检查通过）和几种捷径（订单一创建就去结果页、不调用 `payment.pay`、没有 `catch`、结果页不看订单状态），各自的关键检查不通过。
- 导出：`lib/export/capabilities.test.ts`（包、注册表、插槽文件和屏幕里的插槽、平台默认、只写一次、没用到能力时什么都不加）；`bun run check:product <空文件夹>`（默认的 proof 产品，它的结算页调用 `payment.pay`）把 `packages/capabilities` 和三端的注册表、插槽放进真实的安装、类型检查、测试和构建（`shop` 产品没有用到能力，不生成这些）。

## 已知限制

- 导出的应用还不运行组件事件（`on:markerTap` 等，第四批）：插槽能发出事件，但设计里挂在事件上的动作还不打印，导出报告列为 `event`。
- 能力视图的属性绑定数据只在预览和 Web 里生效；插槽拿到的是设计里的值（第四批随屏幕中间表示一起解决）。
- 手机端和小程序的定位、相机、扫码没有默认适配（需要权限声明），回答 `not-implemented`，要在 `src/custom/capabilities.ts` 里写。
- 导出的应用在开发时也不自动用模拟结果：没写适配的能力回答 `not-implemented`（这正是要提示的），开发菜单和场景切换只换接口的模拟库。要在开发时看各种结果，在 `src/custom/setup.ts` 里 `runtime.setCapabilities(createMockCapabilities({ scenario }))`。
- `push.opened`（点开通知）只是目录里的平台事件：设计里还没有“收到它时跳到哪一屏”的写法，用屏幕参数表达深链接，由适配代码自己导航。
