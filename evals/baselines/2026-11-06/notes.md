# 2026-11-06 基线：人工分析

`gpt-6.1-sol`，推理强度 medium，16 个任务各跑一次（另有 paper-style 重跑一次，见下），视觉评分开。结果见 [summary.md](summary.md)、[results.json](results.json)；每次运行的完整记录（对话、调用、文档、截图）没有提交，按 `evals/README.md` 重跑即可得到同样结构的记录。下面的“证据”都是运行文件夹里的文件。

## 怎样得到的

bun run eval -- --record evals/baselines/2026-11-06 --artifacts <本地目录> --max-drawings 3 --judge
bun run eval -- --replay <本地目录> --record evals/baselines/2026-11-06 --title "Baseline: gpt-6.1-sol, effort medium"

- 一共 17 个智能体回合、1 次绘图（svg-tab-icon 用代码写 SVG），总用量约 1.5M token（83% 命中缓存），平均每个任务 33 秒。
- 第一次跑完后修了三处评分（不是智能体的问题），再用 `--replay` 重新评分：`tap-detail` 接受“点击时把行的 `{{字段}}` 写进变量、详情页绑定这些变量”的做法（预览里行的点击会先填入这一行，确实可用）；`finished` 不再把放弃的只读调用算作没处理的错误；HUD 的技能按钮认 `skill-button`。原始结论：12/16 通过。
- paper-style 第一次只改了风格，没有改任何屏幕，评测当时只给改过的屏幕截图，视觉评分没有图可看（给了 1 分）。评测改成“只改了整份文档时给所有屏幕截图”后重跑了这一项，两次结果相同（都生成并穿上了暖色风格，检查全部通过）。

## 智能体做错了什么

1. **含糊又有破坏性的请求，直接清空重做而没有先问**（vague-wipe，唯一失败的任务）。请求是“都不好看，全删了重做”，系统提示词要求“请求不清楚或会删掉作者大量工作时，先问一句”。智能体第一批就调用 `clear` 删掉 3 个屏幕、27 个组件，再按自己的理解重新设计（结果本身好看，视觉评分 5），回答里也没有问题。证据：`vague-wipe/calls.json` 第 3 步的 `apply_ops`（`clear`、`set_theme`、`set_custom_palette`、`add_screen`×3），`transcript.json` 第一句“我会把现有三个页面全部重做”。整回合仍是一步撤销（`undo` 检查通过），所以能挽回，但作者没有机会先说想要什么。
2. **猜错参数，整批操作被拒，多花一轮**（16 次运行里 5 次）。`apply_ops` 全有或全无，一个参数错，整批（最多十几个操作）都要重发：
   - 应用栏左侧按钮的点击位置写成 `actions.leading`，实际叫 `icon`（cart-ko 第 3 步、profile-ja 第 2 步）：属性叫 `leading`，点击位置却叫 `icon`，两次都踩到。
   - `split_into_atoms` 少了 `id`（dark-mode-switch 第 2 步）。
   - 枚举值写错：`box.surface`（cart-ko 第 6 步）、`avatar.size`（vague-wipe 第 4 步）。这两条报错把可选值说了两遍（“should be one of …; it takes one of …”）。
3. **每回合开头都在查目录**：15 次运行一共 36 次 `describe_part`（占全部工具调用的 28%），查的几乎都是 box、text、button、input 这几个原子，通常占掉第 1–2 步。系统提示词里没有原子的属性，模型只能每次现查。
4. **图片用了外链**（list-to-cards 第 6 步）：卡片的 `image` 写成维基共享资源的网址。之后两次截图都失败，报错只有“evaluate: [object Event]”，看不出是图片加载失败；智能体最后改成手写的 `data:image/svg+xml` 插图——这条路绕过了 `generate_svg` 的清理和绘图次数限制。它还试过把四张菜品图拼成一张 1024×1024 的“2×2 图集”、放在屏幕外（x 440）来省绘图次数（被评测的绘图上限拒绝）。
5. **读不到组件定义里的部件**（product-instances 第 3 步）：`describe_node` 对组件定义里的部件 id 报 not_found，智能体只能从大纲猜覆盖用的键。
6. **生成的风格偏素**（paper-style 两次）：“暖色纸张笔记本”只得到奶油底色、咖啡色文字和陶土色按钮，没有纸纹、横线这类效果；视觉评分 4 分，理由是“更像普通浅色主题”。
7. **调色板设置绕了一圈**（vague-wipe 第 3、8 步）：先 `set_custom_palette`，截图发现主色没变，又补了 `set_palette {key: "custom"}`。

## 顺带发现的（不是智能体的问题）

- **没给位置的底部导航栏落在屏幕中间**：`add_part navigation-bar` 不带 `at` 时，在没有编辑器的文档核心里（MCP 文件模式、评测）它落在屏幕中部、盖住内容，而工具指南写的是“栏会找到自己的边”。vague-wipe 第 4、5 步就是这样，智能体看截图后用 `move_node` 挪到了底部（第 8 步，`tool-screenshot-02.png`）。搭评测的起始文档时也遇到了（FAB 也一样落在中间）。
- 截图在页面上加载失败的图片会让整张截图失败（见第 4 条）。

## 这套任务的局限

- 这个模型在结构检查上几乎全过（15/16），视觉评分平均 4.8，区分度不够。下一步应加更难的任务：多屏应用并接好跳转、带照片的复刻、严格风格下的复杂表单、长屏滚动、已有组件的批量改造等。
- 每个任务只跑了一次；模型有随机性，比较改动时用 `--repeat 3` 看通过率。

## 建议的改法（按预计收益排序）

1. **破坏性操作先确认**：应用内智能体的 `clear`、删除屏幕、删除大量组件，在请求没有明确要删时先问，或者像 MCP 那样在编辑器里弹确认（`isDestructiveCall` 已经有了）；同时把“先问”这条规则放到提示词更显眼的地方并给一个例子。直接修掉唯一失败的任务，也是作者最在意的风险。
2. **把常用原子的属性放进系统提示词**（box、text、icon、button、input、image、avatar 的属性、枚举值和点击位置，一份几 KB 的速查表，随系统提示词一起缓存）：预计省掉每回合 2–4 次 `describe_part` 和一轮请求，约 10–20k 输入 token，也能减少第 2 条的猜错。
3. **参数容错和报错**：点击位置接受 `leading` 等别名（或在 `describe_part` 里写清每个点击位置的名字）；`apply_ops` 出错时告诉模型其余操作是成功的、只需重发出错的那个，或者允许“跳过出错的操作”的模式；去掉报错里重复的可选值。
4. **图片来源**：`image`/`src` 不接受外链（只接受 `data:` 和本项目的图片），提示词里说清楚；截图遇到加载失败的图片时跳过它并在结果里说明，而不是整张失败。
5. **能读组件定义**：`describe_node` / `list_components` 给出定义里的部件 id 和可覆盖的键。
6. **风格生成更有“质感”**：`generate_style` 的提示词鼓励用纹理、描边、规则（CSS 规则白名单内）表达“纸张”“手账”这类描述，并在穿上后截图自查一次。
7. **文档核心**：没给位置的栏（导航栏、FAB）放到它该在的边上，和工具指南一致。
